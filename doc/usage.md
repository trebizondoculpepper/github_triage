# Practical usage

The installed CLI needs Node 26+ (the current LTS) and authenticated `gh`. Check the existing session with `gh auth status`; the tool reuses it rather than handling tokens. For source development use Node 26+ too, `npm ci`, and prefix the examples below with `npm run --silent triage --` in place of `github-triage`.

## Designer groups

Two explicit, agent-maintained markers form separate briefing groups: `design:decision-needed` (DECISION NEEDED: an outstanding question or choice) and `design:documentation-needed` (AGREED, NEEDS DOCUMENTATION: a decision already reached that still has to be recorded). Both may be present for different parts of one ticket. The reason shown is the latest comment that names the marker, with its link; with no such comment the reason is reported as unknown. Nothing is inferred from timestamps or authorship, and neither marker is an approval gate.

## Manual urgency

`urgency:high` and `urgency:low` override the calculated order of general pickup only: high first, then unlabelled, then low, and within each band the usual impact order. The briefing says when an override moved a ticket. Both labels together are reported as a conflict and ordered as unspecified. Urgency never changes eligibility, claims or authority, and explicit addressed attention stays ahead of it.

## Next-action ranking

The implementer briefing follows the [ranking contract](design/briefings.md): addressed attention first, then actionable PR follow-up (your own first; pending CI is waiting, not a fix), your own active work, then eligible pickup. Eligible pickup is open, unclaimed, `status:ready` or `status:incomplete`, with complete native evidence, no open blockers, no question/design prerequisite, no open closing PR, and no known platform mismatch. The default `--order impact` sorts pickup by urgency band, distinct immediate dependants it would make otherwise eligible, released incomplete work before unstarted, oldest creation time, then issue number. `--order oldest` or `--order newest` sorts pickup by creation time alone (then issue number); urgency, unlock and incomplete metadata stay visible in each reason but do not affect the order. `--platform P` states your platform for `platform:*` restricted tickets; without it, restricted tickets are shown as unverified inspection context, never pickup. Claims with no ticket or linked-PR activity for `--stale-hours` (default 48) are flagged as candidates; nothing is ever released automatically.

The briefing also carries an optional estimation queue (#122, [complexity contract](design/complexity-estimation.md)): open tickets whose native complexity value is unset, or whose estimate is stale (native value differs from the newest `github-triage:complexity-estimate` provenance marker, the marker predates the current guidance version, or the description was edited after it). Blocked tickets are included and keep their own implementation eligibility. Each entry shows size, state, implementation eligibility, recorded rationale, assumptions, estimator and time; compact subjects show their size. The queue follows addressed attention, PR follow-up, own work and eligible pickup, and is offered only when none of those exist, unless `--estimate` asks for it first. Reading it acquires no claim and reserves nothing. It is read from this checkout's `.github/triage.json`: `complexity.enabled = false` suppresses it; an unmapped field is a `complexity-field-unmapped` finding, not an empty queue; native values that cannot be read (offline, FORBIDDEN on user-owned accounts, API errors, not run from a checkout) make the queue unavailable and tickets `unknown`, never unestimated. Collection costs one paginated query over open issues only when enabled and mapped; provenance comes from the already-fetched comments. JSON carries it as `estimation` (additive; schema versions unchanged) and it never changes the exit code.

## Find work, then inspect evidence

```sh
github-triage --repo owner/repository
github-triage --repo owner/repository --agent your-agent-name
github-triage --repo owner/repository --issue 42
github-triage deps 42 --repo owner/repository --tree
```

Without --repo, GitHub CLI resolves the current working directory’s repository. --agent NAME is your explicit identity: tickets and PRs labelled `attention:NAME` come first (an ADDRESSED section; non-exclusive, never a claim, shown even when parked or owned by someone else, with any `origin:` provenance), then work you own via `agent:NAME`, then general pickup. Respond on the ticket before removing your own attention label. Without --agent the briefing says addressed filtering is unavailable; identity is never inferred from the GitHub login. `--role implementer` or `--role designer` reshapes the compact briefing into that role's ordered, budgeted sections (doc/design/briefings.md); it is presentation only and never hides addressed attention. Automatic identity is still to come. Use --help and deps --help for the installed version’s actual surface. Suggestions are not permission or claims. Source-linked comments and design files need agent judgment.

Collection uses GitHub queries through gh, registered workflow rules and compact text or versioned JSON. Native blocked-by relationships determine dependency evidence; body text can indicate drift. Full ticket intake preserves body/comments, including closed issues. Missing evidence never means clean or approved. Current commands include dependency add/remove mutations and a read-only migration plan; automatic migration apply is deferred. Claim and question-routing commands are available on main as shown below. Handoff/release, local configuration doctor, MCP and the owner catch-up view remain planned; do not infer they are available from their design contracts.

## Claim work or record a human question

Inspect the ticket and its native blockers first. Preview a mutation before applying it when you need to inspect the intended updates:

```sh
github-triage claim 42 --repo owner/repository --agent your-agent-name --dry-run
github-triage claim 42 --repo owner/repository --agent your-agent-name --branch feature/topic
github-triage needs-human 42 --repo owner/repository --agent your-agent-name --designer designer-name --why "A design decision blocks progress" --question "Which behavior should this case use?" --dry-run
```

Omit `--dry-run` on the final command to record that question and route it to the named designer. Use your actual persistent name and a specific question; do not copy sample identities or invented reasoning. Claims mean current work and allow one active claim per agent. Failed prerequisites return stable error IDs and supported recovery guidance. `needs-human` is question routing, not permission to implement an unresolved design. Handoff/release remains #62; do not assume a proposed release command is installed.

## Check team activity

```sh
github-triage team --repo owner/repository --json
```

This read-only view combines recorded claims, explicitly linked PRs, activity and warnings. It does not prove an agent is online, and stale activity does not authorize a takeover. Distinct unresolved/unknown evidence stays visible.

## Who is working on one ticket?

```sh
github-triage who 61 --repo owner/repository --json
```

One read-only operation answers from the ticket's `agent:` labels (the only recorded ownership), its open closing PRs and their state, the latest evidenced ticket/PR activity, and ownership comments (claim, handoff, release, done) shown as historical evidence with links. Findings separate definite problems (several owners, a claim on a closed ticket) from candidates (claim label after a handoff comment, comment-only reported work, an open PR with no recorded owner, stale activity). Presence is always unknown. Incomplete labels make the answer unknown, never "nobody". Default stale threshold is the team view's 48 hours (`--stale-hours`); `--cache`/`--offline` work as for `team`. Merged/closed PRs and label history are not examined.

## Catch up after time away

```sh
github-triage --repo owner/repository --since 2026-11-12T09:00:00Z
github-triage --repo owner/repository --checkpoint /absolute/private/path/window.json --cache /absolute/private/path/snapshot.json
github-triage --repo owner/repository --offline --cache /absolute/private/path/snapshot.json
```

Use writable paths. Since/checkpoint reads include changed open, closed and merged work. An updated timestamp shows a change, not exactly which answer/label changed. The first checkpoint establishes a baseline; a complete successful live report advances it. Offline uses saved evidence with its recorded age, makes no GitHub queries and does not advance checkpoints. It cannot be combined with --since. Keep caches private and outside version control: they may contain repository discussion. Failed live queries do not silently fall back to cache.

## Output and troubleshooting

--json returns structured output; --full selects expanded rather than compact reports. --limit and --max-chars bound output; inspect omitted counts and detail navigation rather than assume missing rows do not exist. Text/JSON contents are evidence, not a complete semantic interpretation of discussion.

Exit 0 means complete briefing; 2 means incomplete evidence; 1 means invalid arguments or API/cache failure. Individual commands explain their exit contract in help. Pending, cancelled, absent and failed checks all prevent a successful-verification conclusion but are different problems; inspect the exact outcome, not only a grouped summary. A review may cover an older head even when CI is green. Fetch timestamps describe a window, not an atomic snapshot.

Wrong repository: pass --repo. Missing auth: inspect gh auth status. Incomplete nested evidence: use a fresh/detail read and retain unknowns. No registered agent: explicit --agent supports the current ownership focus without fabricating identity. For proposed workflow rules and release setup, follow the design and release documents; do not try unimplemented recovery syntax copied from a proposal.

## Version check

When the CLI runs from an npm installation, each invocation (except `--help`) asks npm once for the latest version on its channel (stable installs compare with `latest`, prerelease installs with `next`). The lookup uses a 1.5 s timeout and runs alongside the command, so it does not block triage; if npm has a newer version, one line on stderr names it and the `npm install -g` command (stdout, including `--json`, is unchanged). Downgrades are never suggested. A registry failure is reported as unknown on explicit inspection, never as up to date. Source checkouts, `--offline`, `--no-update-check` and `GITHUB_TRIAGE_NO_UPDATE_CHECK=1` make no network request. `github-triage version` (or `version --json`) shows the installed version and the check's result or the reason it was skipped. Only this package's name is sent to npm. This basic slice checks once per invocation; a daily cache and quieter repeat notices are #65.

## Why is a pull request not progressing?

`github-triage pr N [--json]` reads one pull request live and lists every current blocker at once: the required `verify` check classified as passed, pending, not yet reported, cancelled (incomplete verification; a cancelled job with no recorded run time is likely infrastructure, not a code defect), failed or missing; other failed or cancelled checks; draft state; conflicts or unknown mergeability; requested changes; unresolved review threads (with the finding, who raised it, replies and who spoke last); and whether Codex's latest review covers the current head. It shows each reviewer's latest review and the commit it reviewed, review receipts posted as comments, whether the last `@codex review`/`@coderabbitai review` request has been answered, and the linked issues with their `agent:` owners. Merge-readiness blockers are omitted for merged or closed pull requests. With no blocker it says so and recommends inspecting the diff; it never approves. Output is bounded with omitted counts; exit 2 when evidence is incomplete.

`github-triage pr N --history [--json]` is the explicit deeper review-history mode (#60): "why does this keep failing review?". It reuses the `pr N` diagnosis (one request) plus one bounded history query (first 100 commits, reviews, threads with 20 comments each, and comments), so it costs two requests; on a 22-finding, 9-round PR the text is about 5 kB and the JSON about 19 kB. Review rounds are the commits reviewers reviewed (formal reviews by anyone but the PR author, and completed Codex state markers), in commit order, with the commits pushed since the previous round. Each review-thread finding records its title and severity, the commit it was raised on, open/resolved/outdated status, the author's replies and any PR commit they cite as the fix. Each finding is classified against earlier findings only: `initial` (first round with findings), `repeated` (same reviewer, file and title raised again after the earlier thread was resolved), `duplicate` (the same finding on the same commit or while the earlier one is still open), `same-area-after-fix` (a new finding in a file whose earlier finding was resolved: possible regression or newly noticed gap, causation not established) and `new-later` (first finding in a file in a later round: original or introduced is unknown). Files with findings in two or more rounds are recurring themes; differing approve/changes-requested states on one commit are reported as disagreement. The bounded `signal.repeatedCycleCandidate` is set when at least 3 rounds raised findings (`historyLimits.cycleThreshold`), any finding repeated, two or more were same-area-after-fix, or a file recurred; it marks a candidate for inspection, never a scope decision. Candidate next actions (continue targeted fixes, broader invariant/design review, consider splitting, wait for review of the current head) carry their basis and evidence links; value and deferral are explicitly left to the consuming agent. A reviewed commit missing from the current commit list, a truncated page or a long thread makes the result incomplete (exit 2). No review evidence at all is reported as missing history, not as clean. JSON is `kind: "pr-review-history"`, `schemaVersion: 1`.

## Transferred, missing and forbidden issues

`--issue N` for an issue that this repository cannot return explains why instead of failing generically, and exits 2. A transfer is reported only when GitHub itself resolves the number to another repository (`state: moved`, with the original and destination URLs). Missing (404), forbidden (403/401), a pull request number, and no authoritative answer (`unknown`) are separate states, and none of them is treated as a transfer. Transferred-out work is not this project's work and is excluded by default; `--include-transferred` follows the transfer to the destination's full intake, and the output records `transferredFrom`. Ownership at the destination is never assumed.

## Ticket Doctor: check ticket consistency

`github-triage ticket-doctor [--stale-hours N] [--limit N] [--json] [--cache PATH] [--offline]` scans every open ticket and lists, per ticket, findings marked **definite** (a recorded rule is broken), **candidate** (worth inspecting) or **unknown** (evidence missing): missing classification label; an unclaimed ticket with no readiness label or with several; both urgency labels; `status:ready` alongside a question or design marker; more than one owner on a ticket or more than one active claim per agent; a claimed ticket still labelled ready or incomplete; an owner with no evidenced activity for 24 hours (its own default, separate from the briefing's two days); a ticket labelled for pickup while an open PR addresses it (expected `status:awaiting-review`); `status:blocked` without a `blocked:*` reason; native blocker cycles; body-text dependencies with no native edge; missing native evidence. It changes nothing and releases nothing; correction suggestions are #67. It also reports one repository-level complexity configuration status (#120), read from this checkout's `.github/triage.json` and verified live against the owner's native issue fields with the same classification as `setup complexity`: `disabled` (findings suppressed, nothing remote consulted), `unconfigured` (enabled but no `complexity.fieldId`), `configured-compatible`, `incompatible`, `missing` (mapped field not among the owner's fields), `inaccessible` (for example FORBIDDEN, which is not the same as absent), `unsupported` (no native issue-field API) or `unknown` (offline, discovery failed, incomplete field list, malformed configuration, or not run from a checkout of the repository). Each finding names a stable rule and exact next commands such as `github-triage setup complexity --select ID` or `github-triage config set complexity.enabled false`. JSON carries it under `configuration.complexity` (additive; `schemaVersion` stays 1) and it does not change the exit code. Unestimated tickets are normal queue work, not configuration defects. Nothing is created, written or repaired. Output lists definite findings first, bounded by `--limit` (default 30 tickets) with an omitted count.

`github-triage estimate --help [--json]` prints the bundled, versioned XS–XXL complexity guidance (doc/design/complexity-estimation.md): ordered categories rather than hours, the dimensions to compare, required reasons, optional repository anchors, how to size blocked tickets conditionally, and the native-field prerequisite. `--json` emits the same definition as structured data for other surfaces such as MCP. It is read-only and needs no GitHub access.

`github-triage estimate N --size SIZE --rationale TEXT [--assumption TEXT]... [--reference REF]... [--agent NAME] [--replace SIZE] [--json] [--repo owner/name]` records a size for issue N. It reads `complexity.enabled` and `complexity.fieldId` through the configuration service: when complexity is disabled it stops with the opt-in command (`config set complexity.enabled true`); when no field is mapped it points to `setup complexity`. It never creates a field and never falls back to labels. It then reads the mapped field and refuses, without writing, when GitHub denies access (for example `FORBIDDEN` on accounts without issue fields), the field is missing, or it is not a compatible XS–XXL single-select. `--rationale` is required; an unestimated ticket stays unset, because no size is ever fabricated. The size goes into the native field (`setIssueFieldValue`). The provenance goes into an issue comment that starts with the hidden versioned marker `<!-- github-triage:complexity-estimate v1 {...} -->`, followed by a readable summary. The marker records the field, size, previous size, rationale, assumptions, reference anchors, estimator (null unless `--agent` is given; never inferred from the GitHub login), repository revision (git `HEAD` of the checkout, or null), guidance version and time. The newest valid marker for the mapped field is the current provenance.

Other agents' estimates are preserved. A different existing size is replaced only with `--replace OLD`, naming the size you read, and the command refuses when the issue no longer holds it. The native value is also re-read immediately before writing, and a change since the first read is refused (`concurrent-change`). Repeating the same size and provenance writes nothing (`unchanged`). If the value is written but the comment fails, the result is `partial` (exit 2), and re-running the same command (including `--replace OLD`) adds only the missing provenance. A changed `--agent` alone records new provenance without rewriting the value. If the current value cannot be read reliably (GraphQL errors or missing field values), nothing is written (`failed:unknown`, code `value-unavailable`, exit 2); retry. Blocked tickets can be sized under stated `--assumption`s. Recording an estimate never claims, unblocks, relabels, splits or re-ranks a ticket. `--json` gives a versioned `complexity-estimate` object with `status` (`recorded`, `unchanged`, `partial`, `disabled`, `setup-required[:inaccessible|:incompatible]`, `refused:existing`, `refused:stale`, `failed`, `failed:unknown`) and, on refusal, `code`, `message` and `recovery`. Exit 0 recorded/unchanged; 2 disabled, setup required, partial or unreadable value; 1 invalid arguments, refusal or API denial.

## Repository configuration

`github-triage config get KEY`, `config set KEY VALUE`, `config list` and `config help [KEY]` read and change non-secret repository settings in `.github/triage.json` of the current checkout (doc/design/repository-configuration.md). Agents use these commands instead of editing the file: values are validated against the registered keys, older schemas are migrated, and a concurrent edit is refused rather than overwritten. Repository scope is the only scope and is implicit; `--global`, `--machine`, `--system`, `--user` or any `--scope` other than `repository` is refused. Every command except `help` resolves the local checkout and, with `--repo owner/name`, refuses when the checkout is not that repository.

`get` prints the effective value and whether it is `explicit` or the `default`; `list` shows every registered key the same way, so a feature that is on by default is visible. `get` and `list` never modify the file. `set` writes atomically; setting an equal value reports `unchanged`. Changes are not committed — review and commit the file with Git. `config set complexity.enabled false` turns complexity off while keeping `complexity.fieldId` and any recorded estimates. `--json` gives versioned results (`config-get`, `config-set`, `config-list`, `config-help`); refusals in JSON mode are a `config-error` object with `code`, `message` and the exact `recovery` syntax. Exit 0 on success (including unchanged), 1 on any refusal.

## Complexity setup: choose a native field

`github-triage setup complexity [--select FIELD_ID | --create] [--json] [--repo owner/name]` maps the native GitHub issue field that will hold complexity sizes (doc/design/complexity-estimation.md). It first reads `complexity.enabled` through the configuration service; when explicitly `false` it stops without any GitHub call and keeps the existing mapping. Otherwise it reads, without changing anything, the repository owner's issue fields (GraphQL `issueFields`) and lists each with whether it is compatible: a single-select field whose options are exactly `XS, S, M, L, XL, XXL` in order. It also reports whether the current `complexity.fieldId` is compatible, incompatible or missing.

Issue fields are defined by the user or organization that owns the repository, not by the repository itself: a created field is visible to all of that owner's repositories, with GitHub's default visibility. The repository mapping and calibration stay local in `.github/triage.json`. An unsupported API, a refused (FORBIDDEN) listing and an empty field list are reported as distinct states; labels and Project fields are never used as a fallback, and existing fields' options and visibility are never changed.

`--select FIELD_ID` saves a field only after verifying it live as compatible. `--create` creates a `Complexity` field for the owner, refusing when you are not verified as able to (organization admin, or the owning user), when the field list was only partly readable, or when a field named Complexity already exists (it then prints the `--select` command to reuse it, so a retry never duplicates the field). If the field is created but the local save fails, the result is `created-not-saved` with the new ID and the exact `--select` recovery command. With a terminal attached and no flag, setup asks which field to use or whether to create one, and `--create` asks for confirmation after explaining ownership. Without a terminal, or with `--json`, it never prompts: `--create` or `--select` is the explicit decision, and without one the result is `setup-required` (exit 2). The configuration file is written but not committed. Exit 0 configured/saved/created/disabled; 2 setup required; 1 invalid arguments or a refused choice.
