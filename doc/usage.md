# Practical usage

The installed CLI needs Node 26+ (the current LTS) and authenticated `gh`. Check the existing session with `gh auth status`; the tool reuses it rather than handling tokens. For source development use Node 26+ too, `npm ci`, and prefix the examples below with `npm run --silent triage --` in place of `github-triage`.

## Designer groups

Two explicit, agent-maintained markers form separate briefing groups: `design:decision-needed` (DECISION NEEDED: an outstanding question or choice) and `design:documentation-needed` (AGREED, NEEDS DOCUMENTATION: a decision already reached that still has to be recorded). Both may be present for different parts of one ticket. The reason shown is the latest comment that names the marker, with its link; with no such comment the reason is reported as unknown. Nothing is inferred from timestamps or authorship, and neither marker is an approval gate.

## Manual urgency

`urgency:high` and `urgency:low` override the calculated order of general pickup only: high first, then unlabelled, then low, and within each band the usual impact order. The briefing says when an override moved a ticket. Both labels together are reported as a conflict and ordered as unspecified. Urgency never changes eligibility, claims or authority, and explicit addressed attention stays ahead of it.

## Next-action ranking

The implementer briefing follows the [ranking contract](design/briefings.md): addressed attention first, then actionable PR follow-up (your own first; pending CI is waiting, not a fix), your own active work, then eligible pickup. Eligible pickup is open, unclaimed, `status:ready` or `status:incomplete`, with complete native evidence, no open blockers, no question/design prerequisite, no open closing PR, and no known platform mismatch. The default `--order impact` sorts pickup by urgency band, distinct immediate dependants it would make otherwise eligible, released incomplete work before unstarted, oldest creation time, then issue number. `--order oldest` or `--order newest` sorts pickup by creation time alone (then issue number); urgency, unlock and incomplete metadata stay visible in each reason but do not affect the order. `--platform P` states your platform for `platform:*` restricted tickets; without it, restricted tickets are shown as unverified inspection context, never pickup. Claims with no ticket or linked-PR activity for `--stale-hours` (default 48) are flagged as candidates; nothing is ever released automatically.

The briefing also carries an optional estimation queue (#122, #152, [complexity contract](design/complexity-estimation.md)): open tickets with no `complexity:XS`..`complexity:XXL` size label, or whose estimate is stale (the size label differs from the newest label-backed `github-triage:complexity-estimate v2` provenance marker, the marker predates the current guidance version, or the description was edited after it). Sizes are read from the labels already collected in the snapshot (also offline from a cache): no native fields, setup, mapping or extra queries. Blocked tickets are included and keep their own implementation eligibility. Several size labels (or an unrecognized `complexity:` label) make a ticket a conflict to inspect, listed separately and never queued; a truncated label page makes it `unknown`, never unestimated. Each entry shows size, state, implementation eligibility, recorded rationale, assumptions, estimator and time; compact subjects show their size. The queue follows addressed attention, PR follow-up, own work and eligible pickup, and is offered only when none of those exist, unless `--estimate` asks for it first. Reading it acquires no claim, creates no label and reserves nothing. Complexity is enabled by default; `complexity.enabled = false` in this checkout's `.github/triage.json` suppresses the queue without deleting labels or history. JSON carries it as `estimation` and it never changes the exit code.

With `--role designer` (#246, [queue contract](design/impact-estimation.md#the-unassessed-work-queue)), NEXT STEPS renders the blended `rankedActions` ([blended queues](design/blended-action-queues.md)) instead of the legacy target list: each line names the action kind and reason codes, the paired `impact · complexity · unlocks` line and the exact next command. Addressed attention, delivery follow-up and designer duties (decisions, documentation, design review) come first; then impact assessment (`assess-impact`) for open tickets whose impact is `unassessed` or `stale`, blocked tickets included under stated assumptions, with tickets of current complexity XS or S boosted first; then new design work. Conflicting or invalid impact labels produce an `inspect-assessment` action whose command is the Ticket Doctor fix (`--replace-invalid` for invalid labels); incomplete evidence (`unknown`) is counted, never queued; parked tickets are not queued. Each assessment command is `github-triage estimate N --metric impact --size SIZE --rationale TEXT --repo owner/name`; assessing acquires no claim. The designer compact JSON adds an `impactEstimation` object: `status`, `guidanceVersion`, `eligible` (open unassessed or stale tickets), `ranked` and `shown` assessment counts, `offered` (at least one ranked, regardless of the display limit), `inspections` (`ranked`, `shown`), `conflicts`, `invalid`, `unknown`, `guidance` and `boundaries`; text ends NEXT STEPS with the same counts. With `impact.enabled = false` no impact action is offered and the summary line is hidden; labels and provenance are kept. The legacy `actions` and `role.next` arrays, other roles and the non-role briefing are unchanged (#259 moves the implementer view).

Report subjects also show designer impact and implementer complexity side by side (#247, [impact contract](design/impact-estimation.md#side-by-side-display)). Compact subjects and expanded issue entries (CLI JSON and MCP) carry a new `assessments` object: `impact` and `complexity`, each with a paired `state` (`current`, `stale`, `unassessed`, `conflict`, `invalid`, `unknown`, `disabled`), a `size` (only for `current` and `stale`) and `provenance` (the newest trusted provenance comment URL, or null), plus the computed immediate-unlock utility `unlocks` and `unlocksUnknown`. It is null for pull requests. Text shows one line per subject, impact first: `impact L · complexity S · unlocks at least 2`; the `--issue N` view adds the provenance links. The existing `complexity` and `estimation` fields are unchanged. A provenance comment counts only when its author and any last editor have write, maintain or admin permission; comment author type and edit history arrive in the existing comment query, and permission is asked through the per-run cache, at most one request per distinct marker author or editor login per run. Offline reads make no permission request, so provenance-backed states are `unknown` there.

Compact briefings end with a bounded workflow guide (#71, [contract](design/workflow-guide.md)): one line per registered rule (attention first, pickup eligibility, ordering, one claim, claim/release/needs-human syntax, which commands change GitHub), generated from the same policy objects and command registry the tool enforces, at most 900 Unicode code points including the pointer to `github-triage process`. It follows the evidence and counts against `--max-chars`; when it does not fit, only the pointer is printed with an explicit omission notice. JSON carries it additively as `process` (`schemaVersion`, deterministic `policyVersion` hash of the guidance-bearing policy, `enabled`, `source` cli/config/default, rule IDs, `guide` or null, `pointer`, `omitted`, `guideCodePoints`, `guideBytes`, `diagnostics`); the briefing `schemaVersion` is unchanged. Opt a project out with `github-triage config set processGuide false` (stored in `.github/triage.json`; a one-line pointer with the policy version remains); `--guide`/`--no-guide` override for one run and conflict if both are given. Configuration is only applied from a checkout whose GitHub remote matches the briefed repository; a missing, malformed, unknown-key, future-schema or mismatched configuration falls back to the guide being shown, with a diagnostic, and never makes the briefing incomplete. `github-triage process [--json]` prints the full guide (rules with detail, implemented commands, limitations) locally without GitHub, credentials or configuration; `--help` has a short generated Workflow section and lists the GitHub-mutating commands from the same registry.

## Find work, then inspect evidence

```sh
github-triage --repo owner/repository
github-triage --repo owner/repository --agent your-agent-name
github-triage --repo owner/repository --issue 42
github-triage deps 42 --repo owner/repository --tree
```

Without --repo, GitHub CLI resolves the current working directory’s repository. --agent NAME is your explicit identity: tickets and PRs labelled `attention:NAME` come first (an ADDRESSED section; non-exclusive, never a claim, shown even when parked or owned by someone else, with any `origin:` provenance), then work you own via `agent:NAME`, then general pickup. Respond on the ticket before removing your own attention label. Without --agent the briefing says addressed filtering is unavailable; identity is never inferred from the GitHub login. `--role implementer` or `--role designer` reshapes the compact briefing into that role's ordered, budgeted sections (doc/design/briefings.md); it is presentation only and never hides addressed attention. Automatic identity is still to come. Use --help and deps --help for the installed version’s actual surface. Suggestions are not permission or claims. Source-linked comments and design files need agent judgment.

Collection uses GitHub queries through gh, registered workflow rules and compact text or versioned JSON. Native blocked-by relationships determine dependency evidence; body text can indicate drift. Full ticket intake preserves body/comments, including closed issues. Missing evidence never means clean or approved. Current commands include dependency add/remove mutations and a read-only migration plan; automatic migration apply is deferred. Claim and question-routing commands are available on main as shown below. Handoff/release, MCP and the owner catch-up view remain planned; do not infer they are available from their design contracts.

## Claim work or record a human question

Inspect the ticket and its native blockers first. Preview a mutation before applying it when you need to inspect the intended updates:

```sh
github-triage claim 42 --repo owner/repository --agent your-agent-name --dry-run
github-triage claim 42 --repo owner/repository --agent your-agent-name --branch feature/topic
github-triage needs-human 42 --repo owner/repository --agent your-agent-name --designer designer-name --why "A design decision blocks progress" --question "Which behavior should this case use?" --dry-run
```

Omit `--dry-run` on the final command to record that question and route it to the named designer. Use your actual persistent name and a specific question; do not copy sample identities or invented reasoning. Claims mean current work and allow one active claim per agent. Failed prerequisites return stable error IDs and supported recovery guidance. `needs-human` is question routing, not permission to implement an unresolved design. To hand over your claim in one operation use `github-triage release N --agent NAME --as ready|incomplete|parked|done [--note TEXT] [--pr URL|--change URL] [--dry-run]` (#62): it re-reads live state, posts a handoff comment, then removes only your `agent:NAME`, sets one handoff readiness label (`ready` → `status:ready`; `incomplete`/`parked` → `status:incomplete`, still pickable; `done` with an open PR, supplied or linked → `status:awaiting-review`, out of pickup; `done` without one → no readiness label, reported for inspection). The comment carries the outcome, note and deliverable. It never closes the issue or PR and never chooses the outcome for you. A missing note is reported but never blocks release. Questions, blockers, attention, needs-design and other owners are kept. The comment is posted before labels change and records the whole label plan (target label, labels to remove, other owners retained, the claim's start) in a hidden marker, so a failed comment changes nothing and a failed label edit leaves a durable record of intent. Each step is reported done/failed/skipped with a safe retry command. A retry is accepted only when such a record exists for the current claim: it applies exactly the recorded label plan (keeping the recorded owners) without a second comment, refuses `RELEASE_DIVERGED` if an owner or readiness label appeared after the record, and refuses `RELEASE_PENDING` if a different outcome is requested. Without a record, a ticket whose claim label is gone is `NOT_CLAIMED`; label history alone never authorises a release. With `--as done`, a verified open closing PR linked to the issue establishes `status:awaiting-review` even if the supplied `--pr` is merged, closed or unknown. An unverifiable `--pr` is reported `UNKNOWN`, not guessed merged. Refusals (`NOT_CLAIMED`, `RELEASE_DIVERGED`, `RELEASE_PENDING`, `EVIDENCE_INCOMPLETE`, `TICKET_CLOSED` for non-done outcomes) follow the usual error-ID contract. `release --help` explains the transitions. For review rework on your own pull request, reclaim explicitly with `github-triage claim N --agent NAME --rework`: it is accepted only when the issue is `status:awaiting-review`, an open closing PR exists, and the latest recorded release on the issue is your own `done` handoff (otherwise `REWORK_NOT_AUTHORISED`); it removes `status:awaiting-review` and claims as usual, and you release `--as done` again when finished. Awaiting-review issues never become general pickup. Suggested recovery commands never contain shell comments; alternatives are listed as separate commands, each carrying `--repo`.

## Check team activity

```sh
github-triage team --repo owner/repository --json
```

This read-only view combines recorded claims, explicitly linked PRs, activity and warnings. It does not prove an agent is online, and stale activity does not authorize a takeover. Distinct unresolved/unknown evidence stays visible.

## Who is working on one ticket?

```sh
github-triage who 61 --repo owner/repository --json
```

One read-only operation answers from the ticket's `agent:` labels (the only recorded ownership), its open closing PRs and their state, the latest evidenced ticket/PR activity, and ownership comments (claim, handoff, release, done) shown as historical evidence with links. Findings separate definite problems (several owners, a claim on a closed ticket) from candidates (claim label after a handoff comment, comment-only reported work, an open PR with no recorded owner, stale activity). Presence is always unknown. Incomplete labels make the answer unknown, never "nobody". Default stale threshold is the team view's 48 hours (`--stale-hours`); `--cache`/`--offline` work as for `team`. Merged/closed PRs and label history are not examined.

## Catch up after time away

```sh
github-triage --repo owner/repository --since 2026-11-12T09:00:00Z
github-triage --repo owner/repository --checkpoint /absolute/private/path/window.json --cache /absolute/private/path/snapshot.json
github-triage --repo owner/repository --offline --cache /absolute/private/path/snapshot.json
```

Use writable paths. Since/checkpoint reads include changed open, closed and merged work. An updated timestamp shows a change, not exactly which answer/label changed. The first checkpoint establishes a baseline; a complete successful live report advances it. Offline uses saved evidence with its recorded age, makes no GitHub queries and does not advance checkpoints. It cannot be combined with --since. Keep caches private and outside version control: they may contain repository discussion. Failed live queries do not silently fall back to cache.

## Output and troubleshooting

--json returns structured output; --full selects expanded rather than compact reports. --limit and --max-chars bound output; inspect omitted counts and detail navigation rather than assume missing rows do not exist. Text/JSON contents are evidence, not a complete semantic interpretation of discussion.

Exit 0 means complete briefing; 2 means incomplete evidence; 1 means invalid arguments or API/cache failure. Individual commands explain their exit contract in help. Pending, cancelled, absent and failed checks all prevent a successful-verification conclusion but are different problems; inspect the exact outcome, not only a grouped summary. A review may cover an older head even when CI is green. Fetch timestamps describe a window, not an atomic snapshot.

Wrong repository: pass --repo. Missing auth: inspect gh auth status. Incomplete nested evidence: use a fresh/detail read and retain unknowns. No registered agent: explicit --agent supports the current ownership focus without fabricating identity. For proposed workflow rules and release setup, follow the design and release documents; do not try unimplemented recovery syntax copied from a proposal.

## Version check

When the CLI runs from an npm installation, an ordinary invocation (except `--help`) compares the installed version with npm's matching channel (stable installs compare with `latest`, prerelease installs with `next`). The result is kept in one small JSON file, `update-check.json`, in the per-user cache directory (`env-paths('github-triage').cache`: `$XDG_CACHE_HOME/github-triage-nodejs` or `~/.cache/github-triage-nodejs` on Linux, `~/Library/Caches/github-triage-nodejs` on macOS, `%LOCALAPPDATA%\github-triage-nodejs\Cache` on Windows), shared by every project checkout and separate from settings and identity. npm is asked at most once per channel per 24 hours, and a failed lookup also waits 24 hours before retrying; there is no background scheduler. The lookup uses a 1.5 s timeout and runs alongside the command, so it does not block triage; if npm has a newer version, one line on stderr names it and the `npm install -g` command, at most once per available version per 24 hours (stdout, including `--json`, is unchanged). After an upgrade, the cached version is compared with the new installed version, so no obsolete notice repeats. Downgrades are never suggested. A registry failure, or a missing or corrupt cache, is never treated as up to date. Concurrent invocations coordinate through a short-lived lock file (wait at most 250 ms; a lock older than 10 s is broken as stale); if the cache cannot be written or the lock cannot be taken, the optional check is skipped rather than repeated. Deleting the cache file is always safe. Source checkouts, `--offline`, `--no-update-check` and `GITHUB_TRIAGE_NO_UPDATE_CHECK=1` make no network request and do not touch the cache. `github-triage version` (or `version --json`) shows the installed version and the check's result or the reason it was skipped. Only this package's name is sent to npm. Measured overhead with a warm cache is under 1 ms per invocation.

## Why is a pull request not progressing?

`github-triage pr N [--json]` reads one pull request live and lists every current blocker at once: the required `verify` check classified as passed, pending, not yet reported, cancelled (incomplete verification; a cancelled job with no recorded run time is likely infrastructure, not a code defect), failed or missing; other failed or cancelled checks; draft state; conflicts or unknown mergeability; requested changes; unresolved review threads (with the finding, who raised it, replies and who spoke last); and whether Codex's latest review covers the current head. It shows each reviewer's latest review and the commit it reviewed, review receipts posted as comments, whether the last `@codex review`/`@coderabbitai review` request has been answered, and the linked issues with their `agent:` owners. Merge-readiness blockers are omitted for merged or closed pull requests. With no blocker it says so and recommends inspecting the diff; it never approves. Output is bounded with omitted counts; exit 2 when evidence is incomplete.

`github-triage pr N --history [--json]` is the explicit deeper review-history mode (#60): "why does this keep failing review?". It reuses the `pr N` diagnosis (one request) plus one bounded history query (first 100 commits, reviews, threads with 20 comments each, and comments), so it costs two requests (four if the head moved between them: it retries once, and a head that still differs is reported as an inconsistent snapshot, exit 2, never combined); on a 22-finding, 9-round PR the text is about 5 kB and the JSON about 19 kB. Review rounds are the commits reviewers reviewed (submitted formal reviews — a PENDING draft is not a review — by anyone but the PR author, and completed Codex state markers), in commit order, with the commits pushed since the previous round. Each review-thread finding records its title and severity, the commit it was raised on, open/resolved/outdated status, the author's replies and any PR commit they cite as the fix. Each finding is classified against earlier findings only: `initial` (first round with findings), `repeated` (same reviewer, file and title raised on a commit at or after a fix commit the author cited for the earlier thread), `duplicate` (the same finding on the same commit or while the earlier one is still open), `same-area-after-fix` (a new finding in a file whose earlier finding has a cited fix at or before this finding's commit: possible regression or newly noticed gap, causation not established) `recurrence-unordered` (either of the previous two shapes where the earlier thread is resolved now but no cited fix establishes that it was resolved first; it never drives the cycle signal) and `new-later` (first finding in a file in a later round: original or introduced is unknown). Files with findings in two or more rounds are recurring themes; differing approve/changes-requested states on one commit are reported as disagreement. The bounded `signal.repeatedCycleCandidate` is set when at least 3 rounds raised findings (`historyLimits.cycleThreshold`), any finding repeated, two or more were same-area-after-fix, or a file recurred; it marks a candidate for inspection, never a scope decision. Candidate next actions (continue targeted fixes, broader invariant/design review, consider splitting, wait for review of the current head) carry their basis and evidence links; value and deferral are explicitly left to the consuming agent. A reviewed commit missing from the current commit list, a truncated page or a long thread makes the result incomplete (exit 2). No review evidence at all is reported as missing history, not as clean. JSON is `kind: "pr-review-history"`, `schemaVersion: 1`.

## Transferred, missing and forbidden issues

`--issue N` for an issue that this repository cannot return explains why instead of failing generically, and exits 2. A transfer is reported only when GitHub itself resolves the number to another repository (`state: moved`, with the original and destination URLs). Missing (404), forbidden (403/401), a pull request number, and no authoritative answer (`unknown`) are separate states, and none of them is treated as a transfer. Transferred-out work is not this project's work and is excluded by default; `--include-transferred` follows the transfer to the destination's full intake, and the output records `transferredFrom`. Ownership at the destination is never assumed.

## Doctor: check local configuration

`github-triage doctor [--agent NAME] [--role NAME] [--entry KEY | --harness NAME] [--repo owner/name] [--json]` runs independent read-only checks. Current stable IDs are `runtime.node`, `gh.available`, `gh.auth`, `project.checkout`, `identity.file`, `identity.git-ignored`, `identity.git-tracked`, `identity.parse`, `identity.entry`, `identity.name`, `identity.triage-role`, `identity.agent` and `triage.role`. The root `agent-inbox.toml` is read through the shared identity service and entry resolver (`--entry`, then `--harness`, then the detected harness), so an absent file, a malformed file (line/column only), a missing or ambiguous entry, a missing or invalid persisted name and a missing or invalid `triage_role` are separate findings, each with exact `github-triage config set identity.… --entry KEY --repo owner/name` or `doctor --entry KEY` recovery commands. A generic `role` key is never read as a triage role. Without `--agent`/`--role`, `identity.agent` and `triage.role` use the selected entry's persisted `name` and `triage_role`; explicit options still win. Nothing is created, repaired or untracked, and no other entry's values or file text are shown. JSON is additive: `schemaVersion` stays 1 and the report gains `entry`. Intentional changes from the first delivery: the placeholder `identity.compatibility` check is removed, `identity.entry` reports real selection instead of `unsupported`, and a `triage.role` with no evidence is `unknown` (exit 2 when nothing else fails) instead of `unsupported`.

Each check has `id`, `status`, `source`, `detail` and `next` (supported recovery commands). Statuses are `ok`, `missing`, `invalid`, `access`, `unsupported` (this version cannot determine it) and `unknown` (evidence unavailable). JSON schema version 1 contains `scope: "local-configuration"`, `repository`, `agent`, `role`, `checks` and per-status `summary` counts. Paths in results are relative to the checkout; credentials and raw auth output are not returned.

Current exit behavior is `1` for any missing/invalid/access finding; otherwise `2` if any unknown remains; otherwise `0`. Unsupported checks do not currently change that exit code, so exit 0 alone is not proof that every capability was verified: inspect statuses and summary. Doctor never repairs configuration, creates fields, refreshes credentials or changes Git tracking implicitly.

The owner confirmed retaining root-level agent-inbox.toml for local identity; the clarified contract is doc/design/identity.md. Current checks remain, and external check-ins are not required. Explicit selection remains supported while shared persisted lookup/configuration is implemented under #70/#38/#64/#25. The earlier field-permission proposal is withdrawn; [labels-only complexity](design/complexity-estimation.md) is delivered separately (#151–#153).

## Ticket Doctor: check ticket consistency

`github-triage ticket-doctor [--stale-hours N] [--limit N] [--json] [--cache PATH] [--offline]` scans every open ticket and lists, per ticket, findings marked **definite** (a recorded rule is broken), **candidate** (worth inspecting) or **unknown** (evidence missing): missing classification label; an unclaimed ticket with no readiness label or with several; both urgency labels; `status:ready` alongside a question or design marker; more than one owner on a ticket or more than one active claim per agent; a claimed ticket still labelled ready or incomplete; an owner with no evidenced activity for 24 hours (its own default, separate from the briefing's two days); a ticket labelled for pickup while an open PR addresses it (expected `status:awaiting-review`); `status:blocked` without a `blocked:*` reason; native blocker cycles; body-text dependencies with no native edge; missing native evidence. It changes nothing and releases nothing. Through the shared label classifier it reports conflicting complexity size labels (`complexity-label-conflict`, definite, with inspect and `estimate` suggestions); unestimated tickets are normal queue work, not findings, and truncated labels are already `labels-incomplete`. The field-era repository configuration status (#120) is no longer evaluated. Nothing is created, written or repaired. Output lists definite findings first, bounded by `--limit` (default 30 tickets) with an omitted count.

Every finding also carries a correction plan (#67; JSON `findings[].plan`, additive, `schemaVersion` stays 1): `facts` it relies on (for example a cycle path `#11 -> #12 -> #11` or a stale claim's last activity), `judgment` (true when the steps are alternatives to choose between, not one fix) and ordered `steps`. Each step has `kind` (`command`: a delivered `github-triage` mutation such as `release`, `needs-human` or `deps add/remove`; `inspect`: a read-only command such as `who`, `team`, `pr`, `deps --tree` or `--issue`; `manual`: a plain `gh issue edit` label change where no triage command covers it), an optional `choice` name (`keep-high`, `keep-low`, `remove-both`, `remove-11-on-12`, …), `argv` and the shell-quoted `command` with `--repo` inside it and no comments, the `<UPPER>` `placeholders` a person or agent must fill, `runBy` and `preconditions`. Plans are deterministic for the same snapshot. Nothing is ever run. Claim commands are addressed only to the claimant named in the label (`runBy`), never to another agent: inactivity is not permission, and stale-claim plans start with `who N`. A merged-PR leftover suggests the claimant's `release --as done` and never closes the issue. Unknown findings (missing or truncated evidence) get only inspection steps. Dependency cycles list each possible edge removal without choosing one; body-text drift offers `deps add` for same-repository references.

`github-triage estimate --help [--metric complexity|impact] [--json]` prints the bundled, versioned XS–XXL complexity guidance (doc/design/complexity-estimation.md): ordered categories rather than hours, the dimensions to compare, required reasons, optional repository anchors, how to size blocked tickets conditionally, and the label storage. `--json` emits the same definition as structured data for other surfaces such as MCP. It is read-only and needs no GitHub access. `--metric impact` (#246) prints the bundled, versioned impact (judged benefit) guidance from its own single definition instead, and `--json` then gives an `impact-guidance` object (`schemaVersion` 1); without `--metric` the output is the complexity guidance as before. `github-triage-mcp --help` carries a bounded rendering of the same impact definition (scale, bands, method, boundaries) and the CLI commands for the full guidance and for recording; the MCP server itself stays read-only.

`github-triage estimate N --size SIZE --rationale TEXT [--assumption TEXT]... [--reference REF]... [--agent NAME] [--replace SIZE] [--json] [--repo owner/name]` records a size for issue N as the label `complexity:SIZE` (#152). It reads `complexity.enabled` through the configuration service and stops with the opt-in command when complexity is disabled; no other setup is needed. `--rationale` is required and justifies the size you assign; an earlier or conflicting estimate needs no explanation, agreement or separate change reason. It reads the ticket's labels and the repository's definition of the requested label fresh. When the repository lacks that label it is created (canonical uppercase suffix); an existing case-equivalent definition is reused without changing its colour or description, and an already-exists race is settled by re-reading. Label creation needs write access; a denial is reported with recovery and leaves the ticket untouched. The new label is added and every other recognized size label is removed one by one, so unrelated labels are preserved and the label collection is never replaced from a snapshot. The provenance goes into an issue comment starting with the hidden marker `<!-- github-triage:complexity-estimate v2 {...} -->` (label-backed, no field IDs): size, every observed previous size, rationale, assumptions, reference anchors, estimator (null unless `--agent` is given; never inferred from the GitHub login), repository revision (git `HEAD`, or null), guidance version and time.

`--replace OLD` is an optional guard: the command refuses (`refused:stale`) when the ticket no longer carries OLD. Labels and provenance are re-read immediately before changing the ticket, and a change since the first read is refused (`concurrent-change`). After the label changes, the final label set is read again: a concurrent contradictory size is `conflict`, an unreadable result `unknown`, a failed removal `partial` (all exit 2, no provenance comment, nothing rolled back). If the labels are right but the comment fails the result is `partial`, and re-running the same command adds only the missing provenance. Repeating the same size and provenance writes nothing (`unchanged`) and returns the stored record; a materially different rationale for the same size records a new assessment as provenance only. A truncated (over 100) or errored label read, or unreadable comment history, writes nothing (`failed:unknown`, exit 2); an unrecognized `complexity:` label is refused for manual inspection. No atomic transaction is claimed. Recording an estimate never claims, unblocks, changes readiness, splits or re-ranks a ticket. `--json` gives a `complexity-estimate` object (`schemaVersion` 2) with `status` (`recorded`, `unchanged`, `partial`, `conflict`, `unknown`, `disabled`, `refused:stale`, `refused:unrecognized`, `failed`, `failed:unknown`), the label changes, final sizes and, on refusal, `code`, `message` and `recovery`. Exit 0 recorded/unchanged; 2 disabled, partial, conflict or unknown; 1 invalid arguments, refusal or API denial.

`estimate N --metric impact --size SIZE --rationale TEXT ...` (#245, [contract](design/impact-estimation.md)) records a designer's judged benefit with exactly the same rules, applied to the labels `impact:XS` through `impact:XXL` (a distinct colour when created) and the marker `<!-- github-triage:impact-estimate v1 {...} -->`. `--metric` defaults to `complexity`, so existing invocations and their output are unchanged. A complexity write never touches `impact:*` labels and an impact write never touches `complexity:*` labels; each parser accepts only its own marker. `--json` gives an `impact-estimate` object (`schemaVersion` 1). It reads `impact.enabled` (default true) and stops with `status: disabled` when it is false. Impact provenance counts only when its author and any editor are users with current write, maintain or admin permission (#215); other markers are ignored, so they never make a retry look already recorded. An identical impact record is `unchanged` only when it is not stale (same guidance version, no description edit after it); otherwise the same command writes a fresh provenance comment, which clears the staleness. Ticket Doctor reports `impact-label-conflict`, `impact-label-invalid` (suggestions from the shared table plus `low`→S and `high`→L, never applied) and `impact-labels-incomplete`, suppressed when `impact.enabled` is false. `config set impact.enabled false` hides impact work without deleting labels or provenance.

## Repository configuration

`github-triage config get KEY`, `config set KEY VALUE`, `config list`, `config convert` and `config help [KEY]` read and change non-secret repository settings in `.github/triage.toml` of the current checkout (doc/design/repository-configuration.md, doc/design/configuration-formats.md). An earlier `.github/triage.json` is still read, and `config set` updates it in place, until `github-triage config convert [--prefer toml|json] [--json]` converts it (#160): convert validates the JSON with the same schema and migrations, creates the TOML file atomically (refused if either file changed meanwhile), reads it back and compares every setting, and only then removes the JSON file, after checking it is unchanged. The retired `complexity.fieldId` is not carried over (reported as `droppedRetired`). A failure after the TOML write exits 1 with code `partial-conversion`, keeps the JSON, and gives the exact command that finishes or reverses the job. Reads never convert or write, and nothing is committed. Both files present is a `duplicate-config` refusal for every command, never a precedence rule: when they hold the same settings `config convert` removes the redundant JSON; when they disagree, `config convert --prefer toml` (remove the JSON) or `config convert --prefer json` (replace the TOML with the JSON settings) decides. `get`, `set`, `list` and `convert` JSON results carry an additive `storage` object (`format`, `path`, `legacy`, and `next`, the convert command while JSON is in use). A repository with neither file gets a new TOML file on its first `config set`. Agents use these commands instead of editing the file: values are validated against the registered keys, older schemas are migrated, and a concurrent edit is refused rather than overwritten. Repository scope is the only scope and is implicit; `--global`, `--machine`, `--system`, `--user` or any `--scope` other than `repository` is refused. Every command except `help` resolves the local checkout and, with `--repo owner/name`, refuses when the checkout is not that repository.

`get` prints the effective value and whether it is `explicit` or the `default`; `list` shows every registered key the same way, so a feature that is on by default is visible. `get` and `list` never modify the file. `set` writes atomically; setting an equal value reports `unchanged`. Changes are not committed — review and commit the file with Git. `config set complexity.enabled false` turns complexity off while keeping existing size labels and recorded estimates. The retired `complexity.fieldId` key (#153) is no longer registered: a file that still contains it loads normally, the key is ignored, `config list` (text, and JSON `retired`) and the briefing's estimation `findings` (`config-retired-key`) name it with the exact correction, and any `config set` (for example `config set complexity.enabled true`, re-setting the current value) rewrites the file without it. `config get complexity.fieldId` is an unknown key. The schema version is unchanged and nothing is migrated automatically. `--json` gives versioned results (`config-get`, `config-set`, `config-list`, `config-help`); refusals in JSON mode are a `config-error` object with `code`, `message` and the exact `recovery` syntax. Exit 0 on success (including unchanged), 1 on any refusal.

Per-agent identity (#70, [contract](design/identity.md)): `config get|set identity.name` and `identity.triage_role` (`implementer` or `designer`) with `--entry KEY` read and write the `[agents.KEY]` table of `agent-inbox.toml` at the Git working-tree root, for example `github-triage config set identity.triage_role implementer --entry codex`. The root is resolved through Git (nested directories and linked worktrees work; no parent, sibling or global fallback); `--repo` must match the checkout's GitHub remote. Without `--entry`, the entry is chosen by one shared resolver (#38, `src/harness.ts`): an explicit supported `--harness claude|codex|ori`, otherwise the harness detected from a registry of verified environment signals (Claude Code: `CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`; Codex: `CODEX_THREAD_ID`, `CODEX_SANDBOX`, `CODEX_MANAGED_BY_NPM`, `CODEX_CI`, not `CODEX_HOME`; Ori: `ORI_SESSION_ID`). A harness selects only its exact entry key (`claude`, `codex`); when the file also has other entries for that harness (for example `codex.review`), when signals of several harnesses are present (an inherited parent marker), when the harness is Ori (one entry per MCP server, `ori.SERVER`, which a shell cannot name) or when nothing is detected, identity keys are refused with `identity-unresolved` and exact `--entry` commands, never a guess. Output reports `selection` (`--entry`, `--harness` or `environment`), the harness and the names of the signals present, never their values. Repository settings keep working and `config list` reports identity as unresolved. For MCP client metadata, the Ori `ori-SERVER` prefix maps to entry `ori.SERVER` before any embedded generic name; no other client name is treated as verified. `get`/`list` never create anything. Setting `identity.triage_role` on a missing file or entry creates it with a generated human-like name, checked against other local names, once; an existing name is never regenerated. Before writing, the file must be Git-ignored: existing ignore rules are reused, otherwise `/agent-inbox.toml` is appended to the repository-local exclude file Git reports; a tracked file is refused (`tracked`) and never untracked, committed or deleted. Writes parse the whole document with smol-toml, keep every other agent, unknown key/table and typed value (large integers, floats, dates), and replace the file atomically, refusing a concurrent edit (`conflict`) or malformed file (`malformed`, reported by line/column only). The serializer does not keep comments, and layout is normalized (for example times gain `.000` fractional seconds). Output only contains the selected entry's registered values and the root-relative path.

## Complexity storage: labels only

Complexity sizes are the repository labels `complexity:XS` through `complexity:XXL` (#151, #152; [contract](design/complexity-estimation.md)). `estimate N` records them; the briefing queue, compact output, MCP reads and Ticket Doctor read them from the collected labels. There is no setup step, field mapping, account-wide field discovery or extra permission: missing size labels or label definitions are not setup errors. The native-field `setup complexity` command, its field discovery and the field-era Ticket Doctor configuration checks were removed (#153); `setup` is now an unknown command. Older field-era `github-triage:complexity-estimate v1` comments are ignored, never read as provenance. The briefing's JSON `estimation` object keeps a deprecated `fieldId` property that is always `null`, so the shape of briefing schema versions 1 and 2 is unchanged; its `status` is now only `available`, `disabled` or `unknown`.
