# Delivery lifecycle: mapping to current triage state

Research report for [#187](https://github.com/trebizondoculpepper/github_triage/issues/187), written against `main` at `55782f5` (2026-11-13). Research only: no code, configuration or live label changes. It maps the lifecycle proposed in the [#186 report](agile-delivery-lifecycle.md) onto what the tool does today, as input to the architecture contract in [#188](https://github.com/trebizondoculpepper/github_triage/issues/188) and the implementation tickets [#189](https://github.com/trebizondoculpepper/github_triage/issues/189)–[#192](https://github.com/trebizondoculpepper/github_triage/issues/192) and [#182](https://github.com/trebizondoculpepper/github_triage/issues/182).

**Stage and effort.** First-stage research under [proportionate research stages](../design/research-stages.md), about 50 minutes, within the one-hour cap. Every code claim cites `file:line` at `55782f5`; the reader should re-check line numbers if `main` has moved. Behaviour was read from source, not exercised against live GitHub, except for one observation noted in [scenario S1](#scenario-fixtures).

**Outcome.** The activity axis (claim) is implemented and well guarded. The delivery axis has no record at all: after `release --as done` the tool forgets who submitted the PR, which PRs are required, and what "delivered" means. Most of the proposed states can be derived from evidence the collectors already fetch; the missing pieces are a durable deliverable record (#189), a responsibility link that survives release (#190), and an integration-target check (#191). Four current behaviours conflict with the proposed lifecycle and need explicit compatibility decisions in #188.

## Inventory of current behaviour

**Labels.** Readiness states are `status:ready`, `status:incomplete`, `status:needs-design`, `status:blocked`, `status:parked` and `status:awaiting-review` (`src/briefing.ts:20-29`). Pickup accepts only `status:ready` or `status:incomplete` (`src/ranking.ts:17`, `src/claims.ts:29`). Prerequisite labels are `status:needs-design`, `question`, `design:decision-needed`, `status:blocked`, `status:parked` (`src/ranking.ts:19-26`). The owner is `agent:NAME` (`src/briefing.ts:49`), addressed attention is `attention:NAME` (`src/claims.ts:25`). Unclaimed work with other than exactly one readiness label is flagged `readiness-inconsistent` (`src/briefing.ts:139-148`). There is no label for any delivery state beyond `status:awaiting-review`.

**Claim.** `planClaim` (`src/claims.ts:437`) refuses closed tickets, truncated labels, other owners, a second active claim, outstanding questions/design, held labels, non-pickable readiness, missing or open native blockers, and an open closing PR (`src/claims.ts:465-652`). One active claim per agent is enforced at `src/claims.ts:481-502`. Linked PRs are read with `closedByPullRequestsReferences(first:10, includeClosedPrs:false)` and truncation is refused, not guessed (`src/claims.ts:375`, `src/claims.ts:556-563`).

**Rework.** `claim --rework` is allowed only when the issue has `status:awaiting-review`, an open linked PR, and the latest release record on the issue is the caller's own `done` with a claim time (`src/claims.ts:580-586`). It removes `status:awaiting-review` on claim (`src/claims.ts:672`). It is also refused while the issue has open native blockers or prerequisite labels (`src/claims.ts:604-643`).

**Release.** `planRelease` (`src/claims.ts:872`) accepts `ready | incomplete | parked | done` (`src/claims.ts:34`). For `done`, the target label is `status:awaiting-review` if the supplied `--pr` reads `OPEN` or any linked closing PR is open, otherwise no readiness label at all (`src/claims.ts:883`, `src/claims.ts:906-907`). A supplied PR is read for its `state` only (`src/claims.ts:851-862`): its repository, its link to the issue, its head SHA and its base branch are not checked. Only one `--pr` or `--change` is accepted (`src/cli.ts:317`, `src/cli.ts:354`). A closed ticket can be released only `--as done` (`src/claims.ts:1043-1052`). The handoff comment carries a hidden marker with a JSON plan `{v, agent, outcome, target, remove, retained, claimedAt}` (`src/claims.ts:186-201`, `src/claims.ts:1071-1080`); the PR URL is in the comment prose only, not in the record. Comment first, labels second; a retry completes exactly the recorded plan or refuses with `RELEASE_DIVERGED` / `RELEASE_PENDING` (`src/claims.ts:979-1035`).

**Needs-human.** `planNeedsHuman` (`src/claims.ts:725`) posts the questions, releases only the caller's claim and adds `attention:DESIGNER`; it is the existing "In progress → Not ready" transition.

**Briefing and roles.** PR findings (`src/briefing.ts:408-516`) classify failed checks, unresolved threads or `CHANGES_REQUESTED`, conflicts, pending checks, a clean `pr-inspect-merge` candidate (requires `verify` success, `MERGEABLE`, a current merge state and no findings; `src/briefing.ts:469-492`), verification needed, and non-current merge state. The implementer role puts `pr-failed-checks`, `pr-review-findings`, `pr-conflicts`, `pr-inspect-merge` in PR FOLLOW-UP (`src/roles.ts:73-78`, `src/roles.ts:172-189`) and everything else in the background "PRS WAITING (inspect; not actionable)" (`src/roles.ts:193-206`, `src/roles.ts:330-331`). "Your PR" is decided by `linkedMine`: the PR or its linked issue carries the viewer's `agent:` label (`src/compact.ts:117-130`).

**Main snapshot scope.** The briefing collector reads only `OPEN` issues and `OPEN` pull requests (`src/github.ts:478-484`), and the issue's reverse link excludes closed PRs (`src/github.ts:280`). Merged PRs and closed issues are invisible to the briefing, Ticket Doctor and pickup.

**`pr N` and `--history`.** `pullRequestStatus` reads one PR's state (reported `MERGED` when merged), head, base branch name, checks, latest review per reviewer with the reviewed commit against the current head, unresolved threads, Codex receipts, review requests, and linked issues with their `agent:` owners (`src/prstatus.ts:101-162`, `src/prstatus.ts:165-170`, `src/prstatus.ts:436`). It does not read the merge commit, whether the base is the repository's default branch, or the PR author. `--history` adds review rounds matched to commits and repeated-cycle candidates (`src/reviewhistory.ts:1-10`, `src/reviewhistory.ts:141`).

**Ticket Doctor.** Scans open tickets only (`src/ticketdoctor.ts:2`). Relevant checks: `ready-with-open-pr` (`src/ticketdoctor.ts:421`), which suggests `release --as done` only once the PR is "finished" (`contributionFinished`: not draft, rollup `SUCCESS`, all threads resolved, no changes requested; `src/ticketdoctor.ts:20-31`); `awaiting-review-without-pr` (`src/ticketdoctor.ts:466-500`), which offers the claimant a choice between "merged → release done" and "closed unmerged → release incomplete" but cannot tell which happened; `multiple-owners`, `leftover-readiness`, stale and unknown agent activity. Plans are suggestions with `runBy` restricted to the claimant (`src/doctorplans.ts:1-10`).

**`who` and `team`.** Ownership is `agent:` labels only; comment prose is surfaced through regex patterns (`done|completed|merged in|fixed in|shipped`, `src/who.ts:23-38`) as inspection hints, never as state. `who` already reports `unowned-open-pr` as a candidate: "it may await review after its contributor released the claim. PR authorship is not identity" (`src/who.ts:159-166`). `team` lists claims and their linked PRs (`src/team.ts:1-9`), so released-but-pending PRs do not appear under any agent.

**Polling.** Event kinds are `attention-requested`, `review-feedback`, `verification-problem`, `pr-follow-up-ready`, `work-became-eligible` (`src/polling.ts:17-23`). PR events are routed to `agent:` labels on the PR or its linked issues (`src/polling.ts:213-225`). There is no merged, closed or delivered event.

**Catch-up (repository briefing mode).** `changes.ts` retains `created`, `merged`, `closed` and `closed-unmerged` events with `stateReason`, `closedAt`, `mergedAt` and native links including cross-repository `closed-by` links (`src/changes.ts:144`, `src/changes.ts:221-268`, `src/changes.ts:276-278`). Releases, npm publication and deployments are explicitly out of scope (`src/changes.ts:14-22`). This is the only current collector that sees merges and closures, but it reports them; it does not evaluate delivery.

**MCP and config.** MCP exposes only read tools: `triage_briefing`, `triage_issue`, `triage_dependencies`, `triage_events` (`src/mcp.ts:440-529`). Repository config has two live keys, `complexity.enabled` and `processGuide` (`src/config.ts:50`, `src/config.ts:58`); there is no integration-target or delivery-policy key.

**Rule prototype.** The rules spike (not runtime) encodes R2 "Get your own pull request merged before taking new work" as `mine ∧ hasOpenPr` (`doc/reports/examples/rules-spike/rules.ts:149-155`), where `mine` means the viewer holds the claim. It has no responsibility or delivery facts.

**Process prose.** [process.md](../process.md) says "One ticket, one PR" (line 18), "Open one PR that closes the issue" (line 30) and "After merging: remove your `agent:` label and check that the issue closed" (line 33). [workflow.md](../design/workflow.md) says done "ends the agent's contribution/claim, not the issue or PR" (line 15) and rework is an explicit reclaim (line 19).

## Conflicts with the proposed lifecycle

**C1. `release --as done` merges two meanings.** It means "contribution done" (claim ended) but its label effect differs by PR state: with an open PR it sets `status:awaiting-review`; with a merged, closed or unknown PR, or a `--change` link, it sets no readiness label at all and leaves the ticket "for inspection" (`src/claims.ts:906-907`, `src/claims.ts:1061-1066`). Nothing distinguishes "merged into the intended branch" from "closed unmerged" or "direct commit". The proposed lifecycle needs a separate submission transition (#190) and a separate, evidence-checked completion (#191); `done` cannot be redefined in place without breaking existing records and retries.

**C2. `status:awaiting-review` is a ticket-level label standing for several delivery states.** It covers Submitted, Changes requested and Accepted alike, and it stays after the PR merges if the issue is not closed (the #186 case, S1). It is in `workflow.readiness`, so `readiness-inconsistent` treats it as the unclaimed ticket's one readiness state (`src/briefing.ts:20-29`, `src/briefing.ts:139-148`). The #186 report recommends deriving delivery state from PR evidence rather than adding labels; keeping `status:awaiting-review` as a coarse "submitted, not pickable" marker is compatible with that, but anything that reads it as "waiting for a reviewer" is wrong once findings exist.

**C3. Rework reclaims the ticket, and responsibility lives on the claim.** After `done`, the agent's `agent:` label is gone, so the briefing calls the agent's own PR a "Review opportunity" or "Open PR" (`src/roles.ts:187-188`, `src/roles.ts:204`), polling routes its feedback to nobody (`src/polling.ts:223-225`), `team` does not list it, and the rule prototype's R2 does not fire (`doc/reports/examples/rules-spike/rules.ts:149-155`). To act, the agent must `claim --rework`, which takes its single active claim. This contradicts the owner constraint that "one active claim does not limit the number of pending PRs" and that "failures request attention, never automatically reclaim" only partly: rework is explicit (good), but fixing any of N pending PRs requires dropping current work first. #188 must decide whether small follow-up on a submitted PR needs a claim at all.

**C4. process.md describes a claim that lasts until merge.** Step 7 ("After merging: remove your `agent:` label", `doc/process.md:33`) and "merge once `verify` passes" (line 30) assume the implementer holds the claim through merge, which the `release --as done` handoff (`doc/design/workflow.md:15`) and the #186 two-axis model both reject. "One ticket, one PR" (`doc/process.md:18`) also conflicts with #188's explicit multi-PR and cross-repository required sets. The prose should be reconciled when #188 merges.

**C5 (minor). `--as parked` vs `status:parked`.** The `parked` release outcome writes `status:incomplete` (pickable), while `status:parked` is a held, non-pickable state (`src/claims.ts:27-33`). The #186 table's "Parked / incomplete" state merges these; #188 should name them distinctly.

## Safeguards to retain

These existing behaviours already satisfy owner constraints and should be preserved by every implementation ticket:

- Missing or truncated evidence refuses (`EVIDENCE_INCOMPLETE`) or reports `unknown`, never "clean" (`src/claims.ts:556-563`, `src/ranking.ts:98-121`, `src/prstatus.ts:412-426`).
- A PR that cannot be read is `UNKNOWN`, never assumed merged (`src/claims.ts:1056-1060`).
- One active claim per agent, no claim stealing, re-check after write (`src/claims.ts:470-502`).
- Rework is explicit and only for the caller's own latest `done` handoff (`src/claims.ts:580-600`); nothing reclaims automatically.
- Comment-first, record-the-plan, idempotent retry with divergence refusal (`src/claims.ts:971-1035`); later label changes by others are never reverted.
- Doctor plans are suggestions; claim mutations are only offered to the claimant (`src/doctorplans.ts:1-10`).
- Green is "inspect / consider merging", never approval (`src/briefing.ts:490`, `src/prstatus.ts:9-10`).
- `who` treats prose and PR authorship as hints, not identity (`src/who.ts:20-22`, `src/who.ts:163`).
- The tool never closes or reopens issues and never merges.
- Catch-up keeps `merged`, `closed` and `closed-unmerged` distinct, with `stateReason` (`src/changes.ts:250-255`).

## Handoff marker trust (#155)

`latestRelease` takes the newest parsable release record "whoever made it" (`src/claims.ts:223-240`), and `releaseRecords` matches on a hash of `[repository, number, agent, claimedAt]` (`src/claims.ts:971`). Anyone able to comment can write a marker, and all agents share one GitHub account, so the comment author does not identify the agent ([#155](https://github.com/trebizondoculpepper/github_triage/issues/155)). Today the worst case is a forged `done` record authorising a rework claim or completing a pending label plan.

If the deliverable record (#189) and responsibility (#190) are stored the same way, a forged record could also redirect responsibility or add/remove a required PR, and a completion evaluator (#191) that trusted the record could report delivery for the wrong set. This raises the stakes of #155 but does not make authenticated identity a prerequisite, provided:

- the record only routes attention and never grants authority (merging, closing, taking a claim);
- completion is evaluated from live PR evidence; the record only names _which_ PRs, and a removal is visible history, not a silent edit;
- readers report conflicting or unparsable records as `unknown`, as `latestRelease` already ignores unparsable ones.

## Schema, config, retry and partial-write implications

- **Release record version.** The marker is `v: 1` (`src/claims.ts:187`). Adding PR URL, head SHA, target or responsibility needs `v: 2` (or a separate record kind), and `latestRelease`/`releaseRecords` accept only `v === 1`, so old binaries would ignore new records. Rework authorisation must decide whether a `v: 2` submit counts as "own done handoff".
- **Read schemas.** `pr-status` and `ticket-doctor` reports are `schemaVersion: 1` (`src/prstatus.ts:102`, `src/ticketdoctor.ts:71`). New delivery fields can be additive; changing the meaning of `status:awaiting-review` findings or `done` facts would need a version bump and MCP schema parity (#192).
- **Config.** No key exists for the intended integration target or delivery policy (`src/config.ts:47-80`). Options: derive from `defaultBranchRef` with no config, or add a registered key; retired-key handling already exists.
- **Retry and partial writes.** Release today has two writes (comment, labels) and recovers by plan. A submit that writes a deliverable record, releases a claim and sets a label has three; the record must be written first (as the release comment is today) so a retry can finish from it. Multi-PR attach across repositories adds per-PR read failures: partial verification must leave the record "unverified", not drop the PR.
- **Pagination.** `closedByPullRequestsReferences(first:10)` (`src/claims.ts:375`, `src/github.ts:280`) and `closingIssuesReferences(first:10)` (`src/prstatus.ts:170`) are refused or flagged when truncated; reading recorded deliverables by URL avoids depending on these lists.
- **Concurrency.** Two agents attaching PRs to the same issue concurrently append separate comments; an append-only record with per-entry markers tolerates this better than one mutable record.

## Migration risks

- **Existing `status:awaiting-review` tickets** have no deliverable record. A new evaluator must report them `unknown` (submitted, set not recorded), not "not delivered", and offer an explicit attach command; inferring the set from closing references would be the "one merged link proves delivery" error #188 forbids.
- **Existing `done` records** (v1) carry no PR URL in the JSON; the URL is only in prose. Parsing prose would contradict the marker-only trust rule; better to treat them as legacy contribution-done.
- **Closed issues with merged PRs** (the normal historical case) would all evaluate `unknown` delivery if checked. #192 must scope drift reports to tickets with a record, or to a recent window, to avoid a flood of false discrepancies.
- **Open awaiting-review tickets whose PR already merged** (S1) will surface as completion candidates; they need an explicit completion step, not an automatic close.
- **Agents mid-rework** hold a claim with `status:awaiting-review` removed; a new submit transition must accept a ticket in that state.
- **process.md readers** (agents following prose) will keep removing `agent:` at merge until C4 is fixed.
- **Downstream consumers** (the Poker Blocks briefing) read `PRS WAITING` and `Review opportunity` text; changing section membership is a presentation change but alters agent behaviour.
