## Summary

The repository formerly known as `block/goose` now lives at **`aaif-goose/goose`** (the GitHub API redirects `block/goose` there; Apache-2.0; latest release v1.59.0, 2026-11-10). Goose ships as a Rust CLI (`goose`) and an Electron Desktop app. The most important architectural change since earlier write-ups: **the old `goosed` HTTP/REST server is gone.** Desktop now spawns `goose serve`, which is an **ACP server over HTTP and WebSocket**, and talks to it over ACP. `goosed` survives only as a legacy binary name the Desktop build scripts delete and as a log-file prefix. There is therefore no separate "goosed REST API" to target; the out-of-process API is ACP plus Goose's `_goose/unstable/*` extension methods.

Integration routes, which must not be confused:

1. **Plain MCP tools** (the baseline in [mcp.md](../../design/mcp.md)). Goose "extensions" are MCP servers: `stdio` and `streamable_http` (SSE removed), configured in `~/.config/goose/config.yaml` (`%APPDATA%\Block\goose\config\config.yaml` on Windows), through `goose configure`, the Desktop extensions UI or deeplinks, or per run with `--with-extension` / `--with-streamable-http-extension`. A `github-triage-mcp` server is called by the model inside the user's session. Nothing wakes or steers it.
2. **ACP controller-owned sessions.** `goose acp` (stdio, spawned by Zed or any ACP client) and `goose serve` (HTTP/WebSocket, `127.0.0.1:3284` by default, `GOOSE_SERVER__SECRET_KEY` required unless `--dangerously-unauthenticated`). `initialize` advertises `loadSession: true`, session `list`/`delete`/`close`, image and embedded-context prompts, and HTTP MCP. Custom methods include `_goose/unstable/session/steer`, `.../session/working`, `.../session/info`, schedules and recipes.
3. **Shared `goose serve` process (new, conditional).** Sessions in a `goose serve` process are held by a shared service, and several ACP connections can attach to the same session (`attach_session`/`detach_session` per connection). A `session/prompt` to a session with a run in flight is rejected with "use `_goose/unstable/session/steer`"; steers are queued into the running loop between model and tool turns. The Roaming guide states this explicitly: a message to a session with a run in flight **in the same process** becomes a steer; a loop in a different process (another CLI) cannot be steered. **This is the only documented route to reach a session another client (Desktop) is showing**, but only when that Desktop is pointed at a `goose serve` whose secret triage also holds. By default Desktop generates a fresh random secret per launch (`crypto.randomBytes(32)`) on a random port, so a third party cannot attach, which is the correct default.
4. **Hooks** (plugin `hooks/hooks.json`, Open Plugins spec): `SessionStart`, `SessionEnd`, `Stop`, `UserPromptSubmit`, `PreToolUse`, `PreToolUseResult`, `PostToolUse`, `PostToolUseFailure`, `BeforeReadFile`, `AfterFileEdit`, `BeforeShellExecution`, `AfterShellExecution`. Only `PreToolUse` and `Stop` can block; the others are observation-only. Unlike Claude Code and Gemini CLI, **no documented hook output adds context to the next turn** (source shows only a `banner` field on some events).
5. **SDK.** `goose-sdk` (the "goose Development Kit", GDK) is a Rust crate, `0.1.0-alpha.13`, with UniFFI bindings for Python (PyPI `goose-sdk` 0.1.0a13) and Kotlin. Its documented surface is provider construction and model completions plus observability hooks. It is a model/agent-building kit, not session delivery. The npm `@aaif/goose-acp-client` is a typed client for Goose's ACP extension methods on top of `@agentclientprotocol/sdk`.

**Scheduled/headless:** `goose run` (`-t`, `-i`, `--recipe`, `--output-format text|json|stream-json`, `--no-session`, `-r/--resume`, `-n`) and `goose schedule add|list|remove|sessions|run-now` (cron, recipes copied to `~/.local/share/goose/scheduled_recipes`; the scheduler runs in `goose serve --enable-scheduler`, which Desktop passes). Each scheduled run creates a **new session**; it is a new process/turn, not delivery to an existing session.

**Recommendation.** Support Goose through the plain MCP server first (a `stdio` extension entry or `--with-extension "github-triage:..."`). Add harness detection on `AGENT=goose` / `AGENT_SESSION_ID` once verified on a Goose host. Do not build a wake adapter for the CLI: there is no host route. A shared-`goose serve` steer/prompt adapter is technically possible but requires the user to run Desktop against an external backend and hand triage the server secret, which grants full ACP control (tools, shell); leave it as a future, opt-in, disposable-session experiment.

## Existing-session boundary

- **Native SDK adapter:** none for delivery. The GDK builds agents and calls models; it does not reach a running Goose session.
- **ACP controller-owned session:** triage spawns `goose acp` or its own `goose serve` and owns the session. Acceptable for disposable sessions and tests.
- **Shared `goose serve`:** the one place Goose differs from Gemini CLI. It is real host behaviour (shared services, per-connection attachment, steer queue), but the secret grants full ACP control, including tools and shell. Triage must never ask users to share it by default.
- **Plain MCP tools:** run inside the user's session, initiated by the model. Correct for reads; cannot initiate anything.
- **Hooks:** cannot inject context, so there is no next-turn notice adapter like the Claude Code or Gemini ones. The smallest useful adapter is a `SessionStart` or `Stop` hook that only writes a local, user-visible notification (for example a desktop notification) saying "triage has N new events since checkpoint", bound to repository, agent name (from `agent-inbox.toml`) and session (`session_id` from the hook payload), batched since the checkpoint, suppressing the agent's own writes, acknowledging only after the notice is shown.

Trust boundary, unchanged: a notice or steer carries no ticket text, acquires no claim and authorizes nothing. The agent runs ordinary triage and the claim rules; ticket content remains untrusted evidence, and all writes stay on the verified-write paths.

## Recommended adapter

1. Ship the read-only MCP server (#25) and document a Goose `stdio` extension example (`config.yaml` entry and `--with-extension "github-triage:<cmd>"`) after an installed-bin smoke on a Goose host.
2. Add a Goose harness detector on `AGENT=goose` plus `AGENT_SESSION_ID`, after verifying which variables reach an MCP server process in a live session (`AGENT`/`GOOSE_TERMINAL` are documented for shell commands; source shows only `AGENT_SESSION_ID` for extensions).
3. No wake adapter for the CLI. Optionally an opt-in notify-only hook as described above.
4. Use `goose acp` (or a private `goose serve`) with `@agentclientprotocol/sdk` and `@aaif/goose-acp-client` only for a disposable-session test harness, gated on owner approval of cost and credentials. Revisit a shared-`goose serve` adapter only if the owner wants Desktop users to opt in to it.

### Disposable-session test plan

On a Goose host with an approved provider account, in a scratch repository with a throwaway `GOOSE_PATH_ROOT` and `GOOSE_DISABLE_KEYRING=1`: record `goose --version`; register the MCP server via `--with-extension` and call one read tool; print environment variable names (not values) from the MCP server process and from a Developer shell command; install a hook plugin that logs only `session_id` on `SessionStart`/`Stop`. Then start a private `goose serve` with a generated secret, open session A from client 1, attach client 2 with `session/load`, and record: whether client 2 receives `session/update` for client 1's turn; whether a `session/prompt` from client 2 to idle session A starts a turn and is visible to client 1; whether a prompt during a run is rejected and `_goose/unstable/session/steer` is applied between turns; and `session/cancel`. Record versions and timings only, no transcripts.

## Risks/unknowns

- Project move (`block` → `aaif-goose`) and very fast releases; pin versions in any test. The npm and crates.io names `goose`, `goose-cli` and `@block/goose` are not the Goose agent.
- `goose serve` replaces `goosed`; any older guidance that targets a goosed REST API is stale.
- `_goose/unstable/*` methods, GDK alpha versions and roaming are explicitly unstable or not shipped.
- Event fan-out to a second attached ACP connection, and wake-by-prompt from a second connection, are inferred from source, not tested.
- The `goose serve` secret is all-or-nothing control; there are no scoped roles.
- Environment variable propagation to MCP servers beyond `AGENT_SESSION_ID` is unverified.
