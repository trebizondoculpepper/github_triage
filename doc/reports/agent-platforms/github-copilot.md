# GitHub Copilot libraries and platform-specific adapters (#227)

Platform follow-up for the parent synthesis #20, written by a Claude Code agent doing desk research on macOS with GitHub Copilot CLI 1.0.85 installed but **not running as the host**. It follows the structure of the Claude Code (#225), Codex (#224) and Gemini CLI (#226) sibling reports so the four can be compared under the same headings. Research and documentation only: no runtime code, hooks, settings, MCP registrations, sessions or GitHub state were changed, no message was queued, no Copilot model turns were run and no credentials were used.

Copilot is not one host. This report treats four surfaces separately: **Copilot CLI** (`copilot`, the terminal agent); **VS Code agent mode** (Copilot Chat in the editor); the **Copilot cloud agent** (formerly "coding agent": works on issues and pull requests on GitHub Actions or a cloud sandbox); and the programmatic surfaces, **`@github/copilot-sdk`** and **ACP** (`copilot --acp`).

## Summary

There are four distinct ways to integrate with Copilot, and they must not be confused:

1. **Plain MCP tools** (the baseline in [mcp.md](../../design/mcp.md)). Every local Copilot surface is an MCP client: the CLI (`copilot mcp add NAME -- CMD`, `~/.copilot/mcp-config.json`, workspace `.mcp.json` or `.github/mcp.json`), VS Code agent mode (stdio and HTTP servers) and the cloud agent (repository and personal MCP configuration). A `github-triage-mcp` stdio server is called by the model inside the session. Nothing wakes or steers the session.
2. **Native SDK control** through the official `@github/copilot-sdk` (MIT, declared generally available, also Python, Go, .NET, Rust and Java). It drives the Copilot runtime over JSON-RPC: by default it spawns the CLI as a child in server mode (`RuntimeConnection.forStdio` or `forTcp`), but `RuntimeConnection.forUri(url)` connects to an **already running** runtime. It has `createSession`, `resumeSession(id)`, `listSessions`, `session.send({ mode: "enqueue" | "immediate", source })`, `session.on("session.idle" | "assistant.message", ...)` and an `onPermissionRequest` handler.
3. **ACP controller-owned sessions** through `copilot --acp` (stdio, or TCP on `127.0.0.1` with `--port`), documented as **public preview**. The ACP client owns the session; `session/new` lets it set the working directory and MCP servers.
4. **Cloud agent tasks.** Not a session on the user's machine at all: a task started from an issue, pull request, the Agents tab, an automation or the CLI's `/delegate` runs on GitHub Actions (59-minute cap) or a cloud sandbox, and its output is a branch and pull request. Triage interacts with it the same way it does with any GitHub actor: through issues, pull requests and comments.

**What is different from the other hosts:** Copilot CLI ships two host-level routes toward an existing session that the others lack in this form. `copilot --connect [sessionId]` and `/remote` ("remote control from GitHub web and mobile, or directly with another CLI") let another client steer a running session, and the SDK's `forUri` connection plus `send({ mode, source: "automation-..." })` is a documented typed message path with provenance. Whether either reaches a session that a user started in an ordinary interactive terminal (rather than one started with `--remote` or in server mode) is **unverified**. VS Code agent mode documents no route for an external process to post a message or start a turn.

**Superseded surfaces (verified):** GitHub App-based Copilot Extensions were sunset on 2025-11-10 in favour of MCP servers; the old `gh copilot` extension is replaced by the standalone Copilot CLI. `@copilot-extensions/preview-sdk` (last modified 2024-10-05) belongs to the retired model and must not be used.

**Recommendation.** Keep the plain MCP server as the Copilot integration for CLI, VS Code and the cloud agent, and add harness detection for Copilot CLI once a session marker is verified. Treat the cloud agent purely as a GitHub actor: no adapter. As a later opt-in spike, test whether an SDK `forUri` client can deliver one fixed notice with `mode: "enqueue"` and `source: "automation-github-triage"` to a session the user explicitly started for remote control, reporting `queued` until a `session.idle`/turn event proves `observed`. Do not use `--acp` or SDK-spawned sessions for notification: they own new sessions and spend AI credits.

## Existing-session boundary

- **Native SDK adapter (spawned runtime):** owns its own process and session. Right for a disposable-session test harness; never for notifying the user's running agent.
- **Native SDK adapter (`forUri` to a running runtime):** the only library route documented to reach a runtime someone else started. It makes triage a JSON-RPC client of that runtime and potentially responsible for permission requests on what it drives. Which interactive sessions expose such a runtime, and with what connection token, is unverified.
- **Host remote control (`--remote`, `/remote`, `--connect`):** user opt-in sharing of a running session. A plausible binding point because the user must enable it per session, but its local wire contract is not documented for third parties.
- **ACP controller-owned session:** the ACP client owns it. Out of scope for notification.
- **Plain MCP tools:** run inside the user's session, initiated by the model. Correct for reads in CLI, VS Code and the cloud agent; cannot initiate anything.
- **Cloud agent:** already reachable through GitHub itself. Triage must not start cloud agent tasks or post `@copilot` comments on its own: that would turn a wake into authorized paid work.

Smallest adapter, if the spike succeeds: opt-in, bound explicitly to repository, agent name (from `agent-inbox.toml`, entry `copilot` once added) and a registered session ID (never a name or ID prefix, which can be ambiguous), with a per-recipient lock, coalescing of all events since the checkpoint into one fixed notice with an opaque batch ID, a rate limit, suppression of the agent's own writes, `source: "automation-github-triage"` for provenance, `mode: "enqueue"` only (never `immediate`), and results reported as `unsupported` / `queued` / `observed` / `failed` / `unknown`. The checkpoint advances only when the agent inspects the batch through ordinary triage.

Trust boundary, unchanged: a notice is fixed text with no ticket content, acquires no claim and authorizes nothing. The agent runs ordinary triage and the claim rules; ticket content remains untrusted evidence, and all writes stay on the verified-write paths. Never use `--allow-all`, `--yolo`, `--allow-all-tools`, `COPILOT_ALLOW_ALL` or the SDK's `approveAll` in any adapter.

## Verification

Done on 2026-11-13, read-only, on macOS from a **Claude Code** session (so this is not a Copilot host):

- `copilot --version` → `GitHub Copilot CLI 1.0.85.` (`/opt/homebrew/bin/copilot`). `gh copilot` was not used; it is the superseded extension and no `gh` extensions are installed.
- `copilot --help` lists commands `app`, `login`, `init`, `update`, `version`, `sessions`, `memories`, `plugin`, `mcp`, `skill`, `instruction`, `lsp`, `completion`, and options including `-p`, `--resume`, `--continue`, `--session-id`, `--connect`, `--acp`, `--remote`, `--remote-export`, `--output-format json`, `--additional-mcp-config`, `--allow-tool`/`--deny-tool`, `--mode interactive|plan|autopilot`, `--extension-sdk-path` (bundled `@github/copilot-sdk`).
- `copilot mcp --help`: `list`, `get`, `add`, `remove`, `enable`, `disable`; sources `~/.copilot/mcp-config.json`, workspace `.mcp.json` or `.github/mcp.json`, plugins. `copilot mcp add --help`: `<name> -- <command>`, `--transport stdio|http|sse`, `--env`, `--header`, `--tools`. `copilot mcp list` was not run because it reads live configuration.
- `copilot sessions --help`: only `import` (from JSONL). `copilot help commands`: `/resume`, `/fork`, `/session`, `/remote`, `/delegate`, `/ide`, `/restart` ("restoring supported live sessions in this process").
- `copilot help config` mentions `hooks` (same schema as `.github/hooks/*.json`), `disableAllHooks`, and a `--server` run mode not listed in `--help`. Hook event names were not enumerated.
- `copilot help environment`: documented variables are all inputs (`COPILOT_HOME`, `COPILOT_MODEL`, `COPILOT_ALLOW_ALL`, `COPILOT_GITHUB_TOKEN`/`GH_TOKEN`/`GITHUB_TOKEN`, `COPILOT_OFFLINE`, `COPILOT_PROVIDER_*`, `COPILOT_OTEL_*`, `COPILOT_CLI_PATH` per the SDK). **No in-session marker** (an equivalent of `CLAUDECODE` or `CODEX_THREAD_ID`) is documented. Environment variable names matching `COPILOT` in this shell: none, as expected. `src/harness.ts` has no Copilot detector, which is correct until a marker is verified.
- Registry metadata via `npm view` for the packages in [Libraries](#libraries).
- **Not run:** any Copilot session, `-p`, SDK or ACP session (would spend AI credits), `--remote`/`--connect`, the cloud agent, VS Code. A Copilot host and an explicit budget are needed for all of these; they are recorded as unverified above.

## Recommended adapter

1. Ship the read-only MCP server (#25) and document Copilot registration examples (`copilot mcp add github-triage -- github-triage-mcp --project /abs/path`, a VS Code `.mcp.json` entry, and the cloud agent repository MCP configuration) after an installed-bin smoke on each surface.
2. Do not build an adapter for the cloud agent. It already consumes GitHub events; triage should only report its pull requests and comments as ordinary evidence.
3. Spike, opt-in only: an SDK `forUri` client that sends one fixed notice with `mode: "enqueue"` to a session the user explicitly shared, observing `session.idle`/turn events to classify `observed`. Adopt only if the disposable-session test proves it reaches a user-owned interactive session without triage answering permission requests.
4. Do not depend on `copilot --acp` or SDK-spawned sessions for notification; use the SDK for a disposable test harness if needed (MIT, no licence blocker, costs AI credits).

### Disposable-session test plan

In a scratch repository with a throwaway `COPILOT_HOME`, `--max-ai-credits` set low and no `--allow-all`: register the MCP server and confirm the three tools load in CLI and VS Code. Start `copilot --session-id <uuid>` interactively, then the same with `--remote`; record which (if any) accept an SDK `RuntimeConnection.forUri` connection and how the URL and token are discovered. Send one fixed notice with `mode: "enqueue"` while idle and while busy; record whether a turn starts, whether a permission prompt reaches the SDK client, and latency. Repeat with the session closed (expect failure, classify `unknown`), a five-event burst (one notice), the agent's own comment (no notice) and two sessions in one repository (no cross-delivery). Dump environment variable **names** inside a Copilot shell tool call to find a harness marker. Record CLI and SDK versions and `gh` request counts; capture no credentials or transcripts.

## Risks/unknowns

- Whether an ordinary interactive CLI session exposes a runtime an SDK can reach, and the auth for `forUri`/`--connect`, is undocumented here; remote control may route through GitHub services rather than locally.
- No documented Copilot session env marker; harness detection cannot be added yet.
- ACP is public preview; the SDK in-process transport is experimental; the SDK is being rebranded as the Microsoft Copilot SDK (package names unchanged per its README).
- CLI auto-updates by default (1.0.85 local vs 1.0.111 registry); capability-check at startup.
- Every model turn spends AI credits; a misbehaving wake loop has direct cost.
- VS Code agent mode details beyond MCP (hooks, queueing, steering) were not researched; VS Code `.vscode/mcp.json` naming was not reconfirmed in the fetched page.
- Cloud agent: 59-minute Actions cap, single branch/PR per task, rulesets can block it; its MCP servers run on GitHub infrastructure, so a stdio triage server needs `gh` auth there.
