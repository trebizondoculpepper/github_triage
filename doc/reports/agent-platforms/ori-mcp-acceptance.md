# Ori MCP acceptance (#255)

This is a real-client acceptance test of the installed `github-triage-mcp` server in Ori, for the per-client matrix of parent #25. It was recorded on 2026-11-13 (UTC). All GitHub calls were read-only: no issue, claim or label was changed by the test runs.

**Verdict: conditional.** Every required check passed in real headless Ori turns, with two conditions. First, **cancellation is not propagated**: interrupting an Ori turn during a tool call leaves the server running the call to completion (Finding 1). Second, **`--project` (or `--repo`) is required**: without it, the default repository comes from the Ori daemon's working directory, not the turn's project (Finding 2). Identity resolution through Ori's `ori-SERVER` client name works without any environment variable, and the triage text output is what the model receives.

## Findings

1. **Ori does not send `notifications/cancelled`.** Interrupting a turn fails it on Ori's side, but the MCP request keeps running in the server until it completes, `gh` children included. For the triage server this wastes collection time (up to the length of one slow read), but it is safe: reads are idempotent and nothing is written. This is Ori-owned behaviour. The server's own cancellation handling (#253: no response sent, no children left) could not be exercised from Ori. Follow-up: an upstream note to Ori, not a triage change.
2. **Ori launches MCP servers in the daemon's working directory, not the turn's.** A server started without `--project` had cwd `/Users/salimfadhley/workspace/github_triage`, the directory the Ori daemon was started from. Confirmed with a turn run inside a disposable checkout whose `origin` is `trebizondoculpepper/agent-inbox`: `run.started` reported that cwd, yet `triage_dependencies` answered for `trebizondoculpepper/github_triage`. Identity was correctly not read (the server treats a missing `--project` as "no local project"). But the **default repository** came from an unrelated checkout. With no tool `repo` and no `--project`, an Ori agent can therefore get another project's briefing. This contradicts `doc/design/mcp.md` ("do not borrow a daemon's arbitrary working directory"). Until it is fixed, always configure `--project` (or `--repo`) for Ori. Follow-up: #271.
3. **Ori keeps MCP server processes alive after a headless turn ends.** Servers from earlier `ori code -p` runs stayed running under the shared `ori code daemon serve` until the daemon reused or dropped them. So a per-turn assumption (one server process per turn) does not hold. A server that polls (`--poll`) would keep polling between turns. This is Ori-owned. No triage change is needed, but it is worth knowing for #32.
4. **Repository-file servers need approval.** `ori mcp test` refuses to start a server declared only in the project's `./.ori/mcp.json` ("only starts after the operator approves it in an attended run"). Headless tests therefore used `ORI_MCP_CONFIG` (or `--config`) pointing at a file outside the repository. The documented per-project setup (`./.ori/mcp.json`) works for attended sessions after approval.
5. **The smoke guide's expectations differ for Ori.** `doc/mcp-host-smoke-test.md` expects three tools at protocol `2025-06-18`, whereas the server now lists four, and Ori negotiates `2025-11-25` through `initialize`. This is the same staleness reported in #253 Finding 2. Follow-up: #272.
6. **Tool search can return no matches.** In two runs with server key `cancel`, `tools/list` succeeded but Ori's `tool-search` returned `No MCP tools match …`, and the model gave up. A later run with the same key worked. The cause is unconfirmed (possibly a race between Ori indexing a newly started server and the first search). It was not reproduced with other keys.

## Reproducible checklist

The checklist uses a scratch directory `$S` with the package installed into a private prefix. It needs no change to `~/.ori/mcp.json` and no `ori mcp add`.

```sh
# 0. Install the exact archive from the commit under test
npm ci && npm run build && npm pack --pack-destination "$S"
npm install --global --prefix "$S/prefix" "$S"/trebizondoculpepper-github-triage-*.tgz
P="$S/prefix/bin"

# 1. Disposable project and per-server identity, using the project's own commands
mkdir -p "$S/proj" && cd "$S/proj" && git init -q
git remote add origin https://github.com/trebizondoculpepper/github_triage.git
"$P/github-triage" config set identity.triage_role implementer --entry ori.reads
"$P/github-triage" config set identity.name acc_ori_reads --entry ori.reads

# 2. Disposable MCP config outside the repository (the server key becomes ori-<key>)
printf '{"mcpServers":{"reads":{"type":"stdio","command":"%s","args":["--project","%s"]}}}\n' \
  "$P/github-triage-mcp" "$S/proj" > "$S/mcp.json"

# 3. Discovery without a model turn
ORI_MCP_CONFIG="$S/mcp.json" ori mcp test reads

# 4. Real headless Ori turn, MCP tools only
ORI_MCP_CONFIG="$S/mcp.json" ORI_HIDDEN_TOOLS=shell,edit,write,read,glob,grep,start_thread \
  ori code -p "Call triage_briefing once with no arguments. Reply with its first line." \
  --model google/gemini-2.5-flash --output jsonl
```

Variants:

- Prompts: `triage_issue` 255 and 999999, `triage_dependencies` 25 with and without `tree`, `triage_briefing` with `repo: "bad"`, with `mode: "briefing"`, and with `agent`.
- Use a **new server key for each variant**. Ori's daemon may reuse a running server process for a key it has already started, so changed `args` may not take effect.
- Missing entry: a key with no `ori.<key>` entry. Missing file: a second Git checkout without `agent-inbox.toml`. Ambiguous identity: add `"--harness","ori"` to `args` with several `ori.*` entries.
- Overrides: add `"--agent","NAME"` or `"--repo",…,"--entry","ori.reads"` to `args`.
- No project: omit `--project` and compare the resolved repository with the daemon's working directory (`lsof -a -p <server pid> -d cwd`).
- Protocol and cancellation: wrap the server in a script that `tee`s stdin and stdout, send SIGINT to `ori code -p` during a `last: 30d` repository briefing, then check for `notifications/cancelled` in the recorded stdin and for leftover `gh api` processes.

Read `tool.started`, `tool.succeeded` and `tool.failed` from the jsonl stream. Record only selection fields and status lines.
