## Summary

Antigravity is Google's proprietary agentic platform spanning **Antigravity CLI (`agy`)**, **Antigravity Desktop App 2.0**, **Antigravity IDE** (the full AI-first editor, plus ACP integration for Zed, JetBrains, Xcode, and Android Studio), and the **Antigravity Python SDK (`google-antigravity`)**. Although Antigravity shares the `~/.gemini/` configuration root family with Gemini CLI (`#226`) and offers `agy plugin import gemini` / `agy plugin import claude`, its runtime architecture, hook protocol, MCP loader, and automation surfaces are distinct from `@google/gemini-cli`.

Five distinct integration surfaces exist:

1. **Plain MCP tools (`mcp_config.json` / `agy mcp add`)**: Any MCP server can expose `github-triage` tools over `stdio` or remote **Streamable HTTP** (`serverUrl` or `url`). Unlike Gemini CLI, Antigravity **does not support legacy HTTP+SSE (`httpUrl`)** directly in CLI/App/IDE (recommending Streamable HTTP or `mcp-remote` over `stdio`), and Antigravity **lazy-loads MCP tool schemas by default** into `<app-data-dir>/mcp/<serverName>/<toolName>.json` (invoked through `call_mcp_tool`) unless `"eager": true` is configured per tool in `mcp_config.json`. Plain MCP remains request/response only: the model must decide to call a tool, and an MCP server cannot wake an idle conversation on its own.
2. **Lifecycle hooks (`hooks.json` in `<workspace>/.agents/hooks.json`, `~/.gemini/config/hooks.json`, or `<plugin-root>/hooks.json`)**: Antigravity runs synchronous command hooks (`SessionStart`, `PreToolUse`, `PostToolUse`, `PreInvocation`, `PostInvocation`, `Stop`) that receive camelCase protojson on `stdin` (`conversationId`, `workspacePaths`, `transcriptPath`, `artifactDirectoryPath`, `modelName`, `lastUserInput`, `hookEventName`, `cwd`) and return JSON on `stdout`. `PreInvocation` and `PostInvocation` can return `injectSteps` (`systemMessage`, `userMessage`, `errorMessage`), giving a clean **context-on-next-turn** channel. However, hooks are strictly synchronous and block the turn loop (default timeout 30s); there is **no `asyncRewake` hook** that waits in the background while a session is idle.
3. **In-session `/schedule` (`schedule` tool) vs. App Sidecars (`sidecar.json` + `agentapi`)**:
   - Inside an active CLI/App conversation, the built-in `schedule` tool (`/schedule`) registers a background one-shot timer (`DurationSeconds`, optional `TimerCondition`) or 5-field cron (`CronExpression`, optional `IsDaemon`). When it fires while the conversation is idle between turns, Antigravity's reactive wakeup system automatically resumes that exact conversation with the scheduled `Prompt`. However, because `schedule` triggers a full model turn on every firing, using an unconditional cron for high-frequency triage polling would waste model turns when no GitHub events exist.
   - On **Antigravity Desktop App 2.0**, background **Sidecars** (`~/.gemini/config/sidecars/<id>/sidecar.json`) run persistent processes or `builtin: "schedule"` cron jobs with an App-injected `agentapi` wrapper on `PATH` supporting both `agentapi new-conversation <prompt>` and **`agentapi send-message <conversation_id> <prompt>`**. An external sidecar script can poll `github-triage` cheaply with zero model tokens and call `agentapi send-message` only when new actionable events arrive. In real-client testing inside `agy` CLI `1.5.8`, `ANTIGRAVITY_AGENTAPI_EXE` points to `/Users/salimfadhley/.local/bin/agy`, and invoking `send-message` directly from a normal CLI shell falls back to standard `agy` flag help rather than acting as a standalone CLI subcommand; `agentapi send-message` is therefore an App-sidecar-hosted route rather than a general CLI command.
4. **Official Python SDK (`google-antigravity` on PyPI, Apache-2.0)**: Bundles a compiled Go `localharness` binary and communicates with it over WebSockets (`LocalConnectionStrategy`). It provides first-class `Agent`, `Conversation`, `CapabilitiesConfig`, `HookRunner`, and `TriggerRunner` (`@trigger`, `every()`, `on_file_change()`, pushing messages into the conversation via `ctx.send()`), plus `save_dir` + `conversation_id` persistence. However, the SDK is **Python-only** (`github-triage` is TypeScript/Node) and **controller-owned**: it spawns and drives its own `localharness` session rather than attaching to an already-running interactive `agy` TUI or Desktop App window.
5. **ACP (`agy acp`) and Headless JSON Streaming (`agy -p`, `agy --input-format stream-json --output-format stream-json`)**: Built into the `agy` binary. `agy acp` speaks Agent Client Protocol v1 over `stdio` (supporting session create/load/resume/list/close, prompt, and mid-turn steering when a prompt is sent during an active turn). `--input-format stream-json --output-format stream-json` keeps a single `agy` process open for multi-turn NDJSON `user` input events and `init` / `step_update` / `result` output events. Both are controller-owned by the spawning client or harness.

## Existing-session boundary

Ticket `#264` and parent `#20` ask what it takes to notify or wake an **existing** Antigravity session without losing conversation state or violating `github-triage`'s trust boundaries:

1. **Plain MCP (`mcp_config.json`) — request/response only**:
   - Registering `github-triage` in `<workspace>/.agents/mcp_config.json` or `~/.gemini/config/mcp_config.json` gives the agent access to triage tools whenever the model chooses to call them.
   - Because Antigravity lazy-loads MCP tool schemas into `<app-data-dir>/mcp/<server>/<tool>.json` by default, small core triage tools should set `"eager": true` in `mcp_config.json` (or via a plugin's `mcp_config.json`) if direct tool declarations (`mcp_github-triage_<tool>`) are preferred over lazy file reads + `call_mcp_tool`.
   - Plain MCP cannot push an asynchronous event into an idle session or inject context before a turn unless the model calls a tool.

2. **Lifecycle hooks (`hooks.json`) — synchronous context-on-next-turn (`PreInvocation`), not idle wake**:
   - Antigravity's `PreInvocation` hook fires before each LLM call in a turn and receives camelCase JSON on `stdin`:
     ```json
     {
       "conversationId": "<uuid>",
       "workspacePaths": ["/abs/path/to/repo"],
       "transcriptPath": "/Users/.../.gemini/antigravity-cli/brain/<uuid>/.system_generated/logs/transcript.jsonl",
       "artifactDirectoryPath": "/Users/.../.gemini/antigravity-cli/brain/<uuid>",
       "modelName": "models/...",
       "lastUserInput": "...",
       "hookEventName": "PreInvocation",
       "cwd": "/abs/path/to/repo"
     }
     ```
   - Returning `injectSteps` on `stdout` injects a system message directly into the conversation before the model runs:
     ```json
     {
       "injectSteps": [
         {
           "systemMessage": {
             "systemMessage": "github-triage: unread notifications or actionable queue updates are waiting; run triage or call the triage MCP tool when ready."
           }
         }
       ]
     }
     ```
   - `PostInvocation` can similarly append `injectSteps` and optionally set `"terminationBehavior": "force_continue"` while a turn is active, and `Stop` can return `{"decision": "continue", "reason": "..."}` to prevent an active turn from going idle.
   - **Boundary**: Hooks are synchronous commands (`default 30s` timeout) that run only at lifecycle transitions of an active turn. Unlike Gemini CLI's experimental `asyncRewake` investigation (`#226`), Antigravity's `hooks.json` specification has **no background idle-wake mode**. Therefore, `PreInvocation` is a **context-on-next-turn** adapter, not an idle-session wake adapter.

3. **In-conversation `schedule` tool (`/schedule`) — native idle self-wake, but clock-driven**:
   - An agent inside an Antigravity conversation can call `schedule` with `DurationSeconds` or `CronExpression` (e.g. `*/10 * * * *`). When the timer or cron fires while the conversation is idle, Antigravity's reactive wakeup resumes that exact `conversationId` and delivers `Prompt` as a high-priority notification.
   - **Boundary**: The `schedule` tool wakes the model unconditionally when the timer/cron fires; there is no pre-turn shell filter inside `schedule` that suppresses the wake when `github-triage` has zero new events. Using `schedule` for frequent background polling would spend model quota on empty checks, though it is viable for coarse user-requested check-ins (for example, while waiting on CI or a PR review).

4. **Antigravity Desktop App 2.0 Sidecars (`sidecar.json` + `agentapi send-message`) — true external wake on App 2.0**:
   - On Antigravity Desktop App 2.0, `~/.gemini/config/sidecars/<id>/sidecar.json` defines background jobs (`command` or `builtin: "schedule"` with `interval` and `script`) that run alongside a project (`ANTIGRAVITY_PROJECT_ID`, `ANTIGRAVITY_SIDECAR_ID`).
   - Sidecar scripts receive an App-managed `agentapi` executable on `PATH` supporting:
     - `agentapi new-conversation <prompt>` (creates a new conversation in the project).
     - `agentapi send-message <conversation_id> <prompt>` (injects a prompt into an **existing** conversation by ID).
   - **Boundary**: A sidecar script can run a cheap local `github-triage` check on a timer and call `agentapi send-message <conversation_id> "<fixed notice>"` **only** when new actionable notifications exist, waking an idle App conversation with zero wasted model turns. However:
     - Sidecars are documented as **Available on: Antigravity App** (not standalone `agy` CLI).
     - In real-client testing inside `agy` CLI `1.5.8`, `ANTIGRAVITY_AGENTAPI_EXE` points to `/Users/salimfadhley/.local/bin/agy`, and running `agy send-message ...` (or `argv[0]=agentapi send-message ...`) directly from a normal CLI shell prints the standard `agy` flag help rather than sending a message; binary inspection confirms the App host generates a sidecar wrapper script with `ANTIGRAVITY_SIDECAR_UI_TOKEN`.
     - Targeting the right conversation requires recording the bound `conversationId` (from `ANTIGRAVITY_CONVERSATION_ID` or a `SessionStart` / `PreInvocation` hook) in local workspace state so the sidecar does not message an unrelated conversation. Because `agy --conversation <id>` and `agy -c` can resume a saved conversation in a new process with the same `conversationId`, a session ID is a binding key rather than proof of a single live OS process; any session-bound waiter or sidecar must still hold a per-session lock.

5. **Controller-owned processes (`agy --input-format stream-json`, `agy acp`, `google-antigravity` Python SDK)**:
   - When an external supervisor owns the session (`agy --input-format stream-json --output-format stream-json`, `agy acp` over `stdio`, or Python SDK `Conversation` + `TriggerRunner`), the supervisor can hold the session open indefinitely and send a new user/trigger message into the existing `conversation_id` whenever an external `github-triage` poll detects work.
   - **Boundary**: These routes require starting the session under the controller (or resuming a saved conversation via `--conversation <id>` / `session/resume` when no interactive TUI owns it). They do not attach to an already-running interactive `agy` TUI terminal.

6. **Trust and checkpoint invariants across all routes**:
   - Any hook `systemMessage` or sidecar `agentapi send-message` payload must contain **only a fixed local notice** (for example, that unread triage notifications or queue updates exist and which local `github-triage` command or MCP tool to run).
   - Never interpolate untrusted GitHub issue titles, bodies, comments, PR descriptions, or labels into `injectSteps` (`systemMessage` / `userMessage`) or `agentapi send-message` prompts.
   - Never auto-claim tickets or advance notification checkpoints from a background hook or sidecar wake; checkpoints advance only when the agent explicitly runs normal triage intake.

## Recommended adapter

Antigravity should be supported in three layered tiers that match `github-triage`'s architecture and existing platform reports:

1. **Tier 1 — Shared `stdio` MCP server (`github-triage-mcp`) + Antigravity harness detection (Recommended baseline across CLI, App 2.0, and IDE)**:
   - Reuse the read-only `github-triage-mcp` `stdio` server from [`src/mcp.ts`](../../../src/mcp.ts) and [`doc/design/mcp.md`](../../design/mcp.md) (`triage_briefing`, `triage_issue`, `triage_dependencies`, `triage_events`), registered in `<workspace>/.agents/mcp_config.json` (or `~/.gemini/config/mcp_config.json` / `agy mcp add`):
     ```json
     {
       "mcpServers": {
         "github-triage": {
           "command": "github-triage-mcp",
           "args": ["--project", "/abs/path/to/repo", "--entry", "antigravity"],
           "tools": {
             "triage_briefing": { "eager": true },
             "triage_issue": { "eager": true },
             "triage_dependencies": { "eager": true },
             "triage_events": { "eager": true }
           }
         }
       }
     }
     ```
   - Note that `--entry antigravity` works immediately with `github-triage-mcp` today (`[agents.antigravity]` in `agent-inbox.toml`) without waiting for `src/harness.ts` changes.
   - Mark the four read-only tools `"eager": true` so Antigravity exposes them directly in tool declarations without requiring an extra lazy schema file read (`~/.gemini/antigravity-cli/mcp/github-triage/<tool>.json`) before the first call.
   - Add an `antigravity` detector to [`src/harness.ts`](../../../src/harness.ts) checking `ANTIGRAVITY_CONVERSATION_ID`, `ANTIGRAVITY_APP_DATA_DIR`, or `ANTIGRAVITY_AGENT` (after verifying in a disposable MCP smoke test whether `agy`'s Language Server forwards those variables to `stdio` MCP child processes or only to `run_command` shells, and whether `McpServer` client info identifies Antigravity).

2. **Tier 2 — Opt-in `<workspace>/.agents/hooks.json` `PreInvocation` hook for context-on-next-turn (Safe cross-surface existing-session notice)**:
   - Configure a lightweight local `PreInvocation` command hook in `<workspace>/.agents/hooks.json` (or ship it in an installable Antigravity plugin's `hooks.json`):
     ```json
     {
       "hooks": {
         "PreInvocation": [
           {
             "hooks": [
               {
                 "type": "command",
                 "command": "npx github-triage hook antigravity-pre-invocation",
                 "timeout": 5
               }
             ]
           }
         ]
       }
     }
     ```
   - The hook reads `conversationId` and `workspacePaths` / `cwd` from camelCase JSON on `stdin`, verifies that `cwd` matches a configured `agent-inbox.toml` workspace, checks local/cached triage state (or a bounded read-only delta check), and when actionable notifications exist, writes `{"injectSteps":[{"systemMessage":{"systemMessage":"github-triage: actionable notifications or queue changes are waiting; run github-triage to inspect."}}]}` on `stdout`.
   - When nothing is pending or the workspace is not configured for `github-triage`, the hook exits `0` with `{}` so ordinary turns incur near-zero overhead.

3. **Tier 3 — Optional idle-session wake (In-session `/schedule` for CLI/App waiting loops; App Sidecar `agentapi send-message` for Desktop App 2.0)**:
   - For **CLI and App sessions waiting on a known blocker** (such as CI completion or PR review), document using Antigravity's built-in `schedule` tool (`/schedule`) with a bounded interval and `MaxIterations` so the existing conversation wakes reactively and runs `npm run triage`.
   - For **Antigravity Desktop App 2.0**, optionally evaluate a workspace-scoped sidecar (`sidecar.json` `builtin: "schedule"`) that runs a read-only `github-triage` check and invokes `agentapi send-message <conversation_id> "<fixed notice>"` only when new actionable work arrives and the target `conversation_id` is recorded as opted-in for that workspace.
   - Do **not** depend on `google-antigravity` (Python SDK) for `github-triage`'s runtime adapter, because `github-triage` is a TypeScript/Node CLI and the Python SDK only drives its own controller-owned `localharness` sessions.

1. **MCP `stdio` environment & lazy/eager tool loading check**:

2. **`PreInvocation` hook `injectSteps` smoke test**:

3. **Desktop App 2.0 Sidecar `agentapi send-message` boundary test (App-only)**:

## Risks/unknowns

- **MCP subprocess environment inheritance is unverified**: `ANTIGRAVITY_CONVERSATION_ID`, `ANTIGRAVITY_APP_DATA_DIR`, and `ANTIGRAVITY_AGENT` are real-client-verified inside `run_command` tool shells, but `stdio` MCP servers are spawned by the Antigravity Language Server (`ANTIGRAVITY_LS_ADDRESS`). Until verified by Step 1 of the disposable test plan, [`src/harness.ts`](../../../src/harness.ts) detection works reliably for CLI commands (`npm run triage`) run inside `run_command`, while MCP servers may need explicit `env` forwarding or workspace-path binding.
- **No cross-surface external idle-wake hook in CLI**: Because `hooks.json` hooks are synchronous and `agentapi send-message` is an App-sidecar mechanism rather than a standalone CLI command, an idle interactive `agy` CLI TUI cannot be woken by an external OS process unless the conversation itself armed a `schedule` timer/cron or is running under `--input-format stream-json` / `agy acp`.
- **Lazy MCP tool loading can hide schemas until inspected**: If `github-triage` registers MCP tools without `"eager": true`, the agent sees only tool names under `Lazy` and must read `<app-data-dir>/mcp/<server>/<tool>.json` and invoke `call_mcp_tool`, adding an extra step per session.
- **MCP output size / file offloading threshold**: In the Antigravity Python SDK (`CapabilitiesConfig.mcp_max_output_bytes`), MCP outputs larger than `4096` bytes are offloaded to a temporary file on disk by default. Because default `triage_briefing` (~67 KB), `triage_issue` (~72 KB), and `triage_dependencies --tree` (~65 KB) outputs exceed 4 KB (see [`claude-code-mcp-acceptance.md`](claude-code-mcp-acceptance.md)), Step 1 of the disposable test plan should record whether `agy` CLI/App offloads large `github-triage-mcp` responses to disk or returns `structuredContent` inline.
- **Permission prompts on first MCP tool or hook use**: Under Antigravity's default permission presets (`Request Review`, `Default`, `Auto`), unconfigured MCP tools default to `Ask` (`mcp(server/tool)`). Users or workspace `.agents/settings.json` may need `permissions.allow` rules (for example, `mcp(github-triage/*)`) for frictionless read-only triage calls.
- **Shared `~/.gemini/config/` namespace collision**: Antigravity CLI, Antigravity App 2.0, and Antigravity IDE all share `~/.gemini/config/mcp_config.json` and `~/.gemini/config/hooks.json`. Global hooks or MCP entries added there affect every workspace unless scoped to `<workspace>/.agents/mcp_config.json` and `<workspace>/.agents/hooks.json`.
