## Summary

Cline has changed shape since it was a single VS Code extension. Its monorepo (`cline/cline`) now contains the VS Code extension (`apps/vscode`, Marketplace id `saoudrizwan.claude-dev`, 4.1.26), a standalone CLI (`apps/cli`, npm `cline`, 3.0.74), a desktop app, and an SDK (`sdk/packages`: `@cline/sdk`, `@cline/core`, `@cline/agents`, `@cline/llms`, `@cline/shared`, 0.2.0). The extension, the CLI and the SDK share one agent core (`@cline/core`); the extension's `package.json` depends on it directly.

There are five integration routes, and they must not be confused:

1. **Plain MCP tools** (the baseline in [mcp.md](../../design/mcp.md)). Cline is an MCP client in both the extension (MCP settings UI, `cline_mcp_settings.json`, an MCP marketplace) and the CLI (`cline mcp install`, `~/.cline/data/settings/cline_mcp_settings.json`, override `CLINE_MCP_SETTINGS_PATH`). A `github-triage-mcp` server registered by the user is called by the model inside the user's own session. Nothing wakes or steers the session.
2. **Native SDK and hub.** `@cline/core` (`ClineCore`, marked `[experimental]`) can start sessions, `send` a prompt to an **active** session with `delivery: "queue" | "steer"`, `abort`, `stop`, `subscribe` to events, list history and read messages. With `backendMode: "hub"`/`"auto"` it connects to a per-machine **hub daemon** (WebSocket, `127.0.0.1:25463/hub`, token from lock files under `~/.cline/data/locks/hub/`). The hub-spoke docs state that CLI, VS Code and JetBrains clients attach to hub sessions as peers and that "multiple clients [can view and control] the same session". **This is the only platform researched so far whose documented SDK claims queued input and active-turn steering into a session that another client may own.** Whether a user's interactive CLI or VS Code session actually lives in the hub (rather than an in-process local backend) is unverified.
3. **VS Code extension API.** The extension exports `ClineAPI` (`startNewTask`, `sendMessage`, `pressPrimaryButton`, `pressSecondaryButton`) to other extensions that declare `extensionDependencies: ["saoudrizwan.claude-dev"]`. `sendMessage` answers the current task's pending "ask" with a user message; there is no event subscription, no session id and no return value.
4. **ACP controller-owned sessions** through `cline --acp`. The CLI is the ACP agent (Zed, JetBrains AI Assistant, Neovim CodeCompanion, Emacs agent-shell). It advertises `loadSession: true` and implements `newSession`, `loadSession`, `prompt`, `cancel`, `setSessionMode`, `unstable_setSessionModel`, `setSessionConfigOption` and `authenticate`. The ACP client owns the process and the session.
5. **Hooks** (`TaskStart`, `TaskResume`, `TaskCancel`, `TaskComplete`, `TaskError`, `PreToolUse`, `PostToolUse`, `UserPromptSubmit`, `PreCompact`, `SessionShutdown`). Hook output carries `contextModification` and `cancel`, so a hook can add context to the next turn. The public hooks page now just points at "SDK Plugins"; the field names come from source.

**gRPC/standalone core:** the extension's `proto/cline/*.proto` services (including `mcp.proto`) and the `hosts/external` "host bridge" are the internal transport between the extension host, its webview and an external IDE host (used by JetBrains). They are not documented as a public API. The public out-of-process surface is now the hub WebSocket via `@cline/core`.

**Recommendation.** Support Cline through the plain MCP server first, as with every other platform. Cline is the strongest candidate so far for a real wake/queued-input adapter, through `@cline/core` in hub mode, but only after a disposable-session test proves that a user-started session is visible on the hub and that `send(..., { delivery: "queue" })` to it starts a turn only when idle. Until then, treat that as unverified and do not build it. Do not use the VS Code `ClineAPI` (it injects into whatever task is current, with no binding). ACP is for controller-owned disposable sessions only.

## Existing-session boundary

- **Native SDK adapter (`@cline/core`, hub mode):** documented to reach sessions owned by other clients. That is exactly the capability that needs the strictest controls: it can inject a prompt into a user's work. Any adapter must bind explicitly to repository, agent name (from `agent-inbox.toml`) and a session id the user opted in, use `delivery: "queue"` only (never `steer`, never `abort`/`stop`), send one batched fixed notice per checkpoint, and acknowledge (advance the checkpoint) only after `send` resolves.
- **VS Code `ClineAPI`:** in-process, no session id, acts on whatever task is current, and `pressPrimaryButton` can approve a pending tool. Unsuitable: there is no safe binding.
- **ACP controller-owned session:** the ACP client owns it; triage would have to be that client. Acceptable only for disposable sessions.
- **Plain MCP tools:** run inside the user's session, initiated by the model. Correct for reads; cannot initiate anything.
- **Smallest adapter today** (without the unverified hub route): **context on next turn** through an opt-in `UserPromptSubmit` hook that adds "triage has N new events since checkpoint" via `contextModification`, with the same bindings, batching, own-write suppression and checkpoint-as-acknowledgment.

Trust boundary, unchanged: a notice carries no ticket text, acquires no claim and authorizes nothing. The agent runs ordinary triage and the claim rules; ticket content remains untrusted evidence, and all writes stay on the verified-write paths. Steering, abort and tool-approval calls are out of scope for any triage adapter.

## Recommended adapter

1. Ship the read-only MCP server (#25) and document a `cline mcp install github-triage -- <cmd>` example and the VS Code MCP settings entry, after an installed-bin smoke on a Cline host.
2. Run the disposable-session test plan below before any further design. Its central question is whether a user's interactive CLI or VS Code session is hub-backed and reachable by `@cline/core` `send`.
3. If (2) passes: write a contract for an opt-in hub adapter over the shared triage events service, using `@cline/core` pinned exactly, `delivery: "queue"` only, explicit repo/agent/session binding, batching, own-write suppression and checkpoint-as-acknowledgment. If (2) fails: fall back to the opt-in `UserPromptSubmit` next-turn notice.
4. Do not use the VS Code `ClineAPI`, the internal gRPC/host-bridge protos, `@cline/cli` 0.0.x, or Roo Code. Use `cline --acp` with `@agentclientprotocol/sdk` only for a disposable-session test harness, gated on owner approval of cost and credentials.

### Disposable-session test plan

On a Cline host with an approved account, in a scratch repository and an isolated `--data-dir` / `CLINE_DATA_DIR` (note `--zen` refuses `--data-dir`): record `cline --version` and `npm ls @cline/core`; register the MCP server and call one read tool; print environment variable names (names only) from a shell tool and from the MCP server process; start an interactive `cline` TUI, then from a separate Node script using `ClineCore.create({ backendMode: "hub" })` call `list` and `get` and confirm whether the TUI session appears. If it does, `send` one fixed notice with `delivery: "queue"` while the session is idle, then while a turn is running, and record whether and when a turn starts. Repeat with the VS Code extension attached. Separately install a `UserPromptSubmit` hook that only emits a fixed `contextModification`, and confirm it appears on the next prompt. Then drive `cline --acp` from an `@agentclientprotocol/sdk` client: `newSession`, `prompt`, `cancel`, `loadSession`. Record versions and timings only, no transcripts, tokens or session ids.

## Risks/unknowns

- `@cline/core` is labelled experimental, at 0.x, and released roughly weekly alongside CLI and extension releases; APIs can change. Pin exact versions in any test.
- The power of the hub is also the risk: any local process with the hub token can send, steer, abort and approve tools in any hub session. An adapter must restrict itself to queued notices and must never read the token from places the user has not opted into.
- Unverified: whether interactive TUI and VS Code sessions run in the hub by default (`auto` "prefers a compatible local hub" for SDK callers; the CLI and extension defaults were not confirmed), and the hub's behaviour across version skew between CLI, extension and SDK.
- The public hooks documentation is a stub pointing to SDK plugins; hook names and output fields come from source and may change.
- No session marker environment variable was found, so a Cline harness detector cannot be added yet.
- JetBrains plugin and the desktop app were not researched separately.
