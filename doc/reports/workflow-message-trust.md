# Workflow message trust: visibility versus authority

Research for #155, a bounded initial spike under [research stages](../design/research-stages.md). It applies the owner decision recorded in [triage efficiency and trust](../design/triage-efficiency-and-trust.md) ("Message visibility is distinct from authority"). No code changes. It feeds the #205 demonstration and the #188/#189 delivery records. Production enforcement is **not** shipped by this report.

**Outcome:** plausible enough to continue. GitHub can prove an author's _current_ effective permission in a way that is useful, but only for the present moment and only for user accounts. Apps and bots, historical permission, and agent identity on a shared account cannot be proved. Every current consumer of comment markers matches on the format and does not check the author. Two of those consumers already decide writes.

Time spent: about one hour of agent time.

Ordinary structured GitHub facts stay facts: labels, PR state, reviews, checks, native dependencies and `closedByPullRequestsReferences`. GitHub already enforces who can change them, so they are outside this boundary. The boundary covers **free text and markers inside bodies and comments**. The proposed #189 delivery records would be another A1/A2-class consumer.

## 2. Threat model under the owner decision

- **Who can comment on a public repository.** Any signed-in GitHub user, unless the issue is locked, the repository limits interactions, or the user is blocked. Any such user can paste a byte-exact claim, release, estimate or Codex marker. A1 and A2 accept it today. The concrete A1 attack: an outsider posts a forged `release` record naming agent X with outcome `done` on an `awaiting-review` ticket. Any agent claiming to be X can then `--rework` the ticket. A forged record naming someone else instead _denies_ X's legitimate rework.
- **Labels.** These need GitHub triage access or higher, so the label consumers inherit GitHub's check. However, triage access is not write access: a triager can set `status:ready` or `attention:*` without being able to push.
- **Shared GitHub account.** All agents here post as one login, so author checks prove only "someone holding this account's token". Agent names in markers remain _reported_. A verified-write boundary does not stop one agent on the account from forging another agent's release record. This is accepted by the owner decision and must be stated, not hidden.
- **Forged bot output.** `isBot` (A5) is a login regex. A user account named like `foo[bot]` cannot be registered, but checking `author.__typename == "Bot"` together with the expected app login is cheap and stricter.
- **Edited comments.** A comment written by a write-capable author can later be edited by that author or by anyone with write or maintain access. The edit changes the marker without a new comment. `createdAt` ordering (A1, A4) then reflects the original time, not when the content changed.
- **Replay.** A genuine record copied into another issue: A2's hash binds the record to the repository, number, agent and claim time. A1's check does not (it requires `claimedAt` to be present, but `:580-586` does not compare it with the current claim). Records copied across repositories are rejected only where the hash includes the repository.
- **Minimised or deleted comments.** A minimised (hidden) comment is still returned and still parsed. A deleted record disappears, so "no record" stays unknown, never "not done" (as A1 already treats incomplete history).
- **Prompt injection.** External text reaches agents through `--issue` intake and briefing excerpts. Classification can stop the _tool_ from treating that text as workflow authority. It cannot make an LLM immune to text that is merely displayed. The design doc already forbids that claim.

## 4. Limits to settle before enforcement ships

1. **Present, not historical.** A record written while the author had write access but read after the author lost it (or the reverse) is judged on present permission only. Recommendation: evaluate at read time, and report "current permission" explicitly. Re-checking on every use is cheap and fails closed when access is revoked.
2. **Insufficient permission to ask.** GitHub's documentation states that the collaborator-permission endpoint requires the caller to have push access. A read-only token, a fork contributor's token or a fine-grained token without metadata scope gets an error or a 404. That result must map to **unknown**, which grants no authority, and never to "external".
3. **API errors, rate limits and pagination.** All of these mean unknown. A partial comment history means the newest record may be missing; the existing `EVIDENCE_INCOMPLETE` handling (`claims.ts:569-575`) is the right pattern.
4. **Cache scope.** Key permission answers by (host, repository, author login, token identity), keep them for one invocation only, and never write them to the [cache research](../design/triage-efficiency-and-trust.md) store as durable facts.
5. **Fork contributors.** PR comments on the base repository are judged by the commenter's base-repository permission. Write access to the fork confers nothing.
6. **Edited records.** Require both the author and, where `lastEditedAt` is set, the `editor` to be verified-write. Otherwise treat the record as unknown. The `userContentEdits` history is visible but does not need to be walked for the demonstration.
7. **Shared account.** Verification proves "someone on a write-capable account". Agent-name checks (A1 and A2 comparing `agent`) stay as consistency checks, reported and not authenticated.
8. **Organisation and custom roles.** The REST `permission` field collapses custom roles to the nearest base level. `role_name` carries the custom name. Treat `write`, `maintain` and `admin` (REST `write`/`admin` plus `role_name`) as write-capable, and `triage`/`read`/`none` as not.

## 5. Recommended per-marker policy

Default: **parse everything, display everything, and grant authority only to verified-write authors (and editors).** Unknown grants no authority.

| Marker or consumer                                                   | Policy                                                                                                                                                                                                                                                                              |
| -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A1 release record → `--rework` authorisation                         | Authority. Count only records whose author (and editor) is verified-write now. Also require `claimedAt` to match the claim being reworked. Unverified records are listed as "unverified record by LOGIN, ignored". Unknown permission → `EVIDENCE_INCOMPLETE`, not "not authorised" |
| A2 release retry record                                              | Authority. Same verification. An unverified record matching the prefix is ignored, and the retry proceeds as if no record existed, still guarded by the existing label-history checks                                                                                               |
| A3 claim marker idempotency                                          | Accept a match only from a verified-write author. Otherwise post the claim comment (harmless duplication)                                                                                                                                                                           |
| A4 estimate provenance                                               | Display with a `verified`/`unverified`/`unknown` author status. Only verified provenance counts as the "previous estimate" in any future rule                                                                                                                                       |
| A5 Codex/CodeRabbit state                                            | Require `__typename == "Bot"` and an allowlisted app login per reviewer service. A text match from any other author is displayed as "claimed review state from LOGIN (untrusted)" and never removes a blocker. It may still _add_ one (fail closed)                                 |
| A6 review requests                                                   | Visibility. An external `@codex review` may be shown, but it should not count as an outstanding request that the agent owes                                                                                                                                                         |
| A7, A8 history and catch-up                                          | Visibility. Add the permission status beside the existing `certainty: "reported"`                                                                                                                                                                                                   |
| A9, A10 labels                                                       | Unchanged. GitHub enforces label permission. Document that triage access suffices to route but not to supply instructions in comments                                                                                                                                               |
| Issue bodies and comments in intake and briefings (external reports) | Listed with title, link and an `external-untriaged` status. Excerpts are marked untrusted data. Never a source of instructions                                                                                                                                                      |
| #189 delivery records                                                | As A1/A2 from day one (section 6)                                                                                                                                                                                                                                                   |

**Per-message authorisation record.** This lets a trusted party say "consider this one message". It is a new marker, `github-triage:authorize-message v1 {json}`, posted by a verified-write author, naming `{repository, subject number, comment node id, comment databaseId, lastEditedAt-or-createdAt observed, purpose, issuedAt}`.

- It authorises _consideration_ of that exact revision. If the target was edited after the observed timestamp, the authorisation is void.
- Revocation is a later `revoke-message` record by any verified-write author, or deletion of the authorising comment.
- An authorisation inside the target message itself is ignored, because it is self-issued. An authorisation by an unverified author is ignored.
- It never conveys trust in the author's other messages. It never bypasses ownership, labels, fresh-state checks or GitHub permissions.
- Limit: an authorisation edited by its own trusted author is re-evaluated as above. There is no signing.

## 6. Inputs to #189 and #205

**#189 delivery records** must record, per record:

- `github actor` (author login and type);
- `editor` and `lastEditedAt`;
- the permission status at read time (`write` / `not-write` / `unknown`, plus the source of that answer);
- the comment `id` and `databaseId`;
- a repository and subject binding inside the payload (not only in a hash), so that replays fail;
- the reported agent, labelled as reported.

Mutation-driving transitions consume only verified records, through the injected trust-decision function that #188 already allows for. Removals of required deliverables follow the same rule.

**#205 demonstration contract.** A pure function `decide(message, permissionLookup, authorizations) → {visibility, authority, reasons}` with injected fixtures and no network access. Test matrix:

| Fixture                                                              | Expected                                                |
| -------------------------------------------------------------------- | ------------------------------------------------------- |
| Write author, unedited release record                                | authority                                               |
| Admin or maintain via a team or custom role (`role_name`)            | authority                                               |
| Triage or read author (MEMBER or COLLABORATOR association)           | visible, no authority                                   |
| External author (association NONE) with an embedded instruction      | listed `external-untriaged`, no authority               |
| Permission lookup returns 403/404/error/rate limit                   | unknown, no authority, no "external" label              |
| Write author, record edited by a read-only editor                    | no authority                                            |
| Author write when written, read now                                  | no authority (current permission only)                  |
| Bot with allowlisted login and type Bot carrying a Codex marker      | review-state evidence accepted                          |
| User account posting a Codex marker                                  | displayed as untrusted, cannot clear a blocker          |
| Explicit authorisation by a write author for comment X at revision R | X considered; another comment by the same author is not |
| Authorisation, then X edited                                         | void                                                    |
| Self-authorisation inside X                                          | ignored                                                 |
| Authorisation by a read-only author                                  | ignored                                                 |
| Two agent names on the same write account                            | both accepted as reported; never "authenticated"        |
| Release record copied from another issue                             | rejected by the repository/subject binding              |

No live mutations. A pass proves classification only.

## 7. Open questions for the owner

One question is posted on #155: whether **triage** access should count as enough to authorise considering a message, given that triage can already set routing labels. The recommendation above is no: write, maintain or admin only. Nothing else needs owner input. Section 4 gives conservative defaults for the remaining items.
