# Delivery lifecycle: claims, responsibility and verified completion

Architecture contract for [#188](https://github.com/trebizondoculpepper/github_triage/issues/188). It reviews the [Agile lifecycle research](../reports/agile-delivery-lifecycle.md) (#186, PR #195) and the [current-model mapping](../reports/delivery-lifecycle-mapping.md) (#187, PR #200), reconciles them with the owner decisions in [triage efficiency and trust](triage-efficiency-and-trust.md#lifecycle-architecture-and-coherent-delivery-188192-182) and the [comment-marker authority contract](workflow.md#focused-handoff-62) (#212, #214), and refines the focused implementation tickets #189–#192 and the ranking ticket #182.

Status: proposed contract. Nothing here is implemented by this document. Commands, record kinds, fields and derived states below are interface contracts for the named tickets, not claims about current behaviour. Until each ticket ships, the existing [claims and handoff](workflow.md) contract and its safeguards remain in force. Merging this document does not close #189–#192 or #182.

## Decisions at a glance

| ID  | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| D1  | Two independent axes, **activity** (the claim) and **delivery** (derived from evidence), plus a **responsibility** relation held at two levels: one ticket-responsible agent per ticket, and a responsible agent per submitted deliverable. Issue **closure** is reported as a third, separate fact. No label per CI or review state.                                                                                                                                                                                                                                                                                          |
| D2  | Delivery is stored as an append-only set of **delivery records** (hidden comment markers, `github-triage:delivery v1`). Records name _which_ deliverables are required and who is responsible; they never state that delivery happened. Delivery is always evaluated from live evidence.                                                                                                                                                                                                                                                                                                                                       |
| D3  | A new `submit` transition replaces `release --as done` for PR-based work. It verifies and records the required deliverables first, then releases only the caller's active claim and sets the coarse `status:awaiting-review` marker. Responsibility survives the release.                                                                                                                                                                                                                                                                                                                                                      |
| D4  | Default completion: every required deliverable is a PR merged into its intended integration target, which defaults to the target repository's GitHub default branch read live. No configuration key is added now.                                                                                                                                                                                                                                                                                                                                                                                                              |
| D5  | A new explicit `complete` operation re-evaluates delivery from fresh evidence and, only when the policy predicate holds, records the evidence and closes the issue as completed. It is refused while any agent holds an active claim on the issue. This deliberately replaces the "the tool never closes issues" rule for this one operation. The tool still never reopens, never merges and never closes on inference.                                                                                                                                                                                                        |
| D6  | Follow-up on a submitted PR the agent is responsible for, whether it submitted it or received it by `deliverables handoff` (answer review threads, fix findings and failing checks on that PR's branch, update a behind branch, re-verify) is responsibility work and needs no claim. New scope, a new or replaced deliverable, or work on the issue beyond the submitted PRs still requires `claim --rework`, which the responsible agent may take (see [Rework authority](#rework-authority)). A rework claim reopens membership, so the ticket is not `delivered` and cannot be completed until the claimant submits again. |
| D7  | `status:awaiting-review` stays as the coarse "submitted, not pickable" marker. It is never read as a delivery state. Delivery state comes only from the evaluator.                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| D8  | Legacy v1 `done` handoffs are **legacy contribution-done** with unknown membership. They are never upgraded by inference; `deliverables attach --legacy` (PRs or commits) and, for non-code tickets, `deliverables attest --legacy` (no claim needed, write-permission author, visible record) are the explicit recoveries.                                                                                                                                                                                                                                                                                                    |
| D9  | Mutation-driving delivery records follow the #212 authority rule from day one: verified current write/maintain/admin `User` author and editor; bots and apps never; unknown grants nothing. Agent names stay reported, not authenticated.                                                                                                                                                                                                                                                                                                                                                                                      |

No new language and no production Datalog engine are introduced.                                                                                                                                                                                                                                                                                                                                       |

Nothing in the merge-based baseline waits for it.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| D12 | "One ticket, one PR" remains the default process rule. A multi-PR required set is the explicit exception for work that cannot be split, cross-repository work being the expected case. Coordinating/local ticket topologies are not mandated.                                                                                                                                                                                                                                                                                                                                                                                  |

## State axes and the responsibility relation

### Activity axis (unchanged)

`unclaimed` or `claimed by A`, stored as the `agent:NAME` label with its claim comment, governed entirely by the existing [claims contract](workflow.md#one-active-contribution). One active claim per agent. A claim means "working on this now".

### Responsibility relation (new, #190)

Responsibility is held at two levels. Both are routing, not a reservation.

- **Ticket responsibility** `ticketResponsible(agent, issue)` holds for exactly one agent, or none, per ticket. It is set by the newest trusted ticket-level record: `submit`, `attach`, `legacy-attach` and `legacy-attest` name their `agent`; a ticket-level `handoff` and a maintainer `reassign` name their `to`. It ends only by an explicit record: a ticket-level `handoff` or `reassign` to another agent, an [effective](#complete-and-concurrent-claims) `complete` record, or a maintainer `reset` (which returns the ticket to ready so another agent can take a claim through the ordinary path). Detaching deliverables, even the last one, never ends it, and neither does a PR closing unmerged. Ticket responsibility is what authorises `attach`, `membership`, `attest` and `claim --rework` without a claim, so the responsible agent can always recover the ticket ([Rework authority](#rework-authority)).
- **Deliverable responsibility** `responsible(agent, issue, deliverable)` holds when the newest trusted record for that deliverable names the agent (the recording agent, or the `to` of a handoff covering it) and the deliverable has not been detached. Detach ends it; `reset` and an effective `complete` end it for every member. It routes follow-up on that PR (D6) and authorises `detach`, `retarget` and per-deliverable `handoff` of that deliverable.

Common rules:

- Responsibility is created, moved or ended only by the explicit records above. It does not expire, and no other agent takes it over automatically; the only way to move it without the responsible agent is the visible [maintainer override](#maintainer-override).
- It never blocks another agent from reviewing, and never grants merge, close or claim authority.
- It directs attention: findings, failures, merge-readiness and cleanup of that deliverable are addressed to the responsible agent in briefings, `who`, `team`, Ticket Doctor and polling.
- An agent may be responsible for any number of tickets and deliverables while holding at most one active claim. Responsibility is not a claim and never counts against the single-active-claim rule; `CLAIM_HELD` refusals concern `agent:` claims only.
- On the shared GitHub account the responsible agent is a reported name. It routes attention; it does not prove which agent or person acts.

### Delivery axis (derived, per deliverable then per ticket)

Per deliverable, recomputed on every read from live evidence bound to the current head:

| Deliverable state   | Evidence                                                                                                                                                                                                                                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `draft`             | PR is open and draft.                                                                                                                                                                                                                                                                                        |
| `waiting`           | Open, not draft; checks pending or review not yet given on the current head; no actionable finding.                                                                                                                                                                                                          |
| `changes-requested` | On the current head: failing required check, `CHANGES_REQUESTED`, unresolved review thread, or merge conflict.                                                                                                                                                                                               |
| `accepted`          | On the current head: required checks green, approval (or the repository's existing review receipt) bound to the current head, no unresolved findings. Mergeability may still need refresh or a branch update; that is an action, not a wait (#182).                                                          |
| `merged`            | Merged, and its merge commit is contained in the live intended target branch of the intended repository, established by a compare of the merge commit against the current target branch head on every read, whether or not the base equals the target. Base equality is a display hint only, never evidence. |
| `merged-off-target` | Merged into another branch, and its merge commit is positively observed not contained in the target (compare `ahead` or `diverged`). Not delivered until merged onward. A containment check that errors or is inconclusive makes the member `unknown`, never off-target.                                     |
| `closed-unmerged`   | Closed without merge. Not delivered.                                                                                                                                                                                                                                                                         |
| `unknown`           | Unreadable, truncated, permission-denied or rate-limited evidence. Never treated as any other state.                                                                                                                                                                                                         |

Per ticket, aggregated over the trusted required set (see [completion policy](#default-completion-policy)):

| Ticket delivery | Meaning                                                                                                                                                                                      |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `none`          | No trusted delivery record and no legacy handoff, or the required set is empty with membership `complete` (for example after the last member was detached) and no attestation applies.       |
| `legacy`        | Only a legacy v1 `done` handoff exists; membership unknown.                                                                                                                                  |
| `submitted`     | Required set recorded (possibly empty) and either membership is `open` (for example during a rework claim) or every member positively observed not yet merged into its target; none unknown. |
| `partial`       | At least one member `merged`, at least one positively observed not merged into its target (open, draft, `closed-unmerged` or `merged-off-target`); none unknown.                             |
| `delivered`     | Membership known and complete, every member `merged` (or a verified direct commit).                                                                                                          |
| `attested`      | A trusted non-code outcome record exists **and applies** (see [attestation applicability](#attestation-applicability)); reported separately from verified delivery.                          |
| `unknown`       | Any member `unknown` (`memberUnknown(t)`), any unverified record that would affect membership, or truncated record history (`recordsUnknown(t)`).                                            |

**Verdict precedence.** The ticket verdict is the first that holds in this order: `unknown` > `delivered` > `attested` > `partial` > `submitted` > `legacy` > `none`. `unknown` takes precedence over every other verdict: when any member or record is unknown, the ticket is never reported `partial`, `submitted`, `delivered` or `attested`, even if other members are positively merged or open. Every negative verdict (`partial`, `submitted`, and any "not merged", "closed unmerged" or "wrong target" explanation) requires positive evidence of that negative state; absence of evidence is `unknown`, never a negative.

### Closure (reported, never inferred)

`open`, `closed-completed`, `closed-not-planned`, `closed-duplicate`, `closed-other`, from the issue `state` and `stateReason`. Closure and delivery are always reported side by side. A closed issue is never evidence of delivery, and an open issue never blocks reporting that delivery holds. Who closed it is reported as the GitHub actor only, never as "a human".

## Invariants

1. One active claim per agent; never stolen; never reacquired automatically (unchanged).
2. Responsibility is created, transferred or ended only by an explicit trusted record. No expiry, no adoption by inactivity, no inference from PR authorship or the GitHub login.
3. Delivery is never stored as a fact. Records list required membership and targets; the evaluator decides from live evidence each time.
4. Missing, truncated, unreadable or unverified evidence yields `unknown`, never `delivered`, `attested`, `partial`, `submitted` or "not delivered". Every negative fact (not merged, closed unmerged, merged off target) is derived only from positive evidence of that state. This includes a recognized delivery record from a trusted or authority-unknown author whose payload is malformed or whose version is unsupported: it sets `recordsUnknown(t)` and is never skipped.
5. One merged PR proves nothing about the others. Issue closure proves nothing about delivery. Green checks are not acceptance and acceptance is not delivery.
6. The tool never merges, never reopens, and closes an issue only through `complete` after the predicate holds on fresh evidence.
7. Membership and target changes are explicit, append-only and visible in history. A removal is a record, never an edit or a deletion.
8. Records drive writes only with authority per #212. Records without authority remain visible as evidence.
9. Repository identities are opaque `owner/name` strings from evidence. No issue-number, repository or named-agent special cases.
10. Read surfaces (briefing, Doctor, `who`, `team`, MCP, polling) are read-only and share one evaluator.

## Delivery evidence model

### Deliverable identity

A deliverable is one of:

- `pr`: `{kind: "pr", repository: "owner/name", number, nodeId}`. The repository is always explicit, including for the ticket's own repository.
- `commit`: `{kind: "commit", repository, oid}` for an accepted direct commit (less preferred, per [workflow](workflow.md#focused-handoff-62)).

Each required entry also records `target` (`{repository, branch}`), `responsible` (reported agent name), and, for PRs, the `headOid` observed at attach time for provenance. The observed head is history, not a freshness proof; acceptance always uses the live current head.

### Facts read per deliverable (targeted reads by recorded identity, never a repository-wide scan)

- PR: `state`, `isDraft`, `merged`, `mergedAt`, `mergeCommit.oid`, `baseRefName`, `baseRepository.nameWithOwner`, `headRefOid`, `mergeable`, `mergeStateStatus`, check rollup on the head, reviews with `commit.oid`, unresolved threads, `closingIssuesReferences` (for link consistency only).
- Commit: reachability from the live target branch head via the compare API (`identical` or `behind` gives `mergedIntoTarget`; `ahead` or `diverged` gives not contained). An API error, unreadable or deleted target branch, missing commit or unexpected status gives `evidenceUnknown`.
- Every merged PR, whether or not its base equals the intended target: the same compare check on `mergeCommit.oid` (for squash or rebase merges, the commit GitHub reports as `mergeCommit`, which is the last resulting commit) against the live target branch head. `identical` or `behind` gives `mergedIntoTarget`; `ahead` or `diverged` gives `mergedOffTarget`; an API error, missing `mergeCommit`, unreadable target branch or an unexpected status gives `evidenceUnknown`. There is no same-base shortcut: a target branch deleted or force-pushed after the merge must be observed, so the recorded or reported base is never containment evidence. Base equality may be shown as a cheap display hint ("merged into base `main`") but never sets `mergedIntoTarget`. Cost: one compare request per merged PR member per read, bounded by the member cap; a single batched GraphQL query may replace the per-member compares where it gives equivalent evidence (containment of the merge commit in the live target head).
- Target default: `defaultBranchRef.name` of the target repository, read live on every read when the record omits an explicit branch. A failed or missing read gives `evidenceUnknown` for every member that depends on it; a default branch observed at attach time, recorded elsewhere, or cached from an earlier read is never substituted.

Recorded metadata (the record's `target`, the attach-time `headOid`, the base observed at attach, and any earlier evaluation) identifies what to read; it is never evidence of the live state.

### Link checks at attach time

- The PR exists and is readable; its base repository equals the recorded target repository.
- Its base branch equals the intended target, or `--target` names it explicitly. A PR targeting a different branch without an explicit target is refused (`TARGET_MISMATCH`), with the explicit-target command in the recovery.
- A missing closing reference to the issue is a warning, not a refusal: cross-repository PRs often cannot close the issue, and membership is what the record says.

## Records: storage, versioning and authority

**Storage.** Hidden comment markers on the issue, the same mechanism as claim and release records, so no new service, credential or daemon is needed. Marker prefix `<!-- github-triage:delivery v1 ` followed by JSON. Each comment carries exactly one record:

```json
{
  "v": 1,
  "op": "submit | attach | legacy-attach | legacy-attest | detach | retarget | handoff | membership | attest | complete | reassign | reset | void",
  "opId": "<stable hash of repository, issue, op, deliverables, agent, claimedAt or issuedAt>",
  "repository": "owner/name",
  "issue": 123,
  "agent": "reported-name",
  "deliverables": [
    {
      "kind": "pr",
      "repository": "owner/name",
      "number": 45,
      "nodeId": "PR_x",
      "target": { "repository": "owner/name", "branch": null },
      "headOid": "abc123"
    }
  ],
  "responsible": "reported-name",
  "membership": "complete | open",
  "to": "reported-name, for handoff and reassign",
  "scope": "ticket | deliverable, for handoff",
  "voids": "comment id, for void",
  "reason": "text, required for every op except submit, attach and complete",
  "plan": { "remove": ["agent:reported-name"], "add": ["status:awaiting-review"] },
  "evaluatedAt": "2026-11-13T00:00:00Z, for complete: when the pre-write evaluation and claim check ran",
  "issuedAt": "2026-11-13T00:00:00Z"
}
```

`branch: null` means "the target repository's default branch, read live". The repository and issue are inside the payload so a copied record fails on another issue (replay binding from the #155 report). `membership: "complete"` asserts the listed set is the whole required set; `open` means more deliverables are expected and the ticket cannot evaluate as delivered until a later record closes membership.

**Folding.** The current required set is the in-order fold of trusted records: `submit`/`attach`/`legacy-attach` add, `legacy-attest` fixes an empty set with membership `complete`, `detach` removes, `retarget` changes a target, `membership` sets the membership statement, `handoff` and `reassign` change responsibility (see [Responsibility relation](#responsibility-relation-new-190)), `reset` ends all responsibility without touching membership, `void` excludes one malformed record from classification, and an [effective](#complete-and-concurrent-claims) `complete` ends responsibility. A `membership` record may be written by `claim --rework` itself (reason `rework claim`), so the fold reflects that scope may change. A comment is a **recognized delivery record** when its body carries the `<!-- github-triage:delivery ` marker prefix. Every recognized record is classified before folding, and no recognized record is ever silently skipped:

| Recognized record                                                                            | Treatment                                                                                                                                                                                                                                                                                                                      |
| -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Trusted author, `v: 1`, payload parses and validates                                         | Folded.                                                                                                                                                                                                                                                                                                                        |
| Trusted author, payload unparsable or fails schema validation                                | Not folded, and `recordsUnknown(t)` becomes true: the record may have changed membership, so the fold is incomplete. Reported as "malformed delivery record by LOGIN"; mutations that depend on the fold refuse `RECORD_MALFORMED`; `complete` and any `delivered` verdict are blocked until a trusted `void` record names it. |
| Trusted author, marker or `v` names a version this reader does not support (`v2`…)           | Not folded, and `recordsUnknown(t)` becomes true, reported as "unsupported delivery record version N by LOGIN"; mutations refuse `RECORD_UNSUPPORTED`. A future version is never guessed at or downgraded.                                                                                                                     |
| Author authority unknown (permission lookup failed, rate-limited, editor history unreadable) | Not folded, and `recordsUnknown(t)` becomes true, regardless of whether the payload parses. Mutations refuse `MARKER_UNVERIFIED` as in #212; read surfaces report `unknown` rather than refusing.                                                                                                                              |
| Author verified **without** authority (no write/maintain/admin, bot or app)                  | Listed as "unverified record by LOGIN, ignored" and excluded. It does not make the fold unknown: an untrusted author could never have changed trusted membership, so excluding it is a decision, not missing evidence. Its parse state is irrelevant.                                                                          |

Authority is decided first, so a malformed or future-version comment from a verified non-writer is simply ignored and cannot be used to block completion. Only comments without the marker prefix are outside the fold. This is invariant 4 applied to records: anything that might have been trusted membership but cannot be read counts as missing evidence. The mapping report's "unparsable records skipped" wording is superseded by this table.

**Authority.** Exactly the [#212 rule](workflow.md#focused-handoff-62): author and any editor must be a `User` with current write, maintain or admin permission from the collaborator-permission endpoint; per-run cache only; bots and apps never. Trust is computed through an injected `TrustDecision` boundary so #205's demonstration result can replace the implementation without changing callers. Until #205's reviewed recommendation lands, production uses the #212 rule, never an anyone-can-comment assumption.

**Versioning.** Delivery records are a new record kind at `v: 1`; release records stay `v: 1` and are unchanged. Readers refuse future versions (`RECORD_UNSUPPORTED`) instead of guessing, and a trusted future-version record makes `recordsUnknown(t)` true (see Folding). Read schemas (`pr-status`, `ticket-doctor`, briefing JSON, MCP) gain additive `delivery`, `responsibility` and `closure` fields within their current `schemaVersion`; no existing field changes meaning.

### Legacy attachment

A v1 `done` handoff creates no responsibility, the ticket is unclaimed, `claim --rework` requires `status:awaiting-review` and an open PR (src/claims.ts:723-730), and pickup excludes `status:awaiting-review` tickets (a no-PR `done` release removes every readiness label, src/claims.ts:1250-1260, so that ticket is not pickable either). Ordinary `attach` is therefore unreachable for the S1 case and for every v1 `done` ticket whose PR has merged or that had no PR, so `attach --legacy` is the explicit recovery path:

- **Author.** The comment author must be a `User` with current write, maintain or admin permission (#215, the #212 rule through `TrustDecision`); unknown permission refuses `MARKER_UNVERIFIED`. The `--agent` name is reported, not authenticated.
- **No claim, no prior record.** It needs neither a claim nor an existing responsibility record, and it never creates a claim, writes an `agent:` label or changes `status:awaiting-review`.
- **Eligibility.** The issue has a trusted v1 `done` release record, no trusted delivery record of any op yet, and `recordsUnknown(t)` is false (otherwise ordinary `attach` applies; refusal `LEGACY_NOT_APPLICABLE`, or the record refusal when the fold is unknown). After any `legacy-attach` or `legacy-attest`, the v1 record is superseded: neither legacy command applies again, even to its original author, and later changes go through ticket responsibility (so after a handoff or reassign only the new responsible agent, or a maintainer override, can act). It refuses `CLAIM_HELD` if any agent other than the caller holds an active `agent:` claim on the issue: that agent owns the work and must attach or release it. A claim held by the caller is allowed but the ordinary `attach` is suggested.
- **Visibility.** It appends one record with `op: "legacy-attach"`, naming the attaching agent, the authenticated GitHub login of the author (from evidence), the cited v1 release record's comment id, and a mandatory `reason`. Briefings, Doctor and history display it as "legacy attachment by AGENT (LOGIN)". Ordinary link checks (`TARGET_MISMATCH`, `EVIDENCE_INCOMPLETE`) apply; merged PRs are accepted. `--commit owner/name@SHA` attaches a commit deliverable, so a v1 `done --change URL` handoff (commit-only work) is recoverable the same way.
- **Responsibility.** The record names the attaching agent as `responsible`, so later `detach`, `retarget` and `handoff` follow the ordinary rules. Membership defaults to `complete` only when stated; `--membership open` keeps the ticket undeliverable until a later record closes it.

### Legacy attestation

A v1 `release --as done` with no PR leaves a non-code ticket with no claim, no readiness or `status:awaiting-review` label, and no responsibility (src/claims.ts:1250-1260). Ordinary `attest` needs a claim or responsibility, pickup needs a pickable label, `claim --rework` needs an open PR, and `attach --legacy` needs a deliverable, so none reaches an attestation. `deliverables N attest --legacy --agent A --reason TEXT [--evidence URL]` is the parallel recovery, with the same rules as [legacy attachment](#legacy-attachment):

- **Author.** A `User` with current write, maintain or admin permission (#215 through `TrustDecision`); unknown permission refuses `MARKER_UNVERIFIED`. `--agent` is reported, not authenticated.
- **No claim, no prior record.** It needs neither a claim nor responsibility, and never creates a claim, writes an `agent:` label or changes any status label.
- **Eligibility.** A trusted v1 `done` release record exists and there is no trusted delivery record of any op, and `recordsUnknown(t)` is false (otherwise refusal `LEGACY_NOT_APPLICABLE`, or the record refusal when the fold is unknown). It refuses `CLAIM_HELD` while any agent other than the caller holds an active `agent:` claim.
- **Applicability.** It is still subject to [attestation applicability](#attestation-applicability). Because eligibility guarantees no delivery record exists, the required set is empty, and the `legacy-attest` record **implicitly declares that empty set complete** (`deliverables: []`, `membership: "complete"`): writing it is the author's statement that the ticket has no code deliverable. `--membership open` is not accepted; an author who expects deliverables uses `attach --legacy` instead. Applicability is re-evaluated on every read as usual, so a later `attach` that adds an unresolved member withdraws `attested` (S34).
- **Visibility.** One record with `op: "legacy-attest"`, naming the agent, the author's authenticated login, the cited v1 release comment id, the mandatory `reason` and optional evidence link. Displayed as "legacy attestation by AGENT (LOGIN)".
- **Responsibility.** The record makes A ticket-responsible, exactly as `submit`, `attach` and `legacy-attach` do (there is no deliverable to carry deliverable responsibility). A therefore satisfies the prerequisite for later `attach`, `membership`, `attest`, ticket `handoff` and `claim --rework` ([Rework authority](#rework-authority)).

**Who may run `complete`.** Any agent with write authority, not only the responsible agent: completion is a factual check, the predicate is the gate, and the S1 case shows waiting for a specific agent can block downstream work indefinitely. The responsible agent is the one the briefing addresses. No agent may run it while any agent, the caller included, holds an active claim on the issue: a claim means work is in progress, and a rework claim means scope may change.

**Merge authority** is unchanged. The tool does not merge and grants nobody new merge powers. #182 may rank "inspect and merge when eligible" for the responsible agent only where existing policy already authorises that agent, with fresh head, protection and ownership checks.

### Rework authority

The existing `claim --rework` prerequisite (src/claims.ts:723-730) accepts only the caller's own v1 `done` handoff. That would strand an agent who received responsibility by `deliverables handoff`: it has no `submit` or `done` record of its own, ordinary pickup excludes `status:awaiting-review` tickets, and D6 requires `claim --rework` for replacement or new scope. #190 therefore widens the prerequisite. `claim N --rework --agent A` is authorised by any one of these trusted records on the issue:

- A's own v1 `done` release record, **only while the issue has no trusted delivery record of any op** (including `legacy-attach` and `legacy-attest`), so that only legacy rules apply. It still needs `status:awaiting-review` and an open PR, so it covers only legacy tickets whose PR is still open; every other legacy ticket recovers through `attach --legacy` or `attest --legacy`. Once any trusted delivery record exists, the v1 record never authorises rework again, even if A wrote it and even if A later writes another v1 `release --as done`: rework authority then comes solely from ticket responsibility, so a v1 releaser who was superseded by `attach --legacy` and a later handoff or reassign has lost it (S65). When the delivery-record trust state is unknown (`recordsUnknown(t)`, or a recognized delivery record whose author's permission cannot be read), `claim --rework` refuses `MARKER_UNVERIFIED`; it never falls back to the v1 path, because an unverified record might be the one that supersedes it.
- A is **ticket-responsible** on the trusted fold: the newest ticket-level record (`submit`, `attach`, `legacy-attach`, `legacy-attest`, ticket `handoff` or `reassign`) names A, and no later `handoff`, `reassign`, `reset` or `complete` has ended it. This holds whether or not any deliverable remains, so an agent that detached the last required PR (for example one closed unmerged) can still rework the ticket. It needs `status:awaiting-review` only if present (it is removed if so) and no open PR. A stale handoff or reassign, superseded by a later one, never authorises.
- Deliverable responsibility alone (from a `--pr` handoff) does not authorise rework; it covers follow-up on that PR only.

Every qualifying record must pass the [authority rule](#records-storage-versioning-and-authority) (#212, #215): author and any editor a `User` with current write, maintain or admin permission, through `TrustDecision`. When the permission of the qualifying record's author is unknown, or `recordsUnknown(t)` is true for the deliverable, `claim --rework` refuses `MARKER_UNVERIFIED`; it never falls back to an older record. Authority is re-evaluated on every attempt, including a retry of a claim that previously failed part-way, so a retry never relies on a v1 authorisation that a delivery record written in between has superseded. All other claim checks stay: single active claim per agent, refusal when another agent holds a claim on the issue, the claim-time freshness checks, and the shared-account caveat that `--agent` is a reported name. Rework requires an open issue. On success, on the delivery-record path, the claim is followed by one `membership open` record (reason `rework claim`), and `status:awaiting-review` is removed; responsibility is unchanged and no member is removed. The open membership makes the verdict `submitted` rather than `delivered`, so read surfaces show that scope may change, and `complete` is refused twice over: by `CLAIM_HELD` while the claim is held, and by the open membership until the claimant runs `submit` again (with replacement or additional `--pr`, or with no `--pr` to resubmit the current set), which closes membership and releases the claim. If the `membership open` write fails after the claim, the claim alone still blocks `complete`; a retry with the same `opId` writes the record once. A legacy v1 rework claim writes no delivery record (there is no fold to reopen); the claim blocks `complete`, and the claimant finishes with `submit`. A claimant who abandons rework releases with `release --as incomplete`; membership stays open and the ticket-responsible agent (still the claimant) closes it with `deliverables membership complete --reason` or attaches the rest.

The same rule governs every other prerequisite that names a single agent. `attach`, `membership`, `attest` and ticket `handoff` accept the caller when it holds the claim or is ticket-responsible; `detach`, `retarget` and `--pr` handoff also accept the deliverable's responsible agent. The original submitter loses these rights once it hands responsibility away. Because ticket responsibility is unique and rework needs it, the single-active-claim rule and `CLAIM_HELD` are unchanged: at most one agent can rework a ticket at a time, and another agent reaches the ticket only after a ticket `handoff`, a `reassign`, or a `reset` returns it to pickup.

### Maintainer override

So that no state is a dead end when the responsible agent is absent, any author who passes the [authority rule](#records-storage-versioning-and-authority) (a `User` with current write, maintain or admin permission, through `TrustDecision`) may run these without a claim or responsibility. Each writes one visible record with a mandatory reason, naming the reported `--agent` and the author's authenticated login, displayed as "override by AGENT (LOGIN)". Unknown permission refuses `MARKER_UNVERIFIED`; `recordsUnknown(t)` refuses with the record refusal except for `void`.

- **`reassign --to B`** makes B ticket-responsible and responsible for every current member. Refused `CLAIM_HELD` while any agent holds an active claim on the issue.
- **`reset --as ready|incomplete`** ends ticket and deliverable responsibility, leaves membership unchanged (the next claimant detaches or attaches with its claim), removes `status:awaiting-review` and adds the readiness label, so ordinary pickup applies. Refused `CLAIM_HELD` while any agent holds an active claim. Refused `RESET_HAS_OPEN_PR` while any open PR links or closes the issue, whether it is a required member or merely linked, naming those PRs: ranking excludes a ticket with an open closing PR and an ordinary `claim` refuses `HAS_OPEN_PR`, so a reset would leave the ticket unpickable with nobody able to `claim --rework`. An open-PR state that cannot be read is unknown, and unknown refuses. The recovery text offers two paths: `reassign --to B`, which keeps responsibility so B can `claim --rework` and either adopt the open PR or replace it (`submit --pr NEW`, then `detach --reason` and close the old one); or close or unlink the open PRs first, then `reset`, after which ordinary pickup applies (S62–S64). It also applies to legacy tickets with no delivery record and no open PR (S54).
- **`membership complete --reason`** closes membership left open by an abandoned rework claim, so a ticket whose responsible agent is absent can still complete. Refused `CLAIM_HELD` while any agent holds an active claim; a maintainer first releases the claim visibly (below), then closes membership, then any agent runs `complete`.
- **`void --comment ID`** excludes one recognized record that is classified malformed, so `recordsUnknown(t)` can clear. It never voids a parsable record (use `detach`, `retarget` or `membership`) or an unsupported-version record (recovery is to upgrade the reader), and refuses `VOID_NOT_APPLICABLE` otherwise.
- **A stuck claim** stays under the [claims contract](workflow.md#one-active-contribution): claims are never stolen by the tool. A maintainer who has confirmed the holder is gone runs `release N --agent HOLDER --as ready|incomplete --note TEXT` stating that it acts for the holder; the release record shows the author's login. The override commands then apply. For a held rework claim the sequence is: visible `release` for the holder, `deliverables membership complete --reason` (or `reassign`/`reset`), then `complete`, which re-evaluates from fresh evidence.

On the shared account every agent can satisfy the authority rule, so the override is distinguished by its explicit op and visible record, not by a separate permission. `complete` is not tied to the submitter: any agent may run it when the fresh evaluation is `delivered` or `attested` and no claim is held on the issue.

## Default completion policy

A ticket is **delivered** when all of the following hold on fresh evidence:

1. The trusted required set is non-empty and its membership is `complete`.
2. Every member is contained in its intended target branch: for a PR, its merge commit (directly when the base is the target, or after an onward merge); for a commit, the commit itself.
3. No member, record or record author is `unknown`, and the record history read was complete.

**Completion prerequisites.** `complete` closes only when, on fresh evidence immediately before the write and again before the close: the verdict is `delivered` or `attested`; no agent holds an active `agent:` claim on the issue (`CLAIM_HELD` otherwise, naming the holder and the recovery: wait for `submit`, or a maintainer's visible release); and records are trusted. Membership `complete` is already part of both verdicts, so a rework claim's `membership open` record also blocks completion after the claim is released, until the claimant or a maintainer closes membership.

`attested` is a separate success outcome for trusted non-code records. It is reported as attested, never as verified delivery, and holds only when the attestation applies (below). When any member or record is unknown the verdict is `unknown` ([precedence](#delivery-axis-derived-per-deliverable-then-per-ticket)) and the explanation names the evidence to re-read. Otherwise everything else is not delivered, with the failing clause and the positively observed state of each outstanding member named in the explanation.

### Attestation applicability

An attestation satisfies delivery only when, on fresh evidence, either the trusted required set is empty and its membership is `complete`, or every required member is itself resolved (`mergedIntoTarget`), with no member or record unknown. An attestation never stands in for an outstanding required deliverable:

- `attest` with any required member not resolved is refused `ATTEST_NOT_APPLICABLE`, naming each outstanding member and the recovery (`deliverables detach --reason` or deliver it first). With membership `open` it is refused the same way, naming the open membership. With an unknown member or `recordsUnknown(t)` it refuses `EVIDENCE_INCOMPLETE` or the record refusal, never `ATTEST_NOT_APPLICABLE` on guessed state.
- Applicability is re-evaluated on every read, not frozen at attest time. An attestation recorded before members were attached does not count while any of those members is outstanding; the ticket evaluates from its required set as usual, and `attested` returns only when the set again satisfies the rule. Release is not part of the default (D11). For this repository the default target is therefore the default branch, `main` at the time of writing, read live.

## Rule and fact interface

Policy is data; collection and enforcement are TypeScript. The convention follows the [rules spike](../reports/examples/rules-spike/rules.ts) and its [report](../reports/rules-language-spike.md): registered facts each carry a TypeScript test, an EDN clause and an English phrase; rules are records `{id, modality, action, when, reason}` that only name facts.

**Facts** (registered; each has an `unknown` companion that the evaluator sets when evidence is missing):

| Fact                                       | Meaning                                                                                                                                                                        |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `required(t, d)`                           | trusted fold lists `d` as required for ticket `t`                                                                                                                              |
| `membershipComplete(t)`                    | the fold's latest membership statement is `complete`                                                                                                                           |
| `mergedIntoTarget(d)`                      | `d` merged and its merge commit (or, for a commit deliverable, the commit) is contained in the live intended target branch, by a compare against the current head on this read |
| `notYetMerged(d)`                          | positively observed open or draft (not merged, not closed)                                                                                                                     |
| `mergedOffTarget(d)`                       | merged, and the merge commit is positively observed not contained in the target (compare `ahead`/`diverged`); an inconclusive check is `evidenceUnknown` instead               |
| `closedUnmerged(d)`                        | positively observed closed without merge                                                                                                                                       |
| `findingOnHead(d)`                         | failing check, changes requested, unresolved thread or conflict, current head                                                                                                  |
| `acceptedOnHead(d)`                        | green and approved on the current head                                                                                                                                         |
| `evidenceUnknown(d)` / `recordsUnknown(t)` | unreadable, missing or unverified evidence (set whenever none of `mergedIntoTarget`, `notYetMerged`, `mergedOffTarget`, `closedUnmerged` is positively established for `d`)    |
| `memberUnknown(t)`                         | some required member of `t` has `evidenceUnknown`                                                                                                                              |
| `responsible(a, d)`                        | trusted deliverable responsibility                                                                                                                                             |
| `ticketResponsible(a, t)`                  | trusted ticket responsibility (unique per ticket)                                                                                                                              |
| `attestRecord(t)`                          | a trusted `attest` record exists                                                                                                                                               |
| `attested(t)`                              | `attestRecord(t)` and the attestation applies (derived, below)                                                                                                                 |
| `issueOpen(t)`, `closedNotPlanned(t)`      | closure facts                                                                                                                                                                  |

**Completion predicates** (Datalog-style, stratified negation; `undelivered` and `partial` hold only from positive `outstanding` evidence and never when `unknown(T)`, and `delivered` additionally requires every member `mergedIntoTarget`, which holds only from a live compare against the current target head on this read (never from base equality or recorded metadata), because any member with no positive state is `evidenceUnknown`; the compiled TypeScript evaluator is normative, the EDN form is the cross-check used by tests):

```text
% Negative member states come only from positive evidence.
outstanding(D)  :- notYetMerged(D).
outstanding(D)  :- mergedOffTarget(D).
outstanding(D)  :- closedUnmerged(D).
memberUnknown(T):- required(T, D), evidenceUnknown(D).
unknown(T)      :- memberUnknown(T).
unknown(T)      :- recordsUnknown(T).
undelivered(T)  :- required(T, D), outstanding(D), not unknown(T).
hasMember(T)    :- required(T, _).
delivered(T)    :- hasMember(T), membershipComplete(T), not unknown(T),
                   not undelivered(T).
attestApplies(T):- membershipComplete(T), not unknown(T), not undelivered(T).
attested(T)     :- attestRecord(T), attestApplies(T).
partial(T)      :- required(T, D), mergedIntoTarget(D), undelivered(T).
```

**Action rules** (records, examples; #182 owns their ordering):

| ID  | Modality   | Action      | When                                                                                           | Reason                                                                         |
| --- | ---------- | ----------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| L1  | `must`     | `follow_up` | `responsible(viewer, d)`, `findingOnHead(d)`                                                   | Fix findings on your own submitted PR before new work.                         |
| L2  | `must`     | `integrate` | `responsible(viewer, d)`, `acceptedOnHead(d)`                                                  | Refresh, update or merge an accepted PR where authorised.                      |
| L3  | `may`      | `complete`  | `delivered(t)`, `issueOpen(t)`                                                                 | Delivery verified; record completion so dependants unblock.                    |
| L4  | `inspect`  | `complete`  | `unknown(t)` (`memberUnknown(t)` or `recordsUnknown(t)`)                                       | Delivery evidence is unknown; re-read it before deciding.                      |
| L5  | `must_not` | `complete`  | `undelivered(t)` (positive `outstanding(d)`, not `unknown(t)`)                                 | A required deliverable is observed open, closed unmerged or merged off target. |

**Boundaries.** `collectDeliveryFacts(issue, records, gh, trust, clock)` returns facts plus coverage and omissions. `evaluateDelivery(facts)` is pure and returns `{delivery, perDeliverable, because, overrides}`. `complete` calls the same evaluator and refuses when it does not return `delivered` or `attested`; an `unknown` verdict refuses with recovery to re-read the named evidence, never to merge or detach. Authority (the `TrustDecision`) is an input to fact collection, never a fact the policy can override.

## Partial failures, retries and concurrency

- **Record first.** `submit` and `complete` post their record before any label or state write, as release does today. The record carries the planned label and close operations, so a retry completes exactly the recorded plan or refuses with `DELIVERY_DIVERGED` when the observed state contradicts it. Changes made by others are never reverted.
- **`opId`** makes retries idempotent: a trusted record with the same `opId` means the record step is done.
- **Per-member read failures** at attach leave that member out of the record and refuse the command with `EVIDENCE_INCOMPLETE`; nothing is recorded as verified on a partial read. At evaluation time they make the member `unknown`.
- **`complete` races.** If the issue is closed by someone else between the record and the close, the close step is skipped and reported. If evaluation changes between the check and the write (a member reverted or detached), the next run reports the discrepancy; the record stores the evidence snapshot (merge commit per member) so the decision is auditable.

### Complete and concurrent claims

Evaluation is live and a claim is a separate write, so `complete` orders its steps to close the window in which a rework claim could slip in:

1. Fresh read of claims (`agent:` labels and claim records), records and member evidence. Refuse `CLAIM_HELD` if any claim is held; refuse unless the verdict is `delivered` or `attested`. The time of this read is the record's `evaluatedAt`.
2. Write the `complete` record.
3. Re-read claims and the record fold. If a claim is now held, or a trusted `membership open` record appears after `evaluatedAt`, stop: do not close, refuse `CLAIM_HELD` (or `DELIVERY_DIVERGED` for the membership change), and report "completion record written, close skipped".
4. Close the issue `completed`, then remove `status:awaiting-review`.

**Effective completion.** A `complete` record is **effective**, and ends ticket and deliverable responsibility, only while the issue is closed and no trusted `membership open` record was created after its `evaluatedAt`. A record left by step 3 is therefore inert: it stays as an audit entry, ends nothing, and the ticket is exactly where the rework claim put it (claimed, membership open, verdict `submitted`). This is the recoverable state: the claimant finishes and resubmits, and a later `complete` writes a new record (new `evaluatedAt`, new `opId`) and closes. `claim --rework` refuses a closed issue, so no claim follows a successful close. A claim that lands in the residual gap between step 3 and the close leaves a closed issue with a claim held; the claimant's `membership open` record makes the completion record inert, responsibility persists, the tool never reopens, and Doctor reports "closed while claimed" so the claimant releases or a human reopens.

- **Concurrent attachments** append separate records and fold in comment order; two writers never edit one shared record.
- **Truncated comment history** makes `recordsUnknown(t)` true.
- Every mutation result enumerates applied, skipped and failed steps; one command is not a GitHub transaction.

**Migration.** No bulk or live migration is performed by any ticket. Legacy tickets are handled one at a time:

1. An open `status:awaiting-review` ticket with only a v1 handoff evaluates `legacy`; Doctor (#192) offers `deliverables N attach --legacy --pr URL --reason TEXT` naming linked closing PRs as **candidates**, never as inferred membership. Legacy candidates and `attest --legacy` suggestions are offered only while the issue has no trusted delivery record and the fold is known; once a `legacy-attach` or `legacy-attest` exists, Doctor addresses the ticket-responsible agent instead and never suggests the v1 author's `claim --rework`.
2. An open ticket whose v1 `done` release had no PR carries no readiness label and is invisible to the `awaiting-review` check; Doctor (#192) still reports it as `legacy` from the release record, and offers `attach --legacy` (with `--commit` for a `--change` handoff) or, for non-code work, `attest --legacy`.
3. An author with current write/maintain/admin permission attaches or attests explicitly through [legacy attachment](#legacy-attachment) or [legacy attestation](#legacy-attestation), with no claim and no prior responsibility (membership `complete` only when they know the set; `attest --legacy` declares the empty set complete); both are refused while another agent holds an active claim. Then `complete` verifies.
4. Closed historical tickets without delivery records are out of Doctor's drift scope by default; Doctor checks only tickets with a delivery record, or an explicitly bounded `--since` window, so history does not flood the report.
5. Any future bulk attachment tool requires its own reviewed plan and a dry run; it is not part of #189–#192.

## Reachability audit

Each review round of this contract found one more state with no legal exit, so this audit checks every non-terminal state against every actor. Actors: **R** the ticket-responsible agent, **O** another agent (no claim, no responsibility), **M** a maintainer using the [override](#maintainer-override). Every path ends at `complete` (issue closed `completed`), an explicit closure outside the tool (`closed-not-planned`, terminal), or `reset` to ready (the ticket returns to ordinary pickup). Wherever M's entry says `reset` it means: only once no open PR links or closes the issue; otherwise `reassign --to B`, or close/unlink the PRs first, then `reset` (`RESET_HAS_OPEN_PR`). ## Release-required completion (separate extension)

Not part of the baseline and not scheduled by this contract. If wanted, a future ticket would add a registered config key (for example `delivery.requireRelease`, default false), a `release` association record naming an artifact (tag, GitHub release or package version) and the deliverables it contains, and a fact `releasedContaining(d)` verified by tag containment. A GitHub release or tag is never equated with npm publication ([npm releases](../npm-releases.md)); publication evidence would need its own collector. Absence of the extension never blocks `delivered`.
