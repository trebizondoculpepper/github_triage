# Briefing mode: repository-wide catch-up

Contract for #163. Product question: “What changed in this repository, and what needs my attention?” This complements the existing next-action/pickup view; it does not replace its eligibility, ranking or authority rules. Use shared GitHub facts and registered presentation policy. No LLM call, polling process, persistent database or new identity service is required.

## CLI and comparison window

Add the planned command `github-triage briefing`, with `--repo`, `--agent`, `--json`, `--limit`, `--max-chars`, `--cache` and `--no-update-check`. It is not installed by this documentation. Select at most one live window source:

```sh
github-triage briefing --repo owner/repository --last 24h
github-triage briefing --repo owner/repository --since 2026-11-13T09:00:00Z
github-triage briefing --repo owner/repository --checkpoint /private/path/check-in.json
```

Default: `--last 24h`. Durations are positive integers followed by `m`, `h` or `d`, meaning fixed elapsed UTC durations, not local calendar days. Reject zero, overflow, invalid timestamps and a future start before collection. `--since` uses the existing ISO-with-time/timezone validation and normalizes UTC. Reject combinations of `--last`, `--since` and `--checkpoint` rather than silently prefer one. Arbitrary historical end times/as-of reconstruction are outside this first slice.

Capture one injected collection-start anchor T0. The requested change window is `[from, T0)`; report the actual collection observation interval separately because GitHub reads are not an atomic snapshot. An event at T0 belongs to the next window. Current-state sections may reflect later evidence observed during collection and are explicitly current observations, not historical state at T0.

A missing checkpoint establishes a baseline at T0, with current attention/activity and an explicit “no previous comparison window” notice; it does not label all existing work newly changed. A valid existing checkpoint supplies `from`. Reuse schema-version-1 repository/through validation and atomic writes. Wrong-repository, malformed, unsupported or future checkpoints are errors, never silently reset. No hidden global “last visit” state: use a dedicated checkpoint path per repository/consumer. Sharing a path deliberately shares that cursor. `--agent` identifies the viewing agent/highlights relevant attention; it never filters the repository-wide change history to only that agent.

## Scope and collection

Version one covers issues, PRs, their collected reviews/checks, current workflow markers, claims and linked-work evidence. It does not audit GitHub releases, npm publication, deployments, file diffs or every transient historical label/state change. Declare this scope in help and structured coverage; a GitHub PR merge is not proof of an npm release. Further sources can be added independently.

Reuse the current open-work snapshot and since-based all-state issue/PR queries. The existing collector currently reduces changed objects to number/title/state/updatedAt; retain the additional normalized evidence needed here rather than repeating full intake for every row. Required change facts include subject kind/identity, creation time, PR merged time, issue closure time/state reason, current title/state, explicit native links, and source coverage. Collected review/thread timestamps and structured operation records can support further qualified events. Keep unknowns explicit.

Preserve the existing `Snapshot.changed` summary for its callers. An optional versioned `changeEvidence` extension can carry the retained changed-subject facts and per-source coverage; old snapshots without that evidence cannot prove detailed history. Version breaking cache/result changes explicitly. Add collector options only for briefing-mode needs; ordinary next-action commands must not acquire unnecessary history queries. Reuse injected GitHub/clock/cancellation boundaries and bounded request/concurrency policies. Output row limits do not truncate source collection silently; any source cap, missing page or unavailable required fact is reported with coverage/omission evidence.

Do not filter subjects solely by `updatedAt <= T0`: a PR merged in the requested window but commented on during collection still has an in-window merge. Qualify each known event by its own timestamp. `updatedAt` alone establishes only an updated item, not which operation occurred, who did it, or that current state began within the window. No complete timeline replay or exactly-once GitHub event guarantee is claimed.

## Five sections and their evidence

| Section            | Contents and qualification                                                                                                                                                                                                                                                                                                          |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Owner attention    | Current explicit unresolved decision/question/access/intervention evidence, with concrete question or recorded reason, what it blocks and next inspection/action. Distinguish a recorded request from a candidate requiring designer triage; a design label or addressed agent request is not automatically an owner-only decision. |
| Completed/disposed | PRs whose `mergedAt` is in-window and issues explicitly completed in-window. Closed-not-planned and closed-unmerged work is a separate disposition, not successful delivery. A previously closed item updated by a comment is not a new completion.                                                                                 |
| Progress           | In-window new issues/PRs, qualified review developments and reported workflow operations, plus updated-item observations when the exact change is unavailable. Use factual templates/title/navigation, not inferred implementation accomplishments.                                                                                 |
| Blockers/risks     | Current failed/cancelled checks, conflicts, unresolved review or dependency evidence and existing repeated-cycle/staleness signals. Distinguish pending/waiting from failure. Call a blocker “new” only with event/delta evidence; otherwise onset is unknown. No new full history analysis on every refresh.                       |
| Current activity   | A short repository-wide summary of recorded claims and open linked PR contributions, grouped/tagged by supported agent identity, with current status and supported next step. Show old ongoing work as ongoing, not newly started. Recorded activity never proves an agent is online.                                               |

Owner attention is always first, including when the question predates the change window. Report `none-evidenced`, `recorded`, `candidate` or `unknown` as appropriate; only say no owner action is identified when supported by collected evidence, never when the relevant source is incomplete. Quote/excerpt the actual question/reason with its link. Agent judgment still determines whether discussion with the owner is necessary. A historical question-shaped comment alone does not reopen an answered question without current workflow evidence.

Within attention, use current actionability/affected active work evidence, then oldest recorded request, then stable subject ID. Within historical sections, sort known event times newest first, then stable subject/event ID; unknown event times follow known times. Current activity uses recorded agent name then subject ID, with unresolved attribution in an explicit group. Do not apply pickup urgency/impact weighting to chronology or change implementation eligibility. Existing explicit oldest/newest pickup controls retain their scope in the normal command; they are not accepted as alternative briefing history policies.

Group a contribution's linked issue/PR evidence once when native links establish the relationship; retain all relevant reasons and links. A PR and a completed issue are different artifact counts, not automatically two delivered features. Incomplete closing-reference evidence cannot establish that work is unlinked. Deduplicate by repository + subject kind/ID + supported event identity, never title. Distinct developments on the same subject remain visible; do not collapse all reviews into one timestamp.

## Agent attribution and readable output

Cover all agents, including unknown attribution. An `agent:NAME` label establishes reported current ownership, not authorship of all earlier work. `origin:NAME` is reported provenance, not proof that the agent performed every change. A structured claim/release/estimate record may report an actor for that operation, but format validation is not authentication; respect the trust limits being discussed in #155. Never map a shared GitHub login to a unique agent or infer activity from a name alone.

Each attribution states its relation/source and whether it is reported, candidate or unknown. Keep a GitHub account actor separate from persistent agent identity. No new cryptographic trust model or external identity lookup is introduced. Useful repository catch-up works with explicit selection and incomplete attribution, so future automatic identity work is not a prerequisite.

Use one deterministic report model for text and JSON. Proposed top-level report: `schemaVersion: 1`, `kind: "repository-briefing"`, repository, viewer context, comparison window/source, observation interval, source coverage, completeness/warnings, summary artifact counts, the five sections, omissions, metrics and checkpoint policy/candidate. Rows carry kind, subject/native related links, event or observation time, factual description, action/evidence/uncertainty and attribution. No raw private configuration or arbitrary command execution appears in results.

Text leads with owner attention status, then a short material-change summary and the five bounded sections. Default `--limit 5` per section, valid 1–100; `--max-chars` defaults 10000, valid 1000–40000. Preserve window, freshness/completeness, scope and omission notices within that budget before expanding row detail. Link to delivered issue/PR detail commands. Distinguish no collected changes from unavailable history. Routine bot chatter and individual commits are not standalone progress rows unless their structured evidence supplies a material finding; do not discard a review finding merely because a bot wrote it.

## Checkpoint, cache and failure behavior

A complete live report advances an explicitly requested checkpoint to T0 only after successful report delivery. Overlap is preferable to skipped updates. Partial collection, cancellation, rendering/output failure or failed required cache write does not advance it. Presentation row omissions may still advance a complete collection, but preserve omitted counts and the previous window so the caller can replay with `--since`; do not claim every item was displayed or read.

Do not promise a checkpoint commit in the JSON printed before that commit. Report the candidate and policy, not `advanced: true`. If the later atomic checkpoint write fails, preserve prior valid data where possible, return exit 1 and sanitized recovery on stderr without appending a second JSON object. A retry reads the actual previous checkpoint; duplicated observations are acceptable, lost history is not. Test these phases independently, without claiming a cross-process/output/filesystem transaction.

`--cache PATH` stores the relevant source evidence atomically, marked with its coverage/window. `briefing --offline --cache PATH` reads that recorded window and observation age, makes no GitHub/update calls and advances no checkpoint. Reject explicit new `--since`/`--last`/`--checkpoint` with offline mode; a cached source cannot verify a newly requested live window. Legacy caches without retained history return an explicit incomplete-history result, not an empty successful catch-up. Wrong-repository or malformed cache is an error. Exit 0 means complete evidence within the declared source scope; 2 means useful but incomplete evidence; 1 means invalid arguments or an operational failure. Completeness never means approval to mutate GitHub.

## MCP follow-up and implementation slices

The shared aggregation service is transport-neutral. A separate adapter slice extends existing `triage_briefing` with optional `mode: "actions" | "briefing"` (default actions) and `last` for briefing mode. Existing mode-omitted inputs/results remain unchanged. Briefing mode accepts one of `since`/`last`, defaults to last 24h and returns the same report with MCP envelope kind `repository-briefing`. Use a strict versioned output union. Keep the three tool names; do not add a second overlapping briefing tool or silently change action-mode output. Reject `last` in action mode rather than ignore it. No checkpoint/cache/file-path/offline arguments or writes are exposed through this read-only MCP mode.

Split delivery into: (1) retained change evidence and shared window selection, (2) deterministic aggregation/rendering, (3) CLI/cache/checkpoint/help/installed-bin behavior, (4) read-only MCP mode integration. The adapter uses the delivered MCP baseline and does not wait for optional automatic identity/client roots or polling. #163 tracks full feature acceptance and is not closed by this docs PR alone. Native dependencies enforce the real slice order after the reviewed contract lands.

Fixtures cover first checkpoint, explicit duration/timezone, boundary timestamps, no changes, mixed all-state work, old closure plus new comment, not-planned disposition, updatedAt-only evidence, in-window merge with later update, incomplete links/history, shared-login attribution, current questions predating the window, waiting versus failed CI, stale review SHA, omitted rows, cache compatibility, invalid/mismatched/future checkpoints and every failure/commit phase. ## Slice 1 implementation notes (#168)

`src/changes.ts` owns window resolution (`resolveWindow`: one injected anchor T0, exclusive `since`/`last`/checkpoint, default `last 24h`, half-open `[from, T0)`, rejection of invalid durations/timestamps and of any start after T0) and the normalized change facts. `collect(..., { changeWindow })` retains them as the optional `Snapshot.changeEvidence` (`schemaVersion: 1`) next to the unchanged `changed` summary; ordinary collection without `changeWindow` is untouched. Each subject records kind, number/URL, current title/state, issue `stateReason`, `createdAt`, `updatedAt`, `closedAt`, PR `mergedAt`, native links (PR closing references; issue closed-by PRs and blocked-by/blocking) with link completeness, window-qualified `created`/`merged`/`closed`/`closed-unmerged` events, an `updatedOnly` marker and an explicit `unknown` list. Snapshots without the extension, or with an unsupported version, are reported as unavailable history by `snapshotChangeEvidence`.

Query cost: change-evidence mode reuses the existing all-state issue and PR queries (50 nodes per page, newest update first) and adds only fields (`closedAt`, issue `closedByPullRequestsReferences(first:20)`), not requests. Each source stops at the first page reaching the window start and is capped at 20 pages (`maxChangePages`), so at most 40 extra requests; a baseline makes none. A cap or missing page before the window start marks that source `complete: false` with an omission and a snapshot warning, never as "nothing changed". Items updated during collection are kept (deduplicated by URL) and qualified by their own event timestamps.

## Slice 2 implementation notes (#169)

`src/catchup.ts` owns the pure aggregation (`catchUp(snapshot, { agent, limit, now })`) and its renderings (`catchUpText`, bounded by `--max-chars` 1000–40000; `catchUpJson`). It reads `Snapshot.changeEvidence` through `snapshotChangeEvidence` for the history sections (completed/disposed, progress) and the current snapshot for the current sections (owner attention, blockers/risks, current activity), each section stating its basis and status (`complete`, `incomplete`, `unavailable` or `baseline`). Owner attention reuses the registered attention, designer-marker and addressed-attention rules, which cover open pull requests as well as issues: `design:decision-needed`, addressed `attention:NAME` and `blocked:credential`/`blocked:testing` are `recorded`; other attention labels are `candidate`; a question-shaped comment only enriches a subject that already has current workflow evidence. Row identity is repository + subject kind/number + event identity (review URL, operation record URL), never title. A merged PR and an issue it natively closes, both completed in the window, form one row with both reasons, while summary counts keep PRs and issues separate. Attribution rows carry relation (`current-owner`, `linked-pr-owner` — an owner label on an open PR grouped into a claimed issue's contribution, sourced to that PR, so the contribution is listed under each agent once — `origin`, `claim-record`, `release-record`, `review-author`, `none`), source, certainty and a separate `githubActor`. No CLI flag, checkpoint write or cache is added here (#170).

## Slice 3 implementation notes (#170)

`src/catchupcli.ts` owns `github-triage briefing` (`cli.ts` only dispatches to it and supplies the checkpoint/cache file boundary). Every argument, including window combinations, duration/timestamp syntax, `--limit` 1–100 and `--max-chars` 1000–40000, is validated before any file or GitHub read; a future `--since`/checkpoint is rejected by `resolveWindow` before collection. The live run reads the checkpoint with the existing schema-version-1 reader, resolves one anchor T0, collects with `changeWindow`, writes `--cache` (the snapshot with its `changeEvidence` window and coverage), delivers the report, and only then atomically writes the checkpoint as `{schemaVersion: 1, repository, through: candidate}` when `catchUp` offered a candidate (complete report or complete baseline). Output, collection or cache-write failure ends the run before that write. A checkpoint write failure leaves stdout as the one delivered report, prints a sanitized recovery line on stderr and exits 1. Malformed, mismatched or unreadable checkpoint and cache files produce a structured refusal (`kind: "repository-briefing-refusal"` with `--json`, otherwise stderr), reporting only the error code, never resetting the file. `--offline --cache PATH` makes no GitHub or update calls, reports the recorded window with an `offline` object (cache time and age) and a text `OFFLINE:` line, and sets the checkpoint candidate to null; legacy caches report history `unavailable` with exit 2. Exit 0 also covers a complete baseline.
