# Bounded read-reuse experiments

Documentation-first contract for #202 (refresh/revalidation) and #203 (storage/isolation), based on merged research #198 and the quota evidence in research PR #296. This authorizes isolated experimental implementation after review, not a production cache, a new default collector, live watcher or daemon. Both experiments can proceed independently against the shared envelope below once this contract merges.

## Why and experimental boundary

Repeated rich reads have material point/payload cost even when the HTTP request count is small. We need to test selective reuse without claiming that timestamps or a PR SHA cover all related evidence. Rank the candidates by evidence and measured benefit, not a presumption that caching must win. A finding that narrower fresh reads are simpler or cheaper is a valid result.

Use TypeScript scripts/tests under doc/reports/examples/cache-experiments/, with injected GitHub, filesystem and clock boundaries. Public fixtures contain synthetic records only. Proposed runners refresh-run.ts and storage-run.ts accept an explicit fixture and produce JSON; they are experimental artifacts, not new installed CLI/MCP flags or user configuration. Default execution uses injected fixtures and temporary storage, never a live project cache. Optional public read probes require explicit --repo and --live, are serial and bounded to ten requests/one page per source per run; stop immediately on a rate-limit response and honor any reset/backoff. No private snapshots in Git, model calls, live mutations or paid resources. Unknown access/cost is not authorization to probe further.

## Shared evidence envelope

Use schemaVersion:1, kind:cache-experiment-snapshot with host, repository identity, authenticatedLogin (known or absent), collectionProfile, observedAt, lastSuccessfulAt, sourceCoverage, manifest and records. The stored context key is a stable digest of canonical host, resolved repository identity, effective authenticated login, schema and profile version. Do not use a token/key fingerprint as a substitute for known authorization context. No shared reuse across unknown/different identities, repository hosts or profiles. A matching login is not proof that permissions remain unchanged: current access is checked before reusing restricted facts. Source coverage records complete/partial/unknown, pagination and selection scope separately for issues, PRs and each required related fact type. A partial page is not an authoritative manifest.

Manifest entries contain stable subject identity, state, updatedAt and PR head OID where applicable, with deterministic ordering. Records contain normalized selected facts and their evidence/source time, not Git objects/diffs, credentials or claims of a transactional repository snapshot. Every reused field identifies its validator and revalidatedAt; TTL reuse is labeled stale/unvalidated, never freshly fetched. A format mismatch is a cache miss/diagnostic, not a migration or a successful empty result. Cache data is JSON, not project settings; TOML configuration preference is unchanged.

## #202 refresh experiment

Compare cold full selected reads, unchanged warm reads, changed-subject hydration and a narrower fresh-only profile against the same synthetic evidence. A complete manifest can identify additions and candidate changes. Disappearance from a complete manifest triggers fresh transfer/deletion/access diagnosis; disappearance from a partial manifest proves nothing. Compare state/updatedAt/head changes to choose full subject re-reads. Overlap watermarks and deduplicate stable identities; a failed/incomplete page does not advance a successful watermark.

Do not assume a subject updatedAt or head OID validates CI, review-thread resolution, mergeability, base/protection, closing/cross references or permissions. Fetch those facts live when the selected action depends on them, even when the manifest is unchanged, or mark the action evidence unknown. Native-edge removals, assignments, reopen/transfer/deletion and review dismissal require explicit missed-change fixtures and must not be promoted to timestamp-covered on historical absence of counterexamples. Reconciliation is explicit: the runner simulates a full selected re-read at least every 30 minutes or on a validator/coverage gap; records older than that interval do not count as validated display evidence. This interval is an experimental control, not a new production setting or an authority TTL.

Compare gh TTL caching and supported REST conditional requests separately from manifest revalidation. HTTP 304 can reuse only the exact matching stored resource/validator/context and known required coverage; gh exit status alone is not the HTTP result. A 304 without a matching payload or with changed access/schema is an error/cache miss requiring a later bounded full read, never empty evidence. No ETag is invented for GraphQL. A failed revalidation is a dated stale fallback only if the consumer explicitly accepts it; no false fresh state. All mutation/merge-boundary verification is live and outside this experiment.

Fixtures cover unchanged timestamp with changed CI/thread resolution/closing link/protection; changed head; issue and comment edits; edge removal; review dismissal; assignment; reopen; transfer/deletion; partial/inconsistent manifests; 304 success/missing payload; API error; cancellation and no watermark advancement. Define the expected fact/action difference before evaluating. Missed changes are counted, not explained away by a speedup.

## #203 storage experiment

Reuse env-paths and existing filelock/atomic-file patterns; default live application storage is not changed. A caller-supplied temporary cache root hosts versioned context directories during tests. Writes go to a same-directory temporary file, are verified and atomically renamed under a short lock. Use injected crash/failure points before/after each step; old good state survives failure. Lock acquisition has a bounded five-second deadline; timeout reports a cache miss and does not break an unknown active lock. Reuse existing stale-lock owner/expiry checks rather than deleting another process's lock merely because it is slow.

Test same-context concurrent writers, readers during rename, different repositories/hosts/logins/profiles, permission loss, corrupt/truncated/future-schema files, future timestamps/clock rollback, interrupted writes, inaccessible directories, missing cache and bounded cleanup. Use a 24-hour maximum retention and at most 256 subject records per experimental context; eviction is explicit and never interpreted as deletion. Prune unseen records only after a complete successful manifest and report eviction/retention omissions. Failed reads/writes do not update lastSuccessfulAt, remove the old snapshot or move checkpoints. No persistent agent identity, settings or repository files are modified.

## Output, evaluation and handoff

Both runners emit schemaVersion:1, kind:cache-experiment, scenario/profile/context IDs, source coverage, fixture baseline and measured counters. Counters include request count, primary point cost (known/unknown separately), bytes, elapsed time, validated hits, TTL-only hits, misses, live hydrations, stale fallbacks, missed changes and diagnostics. Do not report fixture-simulated costs/latencies as live measurements. Live runs record date, gh version, source revision and what was actually queried without tokens/private bodies. Results include a frozen expected-versus-observed table and stop/adopt/narrow recommendation; one fast run is not proof of general reliability.

Acceptance requires deterministic fixture agreement and honest coverage across all listed invalidation/storage failures, plus a comparison that can reject a cache design when savings are absent or complexity dominates. No mandatory percentage speedup, universal timestamp guarantee or production-readiness claim. Produce doc/reports/cache-refresh-experiment.md and doc/reports/cache-storage-experiment.md respectively. Production profile/reuse integration, response-size fixes (#266), degradation (#295) and shared backend (#42) are distinct deliveries. Successful experiments do not activate any of them automatically.
