# Single-operation diagnosis and doctors

All features here are read-only. Share collectors and evidence records; retrieve detail in bounded requests, report missing pages/logs, and keep concise text/JSON. Never rerun CI, request reviews, clear threads, release claims or merge as an implicit diagnosis action. Stable findings carry scope, rule ID, facts, uncertainty, links and supported next commands.

## #59: why is a PR not progressing?

One operation accepts repo and PR, returning current head/fetch window, required check outcomes, bounded failure detail, reviewer findings and later replies, unresolved threads, review status/reviewed SHA, conflicts, linked issues and explicit ownership. Distinguish pending, cancelled, failed, missing and unknown checks. No steps/logs is not a demonstrated code defect. Review receipts may be comments, not formal review objects. A request without reaction differs from a running or completed review. Show simultaneous blockers, not a blanket merge verdict. Green evidence is inspection/merge consideration only. Version the result if compatibility requires it.

## #60: repeated review cycles

An explicit deeper mode extends #59 with review rounds matched to commits, fixes/responses, reopened/resolved findings and recurring themes. Distinguish repeated defects, possible regressions, newly discovered old gaps and duplicate/stale findings. Do not infer causation or abandonment from count alone. Return candidate next actions: targeted fixes, broader invariant/design review, split scope or defer; explain uncertainty and value evidence. Do not run an LLM each background refresh or automatically change scope. A bounded signal feeds designer/owner views, with detail on demand.

Implementation defaults (routine, under this contract): the mode is `pr N --history`; classification uses reviewer + file + normalized finding title only; the inspection threshold is 3 rounds with findings; result shape and bounds are documented in `doc/usage.md`. Wiring the signal into designer briefings and owner catch-up is a follow-up that consumes `signal` without new collection.

## #41 / #61: team and ticket ownership

Team view lists explicit named-agent claims, linked PR state, latest ticket/PR activity, stale/multiple-claim candidates. Ticket lookup answers “who is working on this?” using the same records plus release/done/handoff evidence. Source-link contradictory label/comment history, without treating comment text as an authoritative claim parser. Origin/attention are not ownership. Recorded ownership, recent activity, and live presence are distinct. Without a supported presence source, say online/availability unknown. No presence service is a prerequisite; no shared-login attribution or automatic release. #61 owns focused lookup; #41 owns team aggregation.

## #64: local configuration doctor

Diagnose intended project, selected harness/server entry, supported local configuration parse/identity/name, triage_role, supported role, Git ignored versus already tracked configuration, and missing runtime/gh access as separate checks. No repairs, login, identity creation, role writes, hooks or Git tracking changes. Return actionable in-band results, especially for hosts discarding stderr. Missing/ambiguous detection is explicit. Reuse the confirmed root-level local TOML identity resolver and config boundary in identity.md. Diagnose missing, malformed, ambiguous or unimplemented resolution explicitly; no external service/check-in is required.

Implementation defaults (routine, under this contract): the command is `doctor`; check IDs, statuses (`ok`/`missing`/`invalid`/`access`/`unsupported`/`unknown`) and exit codes are documented in `doc/usage.md`. Doctor reads parse validity, the selected entry, its name and `triage_role` through the shared identity service and resolver; nothing reports them as unsupported. The owner has confirmed the local TOML file and delegated parser selection; completing these checks no longer waits on an owner parser decision. Preserve existing check/exit semantics or explicitly version documented changes. The labels-only decision retires field-specific setup/permission diagnostics; explicit label mutations still report their own denied/unknown operation access.

## #66: Ticket Doctor v1

Scan all open project tickets for missing/conflicting classification/readiness, conflicting urgency/design evidence, multiple claims/owners, leftover claim after handoff, stale agent activity, ready/open-PR mismatch, dependency cycles/drift/missing explanations, and unresolved identity references. Group by ticket, label definite versus candidate versus unknown, and bound output with omitted counts. Prioritize cheap structured checks; do not require perfect coverage of all prose.

For Ticket Doctor, stale-agent default is **24 hours**, configurable, and explicitly separate from the general briefing’s two-day default. Latest linked-PR commits/comments/reviews count. A human assignee is not automatically an agent; apply no agent timeout to humans merely because they share an account. Missing activity is unknown; no automatic reclaim. Classification gaps in an external bug report are triage work, not evidence it is invalid.

## #67: Ticket Doctor v2

Add deterministic correction plans and exact commands to v1, never execution. Examples: stale claim release candidate; ready/open-PR awaiting-review suggestion; merged-PR leftover-claim release; multiple claim dispositions; high/low/remove-both urgency alternatives; missing blocker explanation; cycle path and possible edge removals. Definite mechanics can yield one suggestion; semantic choices remain explicit alternatives. Use only delivered command syntax, with manual/inspection fallback when a mutation is not implemented. No invented auto-repair engine.

Implementation defaults (routine, under this contract): each finding carries `plan` {`facts`, `judgment`, `steps`}, built by `src/doctorplans.ts` from argv builders matching `--help`; step kinds are `command`/`inspect`/`manual` (plain `gh issue edit` for label changes no triage command covers); placeholders are `<UPPER>` tokens; claim commands name only the labelled claimant; unknown findings get inspection steps only. Shape documented in `doc/usage.md`; `schemaVersion` stays 1 (additive). Tests parse every suggested command with the CLI's own argument parsers.

## Acceptance

Fixtures cover current versus stale SHA, cancelled/no-log CI, multiple blockers, meaningful resolved feedback versus bot noise, incomplete history, duplicate issue/PR rows, comment-only ownership, missing presence, malformed configuration, distinct project and host roles, Git-tracked identity files, stale agent versus human assignment, and correction-command parser validity. Show request/output costs. Each ticket is a separate implementation slice; #67 depends on #66 and #60 reuses #59 without requiring unrelated deferred work.

## #39: transferred issue inspection

Use `--include-transferred` to opt into transferred-out work in recommendations; default excludes it from actionable local work. Explicit `--issue N` always diagnoses its transfer when GitHub supplies authoritative transfer/redirect evidence, showing original and destination URLs. Do not silently take destination ownership or infer transfer from a missing/forbidden response. Missing, inaccessible and moved are distinct; if evidence cannot distinguish them, report unavailable/unknown with a next inspection command. Preserve origin repository and destination identity in JSON and cross-repository links. Inject redirects/transfer evidence in tests; no live transfer or automatic issue rewrite. Document bounded fallback reads rather than generic GraphQL failure alone.

## #192: delivery-aware Ticket Doctor (first slice)

Implements the Doctor part of [delivery-lifecycle.md](delivery-lifecycle.md) "#192 diagnostics and reads". For each open ticket carrying a delivery record or a v1 `done` release record, `ticket-doctor` folds the trusted records with the shared fold (which replays handoffs with the shared first-valid-transfer validator) and evaluates delivery from live evidence with the shared collector and evaluator, for at most 20 tickets per run (more are reported as not evaluated and make the scan incomplete). Trusted delivery records, or a trusted legacy v1 handoff, replace the label-only `ready-with-open-pr` and `awaiting-review-without-pr` checks for that ticket; an unknown fold never does.

Findings: `handoff-stale` (S66: sender, recipient, scope, expected and effective predecessor records with links, the effective responsible agent, and a fresh `deliverables N handoff` by that agent as the only recovery); `handoff-unverifiable` (S67, unknown, separate from stale); `delivery-records-unknown`, `delivery-evidence-unknown` (offline or no permission boundary), `delivery-not-evaluated` and `delivery-unknown` (unknown, inspection only); `legacy-delivery` (S1: attach candidates from the release record and closing PRs, named for a decision and never inferred as membership, plus `attest --legacy`); `legacy-release-unverified`; `delivery-partial`; `delivery-member-stalled` (a required PR closed unmerged or merged off target); `delivery-verified-open` (`complete N` for the ticket-responsible agent); `delivery-membership-open` (every recorded member merged, or none required, but membership is open: never completable, with `membership complete` offered to the responsible agent as a judgment); `delivery-empty` (complete, empty set, no applicable attestation); `delivery-diverged-after-complete` (S68 on an open issue: a `complete` record exists but delivery no longer holds; inspection only). `handoff-stale` recovery names the agent responsible after the whole fold, and becomes unknown with inspection only when the final fold is unknown. Legacy candidates are read from the release comment exactly as `release` writes it (`Pull request: URL` or `Change: URL`, a commit URL becoming `--commit owner/name@SHA`) and from closing PRs. A `submitted` ticket whose members are all open or draft is waiting, not a finding. Every plan is a suggestion: nothing is posted, closed, reopened, claimed or reassigned. Tickets with neither record kind are reported exactly as before.

Closed-issue drift (S5, S16, S68 after closing) runs only with an explicit `ticket-doctor --since ISO` window, as the contract scopes it ("Source compatibility and migration", item 4): one bounded page of at most 50 closed issues updated since then is read live (never from a cache; `--offline` is refused), and only those carrying a delivery record are evaluated, at most 20. `closed-not-delivered` (S16) reports a `closed completed` issue whose delivery is not `delivered` or `attested` as a discrepancy, naming the closing login, never as proof of unauthorised closure; with an earlier `complete` record it is reported as the residual post-close race (S68). `closed-cleanup` (S5) turns required PRs left open or draft after a `not planned`, `duplicate` or other closure into close-or-explain attention for their responsible agent. `closed-delivery-unknown` covers unreadable or unverifiable evidence. A window with more issues, or a closed issue whose comment history is truncated before any record is seen, makes the scan incomplete rather than clean. No step ever reopens an issue. The JSON report gains `closedScan` only when `--since` is given.

Stale claims: `stale-agent-activity` now also states the ticket's delivery responsibility, and the deliverables the stale claimant is responsible for, or that responsibility is unknown. Releasing a claim never ends responsibility and inactivity never transfers it; the supported recovery stays the claimant-only release.

Not yet in this slice: delivery, responsibility and closure fields in briefing JSON, `pr`, `who`, `team` and the MCP read tools.

## Complexity label consistency

Follow [complexity-estimation.md](complexity-estimation.md): conflicting recognized size labels are an inspection finding, incomplete label evidence stays unknown, and no size is an ordinary unestimated ticket. Read-only doctors never create labels or repair conflicts. Native field mappings, definition discovery and creation-permission probes are removed by the labels-only replacement; no missing-label-definition setup warning is needed.
